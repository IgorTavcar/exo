Runtime internals

Harnesses & executors

The harness contract and the engine that runs it: how a submitted turn becomes a queue entry, a journaled turn, and a call into a Rust executor or a long-lived Node process speaking line-delimited JSON; how an interrupted turn is recovered; and where the "semantics vs. infrastructure" line is actually drawn in code.

Three things called "harness"

The word is overloaded in the source. Before reading code it helps to keep three layers apart; the docs' "harness" (website/docs-src/architecture/harnesses.md) is only the last one.

Two things worth noticing immediately. First, the Rust executors and the TypeScript runner write to the same TurnHandle: the event log is the only state both agree on. Second, with LocalProvider the Runtime never calls an executor directly; even a single in-process send goes through an (in-memory or durable) queue, so there is one code path for first runs, queued runs and recovery.

The turn lifecycle, as implemented

1. Admission and queueing

  1. Runtime::start_turn submits HarnessCommand::StartTurn(ProviderTurn) and waits on a oneshot receipt (crates/executor/src/harness_executor.rs:602-628). LocalProvider::submit forwards it to accept_local_turn (crates/executor/src/provider.rs:408-427).
  2. accept_local_turn snapshots the merged agent config (agent config artifact + thread model override + thread harness override, crates/executor/src/harness_executor.rs:914-930) and the conversation config into a TurnWork, allocates the TurnRecord (Uuid7::now(), reusing the caller's session_id if any), registers the stream observer before enqueueing so a live drain cannot miss it, then calls coordinator.enqueue (crates/executor/src/turn_queue.rs:388-423). Idempotency keys come back as accepted.duplicate and replay the finished result from the journal (crates/executor/src/turn_queue.rs:438-465).
  3. spawn_queue calls coordinator.claim(thread); only the holder of the per-thread TurnLease drains that thread, so turns on one thread are strictly FIFO and cross-process safe if the coordinator is (crates/executor/src/turn_queue.rs:529-579). The queue contract (enqueue / claim / peek / start / set_suspended / acknowledge / release_if_idle) is TurnQueue in crates/exoharness/src/turn_coordinator.rs:91-169.
  4. run_queue loops: peek the head, start it (which also returns a control watch stream of Run | Cancel | Suspend), open it, then select! between control updates (forwarded to the harness as Resume/Cancel/Suspend commands) and the execution stream (crates/executor/src/turn_queue.rs:581-704). After the stream ends it asks the journal, not the stream, whether the turn finished.

Durable queue is opt-in

LocalProvider::with_host builds StoredTurnCoordinator::in_memory() (crates/executor/src/provider.rs:131-157), so embedders using LocalProvider::basic / rlm / typescript get a queue that dies with the process. The CLI replaces it with the storage-backed one via .with_turn_coordinator(state.turn_coordinator()) (crates/cli/src/providers.rs:90-93); the worker runtime does the same (crates/worker-runtime/src/lib.rs:106-120). "Exo durably queues submitted turns" in the architecture doc is true of the shipped binaries, not of the library default.

2. Journal status decides what "start" means

open_queue_head never trusts in-memory state. It derives JournalStatus from three event kinds on the turn: TurnStarted without TurnEnded is Running, neither is Unstarted, TurnEnded is Finished (with an Error event meaning failed) (crates/executor/src/turn_queue.rs:849-892). Then:

  • Unstarted: run head.work from the queue entry with recovering = false.
  • Running: there is no in-memory work to hand over, so the TurnWork is parsed back out of the turn's own events (TurnWork::from_events) and executed with recovering = true (crates/executor/src/turn_queue.rs:794-801).
  • An Error event or the completion marker is already present: do not run anything, just finish() (crates/executor/src/turn_queue.rs:731-742).

The work is in the log because start_local_turn commits it atomically with the turn start:

BeginTurnRequest.initial_events is documented as "committed in the same write as TurnStarted and the input" (crates/exoharness/src/types.rs:397-406); work.event() is a Custom event named exo.runtime.turn_work (crates/executor/src/harness_executor.rs:37-72). A crash can therefore never leave a started turn without the configuration needed to resume it, and the configuration the turn started with is what recovery uses, even if the agent config changed in between.

Idea worth stealing: write the recovery inputs into the journal atomically with the start marker

Instead of a side table of "in-flight jobs", the turn's own event stream carries exo.runtime.turn_work. Recovery is then a pure function of the log: find turns with TurnStarted and no TurnEnded, read the work event, call resume_turn. See recovery_query (crates/executor/src/harness_executor.rs:1296-1309), which fetches exactly the five event kinds recovery needs.

3. Preparing and starting execution

start_local_turn (crates/executor/src/harness_executor.rs:630-895) is the glue: marks the thread's queue owner active, lazily inits the harness with the HarnessEvents sink (once, via OnceCell), materializes filesystem resources and appends their locations to agent_config.instructions as a system message (only on non-recovery runs), calls executor.prepare_conversation (the "called once before each execute/resume, under the thread's turn lease" hook, crates/executor/src/harness_executor.rs:145-156), calls begin_turn or turn_handle, registers the live turn, and submits an ExecutorTurn to ExecutorHarness.

ExecutorHarness::submit spawns a task that runs the executor future inside a biased select! against a watch channel carrying a StopReason (Cancel, Shutdown, Suspend), wraps the executor in catch_unwind, and converts the result to a HarnessTurnOutcome (crates/executor/src/harness_adapter.rs:141-325). On cancel, shutdown or suspend it also calls executor.cancel_turn (for TypeScript that kills the runner process). It then emits TurnFinished and ExecutionStopped into the sink.

4. Events are the only output channel

Whatever an executor appends goes through HarnessTurn::add_events (crates/executor/src/harness_events.rs:96-126), which emits HarnessEvent::TurnEvents; HarnessEvents appends to the real TurnHandle, then synthesizes the live stream: Messages, ToolRequested, ToolResult, LinguaStreamChunk become ExecutionStreamEvents, followed by a Checkpoint { event_id } after each persisted batch (crates/executor/src/harness_events.rs:189-261). Clients that disconnect resume with watch_turn(after = last checkpoint), which replays the same event format from storage (crates/executor/src/harness_executor.rs:540-591); live streaming and replay share turn_stream (crates/executor/src/harness_events.rs:322-394).

HarnessTurn also keeps a pending_tools set updated from ToolRequested/ToolResult acknowledgements. That set is the only piece of "tool semantics" the host infers from the event stream, and it exists to support one thing: a suspension boundary that waits until no tool call is in flight (crates/executor/src/harness_events.rs:46-73).

5. Finalization

The finalizer task spawned at the end of start_local_turn awaits the outcome and maps it (crates/executor/src/harness_executor.rs:824-891):

OutcomeWhat gets written
CompletedLooks for a exo.runtime.turn_completed custom event for this turn; adds it if the harness did not, then turn.finish() (appends TurnEnded).
Failed(e) / Cancelledfinalize_turn: append EventData::Error { message } then finish() (crates/executor/src/shared.rs:6-25). Cancel is just a failure with message "harness turn cancelled".
SuspendedNo terminal event. Returns TurnSuspended; the journal stays Running and the queue entry stays at the head with control = Suspend.
Interrupted (shutdown)No terminal event, error "harness turn interrupted"; the next process start recovers it.

Idea worth stealing: a completion marker closes the answer-to-TurnEnded crash window

If the process dies after the final assistant message is persisted but before TurnEnded, a naive recovery would re-run the model. BasicExecutor commits the last response events and exo.runtime.turn_completed in one add_events call (crates/executor/src/basic.rs:197-205); for harnesses that don't, the finalizer adds the marker itself. open_queue_head treats the marker as "just finish it" (crates/executor/src/turn_queue.rs:731-742).

The built-in Rust loop (BasicExecutor)

The Rust "basic" harness is the smallest complete example of the contract: rebuild the prompt from events every round, call the model, append, run tools, append results, repeat until a response has no tool calls.

  • The prompt is derived, not stored: materialize_prompt_history reads messages / tool_requested / tool_result / frontend_tool_response events with a per-conversation incremental cursor cache (crates/executor/src/basic.rs:80-133). Tool calls left dangling at a batch boundary get a synthetic "tool execution did not complete before the previous turn ended" result (crates/executor/src/message_history.rs:145; the TypeScript twin is exoharness/typescript/harness/index.ts:679-752).
  • A tool error does not end the turn: it becomes {"ok": false, "error": ...} as the tool result (crates/executor/src/basic.rs:289-303). Each tool is authorized (permissions::authorize) then executed; client ("frontend") tools are routed to frontend_tools::execute instead of ToolRuntime.
  • exo.basic.tool_round is written before the round's tool requests. On recovery load_turn_progress replays only tool_round / tool_requested / tool_result events, finds the first still-unresolved request and resumes the tool phase of that round; it never calls the model again for a round already committed, because "calling the model again could produce a different set of tool calls" (crates/executor/src/basic.rs:319-427). It refuses unless the unresolved call is a client tool or has a matching saved approval request.

TypeScript harnesses: process and wire protocol

How a module is loaded and run

There is no HTTP and no JSON-RPC 2.0. TypeScriptExecutor spawns a Node child per (conversation id, module path) and talks to it over stdin/stdout with one JSON object per line, discriminated by a kind tag and correlated by numeric id where a reply is expected.

  1. run_turn checks the module file exists, builds the key "{conversation_id}:{module_path}", and gets or starts a runner (crates/executor/src/native/typescript.rs:179-248).
  2. TypeScriptRunnerProcess::start runs node --import tsx exoharness/typescript/harness/runner.ts <module> with current_dir(workspace_root), kill_on_drop(true) and piped stdio (crates/executor/src/native/typescript.rs:286-333). The workspace_root for the built-in constructors is CARGO_MANIFEST_DIR/../.., resolved at compile time (crates/executor/src/native/typescript.rs:556-561).
  3. runner.ts import()s the module once, accepts a default export or a named harness export, and requires runTurn to be a function (exoharness/typescript/harness/runner.ts:234-249, exoharness/typescript/harness/runner.ts:278-293).
  4. For each turn the host sends an init message (a TypeScriptInitPayload: agent, conversation, turn record, both configs, the SendRequest, streaming, recovering, tool definitions, native MCP servers; crates/executor/src/typescript_runtime.rs:522-535). The runner builds a TurnContext from it (exoharness/typescript/harness/client.ts:1103-1224) and calls runTurn or resumeTurn.
  5. The runner replies done or error, then loops waiting for the next init. The Node process and any module-level state stay warm across turns of the same conversation.

The TypeScript mirror is HostToGuestMessage / GuestToHostMessage in exoharness/typescript/harness/client.ts:411-435; wire.ts only converts snake_case config records to camelCase (exoharness/typescript/harness/wire.ts:60-120).

Host-side multiplexing

The host's turn loop is a single biased select! over finished tool futures, the next stdout line, and a 100 ms child-exit poll (crates/executor/src/native/typescript.rs:414-505). Details that matter:

  • runtime_requests are pushed into a FuturesUnordered and answered whenever they finish, so a tool waiting on a human approval does not block output, other requests or noticing that the runner died. There is a test for exactly this (crates/executor/src/native/typescript.rs:1252-1345).
  • exo_requests are awaited inline. A TurnAddEvents whose agent, conversation, session and turn ids all match the running turn is routed to the host's TurnHandle (i.e. through HarnessTurn, so pending-tool tracking and the stream relay apply); any other request goes to ExoHarnessServer::handle_request (crates/executor/src/native/typescript.rs:450-462).
  • A line that fails to decode is not fatal. If the lenient GuestMessagePreview can still recover kind and id, the host replies with ok: false so the guest's pending promise rejects; otherwise the line is logged and dropped (crates/executor/src/native/typescript.rs:508-528, crates/executor/src/native/typescript.rs:587-632).
  • The runtime half (TypeScriptRuntime) is deliberately transport-free: "Hosts only transport runner requests and events" (crates/executor/src/typescript_runtime.rs:1-2). The Cloudflare Durable Object host reuses it from WASM and supplies a different HarnessClient to createTurnContext instead of stdio (exoharness/cloudflare/src/runtime-io.ts:420-465). HarnessClient (exoharness/typescript/harness/client.ts:449-458) is the real TypeScript transport abstraction.

What runTurn gets

There is no beginTurn in the TypeScript API. The host has already begun the turn; the harness receives it as context.exoharness.current.turn, a Turn with addEvents and writeArtifact* and no finish() (exoharness/typescript/harness/index.ts:378-398). (The wire type does include a turn_finish request, exoharness/typescript/harness/client.ts:380, served by crates/exoharness/src/server.rs:550, but no TS API method sends it.) Returning from runTurn sends done; the host adds the completion marker and TurnEnded. A harness reads history through context.exoharness.current.conversation.getEvents(), usually via materializePromptMessages, and writes messages, tool_requested, tool_result events with the helpers in index.ts (messagesEvent, toolRequestedEvent, toolResultEvent, appendCustomEvent).

The stock loop, runResponsesHarnessTurn (exoharness/typescript/model-runtime/turn-loop.ts:34-217), is the TypeScript twin of BasicExecutor: per round it rebuilds the tool registry, validates tool policies, materializes prompt messages from events, calls the Responses runtime (streaming through context.stream.text if context.streaming), appends response events, and for each tool call runs tools.executePending then appends the result events. It writes no round marker and defines no resumeTurn, so a basic-harness.ts-style module cannot be recovered (below). Hooks instructions(context) and registerTools(registry, context) are re-run every round, which is what the custom-harness tutorial uses to inject live context. Tool registry details, MCP and permissions: tools-and-mcp. Prompt text: prompts.

Warm runners and reusable sandbox processes

The runner is cached in TypeScriptExecutor.runners and reused for the next turn of the same conversation. It is dropped (process killed) on: any failed turn, cancel_turn (called after cancel, shutdown and suspend), executor shutdown, or when a sandbox process the previous turn marked reusable is no longer running (crates/executor/src/native/typescript.rs:179-217). A harness opts a child process into warm reuse with startSandboxProcess({ command, reuseKey }). The host records a typescript_sandbox_process_reuse custom event; the next runner (even after a service restart) finds the newest event for that key and sandbox, attaches to the still-running process from its latest cursor and reports reused: true. An exited newest generation is never resurrected by an older still-running one (crates/executor/src/typescript_runtime.rs:397-467, with a regression test at crates/executor/src/typescript_runtime.rs:789-884). This is what lets the Codex adapter keep a native app-server alive across turns and reconnect to it after a restart (native-harnesses).

Surprise: "shutdown" is a kill, and the shutdown message is dead code

HostToGuestMessage::Shutdown exists on both sides, but nothing in the Rust crate ever constructs it (crates/executor/src/native/typescript.rs:569 is the only occurrence). TypeScriptRunnerProcess::shutdown is child.kill() plus cancelling tracked sandbox processes (crates/executor/src/native/typescript.rs:278-284). A harness has no hook to flush or clean up; anything it must preserve has to already be in events or artifacts.

Warm runner caveats

The module is imported once per runner process (exoharness/typescript/harness/runner.ts:286-289) and the cache key has no file mtime or content hash, so editing a harness file does not affect conversations whose runner is still warm. I found no idle eviction in TypeScriptExecutor: one Node process per active conversation persists until failure, cancel or shutdown. The runner inherits the host environment plus the executor's env map (command.envs(env), crates/executor/src/native/typescript.rs:305-306).

Surprise: the harness process gets the whole ExoHarness API

Every exo_request other than the matching TurnAddEvents is served by ExoHarnessServer over the executor's root ExoHarness (crates/executor/src/native/typescript.rs:390, crates/executor/src/native/typescript.rs:461). The TypeScript ExoHarness type exposes newAgent, deleteAgent, createVault and vault secret reads/writes, not just the current turn (exoharness/typescript/harness/index.ts:322-334). Whatever limiting exists comes from the state object the provider was built with (with_state for caller-scoped runtimes), not from the runner protocol. This matches the architecture doc's trust model ("Harness modules ... run as trusted code in the harness process"), but it is broader than "a turn handle".

Recovery, suspend and resume

The pieces

  1. On startup the service calls Runtime::recover_unfinished_turns (once, OnceCell-guarded; crates/executor/src/harness_executor.rs:392-397, called from crates/executor/src/native/http_service.rs:110). For the local provider that is coordinator.pending_threads() followed by drain_queue for each (crates/executor/src/harness_executor.rs:593-600). Concurrency is a semaphore of 4 permits unless set_recovery_concurrency says otherwise (crates/executor/src/harness_executor.rs:209-215, crates/cli/src/serve.rs:46). Caller-scoped queue entries need a recovery_resolver to build a runtime with the right principal.
  2. open_queue_head classifies the head via the journal and calls execute_turn(..., recovering = true) for Running turns (above).
  3. ExecutorHarness::submit runs restore_recovery_tools unless the executor reconciles tool calls itself. It scans the turn for tool_requested without a matching tool_result, and refuses to continue (cannot safely resume unresolved tool call ...) unless that call is a client tool or the executor can resume a pending approval and an unanswered approval request matches (crates/executor/src/harness_adapter.rs:328-410).
  4. The executor's resume_turn runs. For Basic that is the round-marker replay above. For TypeScript it is init.recovering = true and runner.ts decides:

hasUnresolvedToolCalls counts tool_requested minus tool_result per tool_call_id for the current turn (exoharness/typescript/harness/runner.ts:251-276). So the Rust-side gate (can_reconcile_unresolved_tool_call = config.typescript.is_some(), crates/executor/src/native/typescript.rs:72-74) always defers the decision to the module, and the module's own gate is the one that matters. Tests: a module with reconcileUnresolvedToolCalls: true gets resumeTurn, not runTurn, after a simulated crash (crates/executor/src/native/typescript.rs:905-1031); a module that has resumeTurn but not the flag is rejected when a tool call is open (crates/executor/src/native/typescript.rs:1033-1141).

Suspend and resume

Suspension is a queue-level control (TurnControl::Suspend) distinct from cancel. set_queued_suspended only checks executor.can_suspend_turn(config) and then flips control in the coordinator (crates/executor/src/turn_queue.rs:284-319). Inside ExecutorHarness the behavior depends on the other flag:

  • Resumable but not reconciling (Basic): set suspending, wait on suspension_boundary until pending_tools is empty, then drop the execution future while holding the guard so it cannot journal another tool request. Suspension never interrupts an in-flight tool.
  • Reconciling (TypeScript): suspend immediately, even with a tool in flight, then cancel_turn kills the runner. Safety is pushed to resumeTurn.
  • Not resumable (Rlm): set_queued_suspended returns false before touching the queue, and the harness ignores a stray Suspend signal.

Suspend is accepted for TypeScript harnesses that cannot resume (from reading, not run)

ManagedExecutor::can_suspend_turn is true for every AgentHarnessKind::TypeScript config (crates/executor/src/native/managed_executor.rs:136-141), and the Rust side does not look for a resumeTurn export. Suspending a Claude Code or Pi turn therefore kills its runner; resuming it re-enters as recovering = true, hits the "cannot safely resume an unfinished turn" branch in runner.ts, and fails the turn. Only modules that export resumeTurn (Codex) get a real suspend/resume.

The RLM harness

"RLM" (recursive language model) here is a harness that does not show the model the conversation. It hands the model a persistent JavaScript REPL in which the full transcript is a variable, plus the ability to ask sub-LLM questions about slices of it. The model works by writing code that inspects and chunks context and calling subquery over the chunks.

Mechanism (Rust, AgentHarnessKind::Rlm)

  1. At turn start, materialize all conversation messages and flatten them to a USER:\n... / ASSISTANT:\n... transcript; build JsReplState::new(context_text, history_messages) and append an rlm_context_initialized custom event (crates/executor/src/native/rlm.rs:54-70).
  2. The prompt is just instructions + an RLM system prompt + a root prompt with the latest request, a 400-char preview and metadata (crates/executor/src/native/rlm.rs:72-80, crates/executor/src/native/rlm.rs:613-685). Prompt text lives on prompts.
  3. Each round exposes three built-in tools (repl_execute, subquery, subquery_variable, crates/executor/src/native/rlm.rs:687-750) plus any external and client tools. The model response goes through complete_model_round with ModelStreamOutput::Internal: chunks are used for TTFT but not shown to the user (crates/executor/src/native/rlm.rs:108-116).
  4. repl_execute evaluates JS in the Boa engine. State is a JSON Map in Rust; each call builds a fresh BoaContext, injects context, getMessages(role), print and the saved globals, evals the code, then reads back every JSON-serializable global (crates/executor/src/native/harness_js_repl.rs:27-111). Only JSON-compatible values persist between calls; functions and closures do not.
  5. subquery / subquery_variable call ModelClient::complete directly with the instructions, a fixed "You are a subquery model ... Do not call tools" system message, and the prompt (or question + variable value). The result may be stored into a REPL global via target_var (crates/executor/src/native/rlm.rs:336-387).
  6. Termination: a response with no tool calls ends the turn, taking the answer from FINAL(...), FINAL_VAR(name) or the plain text; or any tool call that leaves globalThis.Final non-null (crates/executor/src/native/rlm.rs:132-136, crates/executor/src/native/rlm.rs:275-278, crates/executor/src/native/rlm.rs:581-611).
  7. Persistence: only rlm_* custom events (rlm_model_response, rlm_tool_call, rlm_tool_result, rlm_final_answer) plus one final Messages event with the answer. Intermediate model turns are not messages events, so they never enter later prompts or materialize_conversation_messages.

Surprise: the RLM is neither resumable nor error-tolerant, and "recursive" is one level deep

(1) RlmExecutor implements only execute_turn, so recovery fails by default. (2) A tool error returns Err out of the whole turn loop (crates/executor/src/native/rlm.rs:242-247), whereas BasicExecutor turns it into an {ok:false} tool result. (3) run_subquery passes no tools and tells the sub-model not to call any, so recursion depth is exactly one; the recursion is the model's own loop of repl_execute over sub-answers. (4) Sub-queries use model.complete directly, with no turn trace and no persisted event of their own, only the tool result. (5) The REPL state lives in process memory and is rebuilt from the transcript each turn: variables from a previous turn are gone.

A second implementation

There is also a TypeScript RLM at exoharness/examples/typescript/rlm-harness.ts with the same tools and event names but node:vm as the engine (it records engine: "node_vm" vs the Rust "boa_js", exoharness/examples/typescript/rlm-harness.ts:114). The Rust one is selected by harness: rlm; the TS one by pointing harness: at the file. The two share no code: the loop, REPL wrapper and prompts are written twice.

Scheduler and wakeups

"Scheduling" in the executor crate is narrower than the name suggests. It runs shell commands in a sandbox on a timer and then wakes a conversation with a report; no model runs at the scheduled time.

  • Data: SchedulerStore keeps JSON files: tasks/{id}.json, per-task runs/, and pending-fire records, written via temp-file + rename (crates/executor/src/native/scheduler_store.rs:14-60, crates/executor/src/native/scheduler_store.rs:266-278). It is outside the event log; the log only sees the resulting wakeup turn and the result artifact. Records are schema-versioned with one-step migrations that refuse records from newer builds (crates/executor/src/native/scheduler_types.rs:13-16, crates/executor/src/native/scheduler_types.rs:390-418).
  • Creation: the Exo harness kind's ExoToolRuntime gives the model schedule_sandbox_task, list_scheduled_tasks, cancel_scheduled_task, delete_scheduled_task (crates/executor/src/native/harness_tool.rs:117-145; see tools-and-mcp). Schedules are @every 30m, @at <rfc3339>, or exactly */N * * * *; no other cron syntax (crates/executor/src/native/scheduler_types.rs:427-461).
  • Execution: run_due_tasks claims due tasks with a 10-minute lease, then run_task consults plan_missed_fires. MissedPolicy is Skip, Once or All (capped at MAX_MISSED_FIRE_CATCHUP = 100). Fires land on anchor + n * interval, not "last finish + interval" (crates/executor/src/native/scheduler_runtime.rs:46-126, crates/executor/src/native/scheduler_types.rs:72-90, crates/executor/src/native/scheduler_types.rs:272-300). Sandbox mode is Agent, Conversation or TaskFresh.
  • Reporting: stdout/stderr go into a conversation artifact scheduled-tasks/{name}/{run}.json, then send_conversation_wakeup submits a normal user-role turn containing the report prompt and previews, and ends the session (crates/executor/src/native/conversation_wakeup.rs:12-40).

On startup redeliver_pending_wakes resends any unconfirmed fire (at-least-once; the (task, slot) key bounds repeats; fires whose agent or conversation vanished are retired, crates/executor/src/native/scheduler_runtime.rs:71-102).

Surprise: nothing in the server starts the scheduler

run_due_tasks and redeliver_pending_wakes are exported, but the only caller in the repo is a separate binary, examples/self-improving-agent/scheduler-runner/src/main.rs:60-90, which takes a SchedulerRunnerLock and polls. exo serve does not drive tasks, and the CLI's only use of send_conversation_wakeup is conversation send (crates/cli/src/main.rs:1978). The runner is built and launched by examples/self-improving-agent/exo.sh. Scheduled tasks created by an exo-kind agent will not fire unless that runner is running. The executor crate treats the scheduler as a library plus store, not a service.

Surprise: wakeups are serialized with a temp-dir lock file, outside the durable queue

send_conversation_wakeup first acquires $TMP/exo-wakeup-locks/{conversation}.lock via create_new, polling every 100 ms and breaking locks older than 30 minutes (crates/executor/src/native/conversation_wakeup.rs:42-107), and only then calls Runtime::send. This serializes concurrent scheduler runners and CLI sends on one machine; it does nothing across hosts, and the turn queue already serializes per thread. The lock is belt-and-braces for callers waiting on send, not part of the recovery design.

Related host-side event writers: record_host_event and complete_rebuild_and_restart_update append Custom events (e.g. rebuild_and_restart_exo) so host actions land in the same log the agent can read back via list_conversation_events (crates/executor/src/native/conversation_events.rs:1-12, crates/executor/src/native/conversation_events.rs:106-132). agent_sandbox.rs holds the agent-scoped sandbox, recorded in config/agent-sandbox-v2.json and deliberately not recreated when agent config drifts (crates/executor/src/native/agent_sandbox.rs:10-12, crates/executor/src/native/agent_sandbox.rs:66-73); see sandboxes.

Where the semantic/infrastructure line is actually drawn

Reading the line

The boundary is a placement convention over a shared event log, not a type-system wall. The host enforces ordering, authorization, sandbox access and journaling; it cannot stop a harness from writing arbitrary events, and does not need to, because recovery only trusts what recovery code replays. Because the Rust "basic" loop is itself a harness living in the host process, the same line runs through the middle of the Rust crate: basic.rs and rlm.rs are on the semantic side, harness_executor.rs, harness_adapter.rs, turn_queue.rs on the infrastructure side.
