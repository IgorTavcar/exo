Runtime internals

Egress, secrets & vaults

How Exo lets an agent sandbox use API keys it can never read: a per-sandbox TLS-intercepting proxy swaps placeholder strings for real secrets from an encrypted vault, but only on requests to hosts that three independent allowlists agree on.

The idea in one picture

The sandbox gets placeholders, never secrets. Inside the VM, OPENAI_API_KEY is the string exo_egress_<32 hex>. Everything the VM sends over TCP 80/443 (and DNS) is redirected by the host firewall to a per-sandbox proxy in the Exo runtime. The proxy terminates TLS with a throwaway CA the guest was told to trust, checks the request, asks a EgressCredentialResolver for the real value, rewrites the header, and forwards to a pinned public IP. The real value exists only in the runtime's memory and in the encrypted vault file.

  sandbox (Firecracker / SmolVM)            host: one EgressProxy per sandbox
  ------------------------------            ------------------------------------------------
  OPENAI_API_KEY=exo_egress_ab12..          nft DNAT 80/443/53 -> listeners (source-IP bound)
  curl https://api.openai.com/v1/..   --->  TLS accept (leaf signed by throwaway CA)
    Authorization: Bearer exo_egress_ab12     1. Host == SNI == allowed host, port 443, no "//"
                                              2. placeholder only in a plain header, HTTPS only
                                              3. binding's own host/URL allowlist permits dest
                                              4. resolver -> sandbox's pinned SecretReference
                                              5. vault: secret's own policy permits dest (AAD-bound)
                                              6. swap, resolve DNS -> public IPv4 only, pin, no redirects
                                        ---> api.openai.com   Authorization: Bearer sk-real...

Code map: the HTTP/TLS machinery is crates/exoharness/src/egress/mod.rs; the substitution rules and the resolver trait are crates/exoharness/src/egress_credentials.rs; vault storage is crates/exoharness/src/vault.rs + crates/exoharness/src/vault/local.rs; encryption is crates/exoharness/src/secrets.rs; the CLI is crates/cli/src/vaults.rs. Sandbox providers themselves are covered in Sandboxes; MCP in general in Tools & MCP.

Threat model

The adversary is code running inside the sandbox: a prompt-injected model issuing arbitrary shell commands, a malicious dependency, a compromised build script. It can read every env var and file in the guest, craft any HTTP request, point DNS wherever it likes, and open any socket. The Exo runtime, its state directory and master key are trusted.

Forcing traffic through the proxy, per provider

The proxy is only constructed when it is needed: EgressPolicy::requires_proxy() is true if there are credential bindings, an allowed_tcp_ports list, or Limited networking (crates/exoharness/src/types.rs:948-953). Plain unrestricted or disabled networking uses the backend's own rules and no interception (crates/exoharness/src/egress/sandbox.rs:262-265). A proxied sandbox must also have a managed lifecycle (idle_ttl), otherwise acquisition fails (crates/exoharness/src/egress/sandbox.rs:267-270).

What the Firecracker firewall actually says

On top of the firewall, the listener itself checks who is connecting. LocalEgressTransport holds a single atomic "bound source" (the guest IPv4) set once by bind_source via compare-and-swap; accepts_peer drops any connection whose peer differs, and 0 means "no one admitted yet" (crates/exoharness/src/egress/transport.rs:255-265, :308-314). The proxy is created before the VM boots (so its endpoints can be written into the firewall) but admits nobody until the VM's address is bound (crates/exoharness/src/egress/sandbox.rs:286-291).

For non-80/443 TCP in restricted mode, the firewall only permits destinations in the allowed_hosts nft set. That set is filled by the DNS service: it resolves an allowed name on the host, admits the addresses, and only then answers the guest, so "a connection cannot race its firewall rule" (crates/exoharness/src/egress/transport.rs:394-427). Entries expire after an hour.

DNS is part of the policy engine

There are two layers. The base dns_response answers an allowed name's A query with the fixed synthetic address 192.0.2.1 (TTL 0) and every other name, including subdomains like leak.api.test, with NXDOMAIN (crates/exoharness/src/egress/transport.rs:429-462; test crates/exoharness/src/egress/tests.rs:1061-1100). On Firecracker, network_dns_response then throws that synthetic answer away and substitutes the real public IPv4 addresses (TTL 60) resolved on the host by FirecrackerDns, after adding them to the VM's nft allowed_hosts set (crates/exoharness/src/sandbox_provider/firecracker.rs:3592-3661). HTTP(S) works either way because the DNAT rule ignores the destination IP; the real addresses only matter for non-HTTP TCP. In limited mode, DNS lookups of non-allowed names (the classic exfiltration channel) die at the first hop; unrestricted mode answers everything.

TLS interception and the CA

Yes, it is a full MITM, scoped to the hosts that need it. tls_configuration builds a brand-new CA and a single leaf certificate per sandbox, and returns only the CA certificate PEM and a TlsAcceptor:

  • One leaf, SANs are the interception set. In Limited mode that is every allowed host. In Unrestricted mode it is only the hosts named by credential bindings (crates/exoharness/src/egress/mod.rs:256-263).
  • Trust installation is per-process env, not the system store. After boot the handle runs PREPARE_TRUST, which copies /etc/ssl/certs/ca-certificates.crt to /tmp/exo-egress-<uuid>.pem and appends the CA (crates/exoharness/src/egress/mod.rs:823-830). Every command then gets SSL_CERT_FILE, CODEX_CA_CERTIFICATE, REQUESTS_CA_BUNDLE, NODE_EXTRA_CA_CERTS, CURL_CA_BUNDLE and GIT_SSL_CAINFO pointing at it, overriding anything the caller passed (crates/exoharness/src/egress/sandbox.rs:119-136). Clients with their own trust store (Java, browsers) are not covered.
  • HTTP/1.1 only (ALPN). WebSocket upgrades and CONNECT are refused with a denial in rewrite_headers (crates/exoharness/src/egress_credentials.rs:441-446).
  • Unrestricted mode does not MITM public sites. transparent_https_connection peeks the ClientHello with rustls::server::Acceptor, extracts the SNI, and either intercepts (SNI is a credential host) or copy_bidirectionals the original bytes to the real server. The test transparent_unrestricted_egress_intercepts_credentials_and_preserves_public_tls asserts a client that trusts only the upstream's CA still reaches public.test (crates/exoharness/src/egress/mod.rs:656-717, crates/exoharness/src/egress/tests.rs:1782-1867).

Idea worth stealing: placeholders are minted per sandbox, so they are not even portable between sandboxes

Each proxy mints its own exo_egress_<uuidv4> per binding (crates/exoharness/src/egress_credentials.rs:100-116). Sandbox A's placeholder presented to sandbox B's proxy fails validation ("credential placeholder does not match this request") and never reaches the resolver; the test expects a 502 (crates/exoharness/src/egress/tests.rs:1820-1828). Combined with the CA being per sandbox, an exfiltrated placeholder or CA bundle is worthless elsewhere.

Evaluation order for one HTTPS request

  1. Peer. Listener accepts only the bound guest IP (or, for SmolVM, a stream carrying the right token and a public IPv4, non-IPv6 destination).
  2. Port and host. transparent_https_connection calls check_port(443). In limited mode every connection is intercepted; in unrestricted mode the SNI is peeked and the host must satisfy permits_host.
  3. Request shape (State::destination, crates/exoharness/src/egress/mod.rs:402-458): not CONNECT; origin-form URI; exactly one Host; host canonicalised and permitted; standard port; SNI equals Host; path starts with / but not //; the parsed URL's authority is unchanged. Violations are plain anyhow errors and therefore a generic 502.
  4. Upstream client (State::client): resolve DNS now, keep only public IPv4, pin with resolve_to_addrs, no_proxy(), redirect(Policy::none()). The client pool is keyed on (host, port) and rebuilt whenever the resolved set changes (test crates/exoharness/src/egress/tests.rs:1579-1625).
  5. Header rewrite (rewrite_headers): reject Upgrade/CONNECT, validate_credentials, strip hop-by-hop headers (including those named in Connection), then substitute_credentials.
  6. Resolver, which re-checks the secret's own policy (next section).
  7. Relay. Request bodies are fully buffered with a 128 MiB cap (EXO_EGRESS_MAX_REQUEST_BODY_BYTES), responses stream. On a 401 with substituted credentials, one refresh-and-retry.

Connection hygiene: at most 128 concurrent connections per proxy (MAX_CONNECTIONS), a 30-second I/O timeout (IO_TIMEOUT) for TLS accept, header read, body read, resolver call and refresh call, and 10 seconds to connect upstream (crates/exoharness/src/egress/mod.rs:53-57).

Public-IP filter is conservative and IPv4-only

public_ipv4 rejects 0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, multicast and above, and every IPv6 address, including ::ffff:8.8.8.8 (crates/exoharness/src/egress/mod.rs:527-549; test crates/exoharness/src/egress/tests.rs:929-944). A host that has only AAAA records is unreachable through the proxy.

Credential substitution

Anatomy of a binding

A binding says: "environment variable V in the guest stands for secret name, usable on these hosts/URLs, in these places". prepare_bindings validates the variable name ([A-Za-z_][A-Za-z0-9_]*, no duplicates), normalises the networking policy, and mints (or validates, when caller-supplied) a placeholder of exactly exo_egress_ + 32 hex characters (crates/exoharness/src/egress_credentials.rs:71-124).

Where substitution happens

Request headers only. There is no URL or body substitution: validate_credentials and substitute_credentials iterate headers and nothing else, and CredentialInjectionLocation (deny_unknown_fields) rejects {"header": true, "body": true} (test crates/exoharness/src/egress/tests.rs:1007-1010). A placeholder in a URL or body is simply forwarded as the inert literal. Within headers the placeholder may be anywhere in the value, so Bearer <ph>, a bare x-api-key, and Token <ph>; scope=read all work (test crates/exoharness/src/egress/tests.rs:553-621). There is one special case: for Authorization: Basic the proxy base64-decodes the value, substitutes inside user:pass, and re-encodes (crates/exoharness/src/egress_credentials.rs:209-225, used by the Git smart-HTTP flow).

The last ensure! is the heart of the exfiltration defence. It removes every placeholder the binding set is allowed to resolve for this destination and then fails if any exo_egress_ text survives. A request that carries a placeholder to a host the binding does not cover is rejected before the resolver is ever called, and before any upstream connection is opened. The tests assert this directly: after sending the placeholder to public.test and with a spoofed Host: public.test, resolver.uses is empty and upstream.connections == 0 (crates/exoharness/src/egress/tests.rs:795-815).

set_sensitive(true) marks the header so hyper/reqwest debug output redacts it. The substituted pairs are returned so the 401 path knows exactly which credential values were rejected.

Host-binding: three allowlists that must all agree

A secret reaches an upstream only if all three of these independently permit the destination:

  1. The sandbox network policy (NetworkPolicy::permits_host): can the sandbox talk to that host at all.
  2. The binding's CredentialNetworkPolicy (Binding::permits_header, crates/exoharness/src/egress_credentials.rs:59-69): is the binding's host set a member and does the policy allow https://host:port/path.
  3. The secret's own stored CredentialPolicy, evaluated inside BasicVaultHandle::read_for_destination (crates/exoharness/src/vault/local.rs:451-479) with an error that tells the operator to use --allow-origin / --allow-url.

The docs state the consequence: "Expanding the sandbox's allowlist never expands a credential's allowed destinations." Layer 3 matters because layer 2 is built from the policy at sandbox creation time, whereas layer 3 is read live from the vault on every request, so shrinking or deleting a secret's policy takes effect immediately.

Origin vs URL destinations (crates/exoharness/src/credential_policy.rs:65-72): an Origin policy permits any destination with the same scheme+host+port; a Url policy permits only the identical normalised URL; an Origin never matches inside a Url policy and vice versa. The unit test lists the edge cases (api.example.evil, ?tenant=two, trailing slash) at crates/exoharness/src/credential_policy.rs:209-239.

A non-443 origin grant can never be used through the sandbox proxy

CredentialDestination::origin("HTTPS://API.EXAMPLE:8443") is accepted and tested (crates/exoharness/src/credential_policy.rs:212), and the docs say credentials "authorize one exact HTTPS origin, including its port". But http_destination only admits ("http", 80) and ("https", 443) (crates/exoharness/src/egress_credentials.rs:360-363), and model/MCP/Git bindings additionally insist on 443. Such a grant is useful for host-side (non-sandbox) resolution only.

From placeholder to secret: the resolver chain

The EgressCredentialResolver trait (crates/exoharness/src/egress_credentials.rs:29-51) is the extension point: resolve(identity, binding_name, destination) -> Result<String, EgressError> plus an optional refresh. The local implementation is LocalEgressResolver (crates/exoharness/src/basic/egress.rs):

  1. Load the persisted sandbox record and require sandbox.running.
  2. If an access policy is installed, rebuild the sandbox's authenticated Caller and re-run harness.check(scope), so revoking a user's access to the thread revokes the sandbox's secrets.
  3. Look up sandbox.credentials[binding_name], a SecretReference { vault_id, secret_id } pinned when the sandbox was created (crates/exoharness/src/basic/sandboxes.rs:1777-1790).
  4. egress::vault::resolve_credential builds the target URL from host, port and path and calls vault.resolve_secret(secret_id, target) (crates/exoharness/src/egress_credentials/vault.rs:33-58).

Idea worth stealing: bind names to IDs at attach time, resolve values at use time

Binding names for model/Git/MCP credentials are the secret's ID (reference.secret_id.to_string(), crates/executor/src/sandbox_policy.rs:146-165). So rotation (same ID, new value, bumped revision) is picked up on the very next request, while deletion fails closed and "recreating its name does not restore access for the old sandbox" (docs/egress.md). Name-to-ID resolution happens exactly once, at sandbox creation, via find_secret; a later secret with the same name in a higher-precedence vault cannot hijack a running sandbox.

Another narrowing step: when the CLI turns a vault secret into a binding it calls CredentialPolicy::for_destination, which replaces the secret's possibly-broad policy with exactly the one destination the harness needs (crates/exoharness/src/credential_policy.rs:114-121). A GitHub token whose policy permits both github.com and api.github.com becomes a Git-origin binding for the repo host plus a separate GH_TOKEN binding for api.github.com; a model key becomes a binding for the model's origin only; an MCP credential becomes a binding for the exact MCP URL (crates/executor/src/sandbox_policy.rs:53-242).

401 handling and OAuth refresh in the proxy

If the upstream answers 401 and credentials were substituted, State::forward calls resolver.refresh(identity, name, destination, rejected_value) for each substituted credential. If any returns a new value, headers are rebuilt from the original, pre-substitution header map and the request is replayed once with the same buffered body (crates/exoharness/src/egress/mod.rs:370-398). The local resolver only returns a value that differs from the rejected one (crates/exoharness/src/basic/egress.rs:62-73). 403 never triggers a refresh. Test oauth_retries_once_with_the_original_mcp_body_and_session checks the three outcomes (refreshed 200, still-401 after one refresh, 403 with zero refresh calls) and that mcp-session-id and the body survive the replay (crates/exoharness/src/egress/tests.rs:1684-1716).

Typed rejections to sandbox clients

Commit 58fa2ff (#405) changed the resolver contract from anyhow::Result to a three-variant error so that a resolver can tell the sandbox why a request was refused without leaking internals:

Nothing in the repo produces Rejected yet

A grep for EgressError::Rejected finds the definition, the two match arms (crates/exoharness/src/egress/mod.rs:599, crates/worker-runtime/src/operations.rs:152) and tests. Both in-tree resolvers (LocalEgressResolver and the session Resolver) convert vault errors through ? into Internal, so a message like "secret X is not authorized for https://..." from read_for_destination still surfaces to a local guest as the generic 502. The hook exists for hosted resolvers. Also note the commit message and PR call the type EgressRejection; the merged type is EgressError::Rejected.

Vaults

Data model

A VaultRecord is {id, name, created_at}; a vault holds secrets, each with a SecretMetadata (id, name, type, optional policy, monotonically increasing revision) and an encrypted payload (crates/exoharness/src/types.rs:1294-1303). The Secret payload is a tagged enum (crates/exoharness/src/types.rs:1498-1538):

Secret variantFieldsRefresh
Keyvaluenone (rotate with exo vault secret update --token-env)
Oauthaccess_token, refresh_token, expires_at, refresh: OAuthRefresh (token endpoint, client id/secret, resource, scopes)proactive (60 s before expiry) and reactive (after upstream 401)
GithubClivalue, accountre-reads gh auth token --user <account> on the runtime host at most every 24 h; only creatable on a local vault (require_portable_secret)

Validation (crates/exoharness/src/vault.rs:75-101): if a policy is set, the bearer value must be non-empty ASCII graphic (no whitespace or control characters, so it can never smuggle a header line); OAuth token endpoints must be HTTPS or loopback HTTP.

Scoping and precedence

The code has no "user/agent/thread vault" types; scope is composition. A VaultContext lists vaults in increasing precedence and find_secret walks them in reverse, so the last match wins (crates/exoharness/src/vault.rs:178-198):

  global  (always)  <  [personal: the signed-in user's vault, on authenticated servers]
          <  agent.vaults  <  thread.vaults  (later attachments beat earlier ones)
  • Agent: BasicAgentHandle::list_vaults starts from the global vault, adds the caller's default ("personal") vault when authenticated, then the agent's attached vaults. Thread: the agent's list plus the thread's attached vaults (crates/exoharness/src/basic/access.rs:222-290). Unauthenticated local use goes through compose_vaults, which de-duplicates so an explicitly attached vault moves to the end (crates/exoharness/src/vault.rs:164-176).
  • Resolution by ID wins over names: a secret literally named like another secret's UUID in a different vault cannot shadow it (secret_ids_cannot_be_shadowed_by_names, crates/exoharness/src/vault/local/tests.rs:464-490).
  • For MCP, VaultSelection::from_vaults picks per-server credentials by policy match, preferring an exact URL grant over an origin grant, and errors when two secrets in the same vault tie ("narrow their policies to select one credential"). The selection is saved as a thread artifact and cannot be changed afterwards (crates/managed-agents/src/vaults.rs:49-86, :123-139).
  • Names are unique within a vault, and so are Url-style resource policies (one secret per exact MCP URL per vault) (crates/exoharness/src/vault/local.rs:317-325).

OAuth login and refresh

  • Interactive login for MCP servers (--url / --from-agent): prepare_mcp_login does standard discovery via rmcp, falling back to probing for a 401 WWW-Authenticate challenge (crates/cli/src/vaults/login.rs:162-185). crate::oauth::authorize_with binds 127.0.0.1:0, runs a one-shot actix server for /callback, checks the state parameter against a CSRF token, supports RFC 9207 iss, and times out after 300 s or on Ctrl-C (crates/cli/src/oauth.rs:73-150). Tokens are held in an in-memory credential store and only written to the vault afterwards; failed_authorization_preserves_existing_vault_entry covers the failure case.
  • Device flow (--client-id + --device-url/--token-url, or the GitHub defaults): crates/cli/src/vaults/login.rs:240-298. Error text from the OAuth server is escape-sanitised before printing (test device_login_reports_errors_without_echoing_server_secrets).
  • Refresh lives in the vault, not the proxy: BasicVaultHandle::resolve_credentials refreshes when an OAuth secret expires within 60 s (crates/exoharness/src/vault/local/oauth.rs:19-21), and refresh_secret forces it after an upstream rejection. It uses the oauth2 crate with redirects disabled (crates/exoharness/src/vault/local/oauth.rs:110-122).

Idea worth stealing: refresh tokens rotate, so never let the caller's cancellation lose the new one

Many OAuth servers invalidate the old refresh token the moment they issue a new one. If the request that triggered the refresh is cancelled after the server responds but before the vault write, the grant is bricked. Exo runs the refresh on a spawned task, serialises it with a file lock (oauth.lock, 60 s wait) so multiple processes sharing a state dir cooperate, and persists with a revision check. Tests: refresh_survives_cancellation_and_persists_before_reuse (abort the caller, still see the rotated token on disk after reopening, crates/cli/tests/vault_oauth.rs:795-849), refresh_cannot_restore_a_revoked_or_manually_rotated_secret (delete or overwrite the secret mid-refresh and the refresh result is discarded, crates/cli/tests/vault_oauth.rs:602-648), and refresh_errors_and_redirects_leave_the_grant_intact (a 307 to /leaked is never followed).

Secret storage at rest

  • Layout. One JSON catalog <root>/vaults/vaults.json written via temp file + fsync + rename, serialised by an flock on vaults.lock in a mode-0700 directory (crates/exoharness/src/vault/local/native.rs:35-59). Metadata is plaintext JSON; each secret payload is {algorithm, nonce, ciphertext}. On Cloudflare/wasm the same catalog lives in an object store behind an async mutex (crates/exoharness/src/vault/local.rs:84-102).
  • Cipher. AES-256-GCM, random 96-bit nonce (UUIDv4 prefix), key supplied by a SecretKeyProvider (crates/exoharness/src/secrets.rs:14-77).
  • Master key. Chosen by --secret-backend / EXO_SECRET_BACKEND: apple-keychain (macOS Keychain entry holds the 32-byte key only) or file (<root>/master.key or EXO_MASTER_KEY_PATH, created with a 0600 temp file and persist_noclobber) (crates/exoharness/src/secrets/native.rs:6-9, :54-89, :154-169; crates/cli/src/main.rs:409-416). Tests use Static.

Idea worth stealing: put the authorization policy in the AEAD's associated data

Because the AAD is (vault_id, metadata) and metadata includes name, id, revision and policy, an attacker with write access to the JSON file (but not the master key) can neither widen a secret's destinations, move a ciphertext between vaults, nor roll back to an older revision's metadata. Policy and secret are one tamper-evident unit. This is how the "where may this be sent" rule gets the same protection as the secret itself.

How model credentials flow

An agent definition names a credential, never a key: model.credential: openai. Resolution is the same find_secret walk over the thread's vaults; if absent it is a hard error, "Missing model credentials fail instead of falling back to host API keys" (crates/executor/src/harness_helpers.rs:198-210). From there the path depends on where the model client runs.

MCP and Git credentials

  • Host-side MCP clients (Basic, RLM, Pi): exo_mcp wraps the rmcp streamable-HTTP transport in CredentialClient so every request calls McpCredentialProvider::resolve, and one retry is made after a 401 using refresh (crates/mcp/src/auth.rs:40-88, crates/mcp/src/client.rs:113-136). The vault-backed provider compares a vault:secret:revision version string with the rejected one so a concurrent refresh by another caller is reused rather than repeated (crates/managed-agents/src/vaults.rs:220-266). Failure messages name the server, secret IDs and selected vaults, never the token (crates/managed-agents/src/vaults.rs:177-204).
  • Native MCP clients inside the sandbox (Codex, Claude Code): each authenticated server gets an env var EXO_MCP_<secret-id> (crates/executor/src/mcp_types.rs:18-20) holding a placeholder, and a binding whose destination is the exact MCP URL including path and query (crates/executor/src/sandbox_policy.rs:188-242). It is the same proxy path as model keys, including 401 refresh. See Tools & MCP.
  • Git over HTTPS uses Authorization: Basic; the proxy decodes user:placeholder, substitutes, re-encodes. The resolver sees method and path and may restrict to the four smart-HTTP endpoints (info/refs for upload/receive-pack, and the two POSTs); the Git test resolver does exactly that and an unlisted repo path gives 502 (crates/exoharness/src/egress/tests.rs:624-708). Authorization of which repository is the resolver's job, not Exo's.

Hosted variants: sessions and CONNECT servers

Two APIs let a hosted runtime reuse the same substitution rules without the native listeners:

  • EgressSession (crates/exoharness/src/egress_credentials/session.rs:13-102) persists {identity, policy, placeholder env} to storage at sandbox/<id>/egress.json. On re-configure it keeps the placeholder for any binding that is unchanged, so running processes keep working. rewrite re-authorizes against the network policy, rebuilds the bindings from stored placeholders, and returns the rewritten headers plus SHA-256 fingerprints (not values) of the substituted credentials and a refreshed flag. A caller that sees a 401 passes the fingerprints back as rejected, and the vault only refreshes if the current value still hashes to that fingerprint (crates/exoharness/src/egress_credentials/vault.rs:5-16).
  • serve_connect_proxy / ProxyAuthorizer / ProxySession (crates/exoharness/src/egress/explicit.rs:9-75): a shared listener where each CONNECT is authenticated with Basic credentials and mapped to a sandbox session; None gives 407, an error or a 10 s timeout gives 503. The test hosted_proxy_selects_and_isolates_sessions_on_one_listener exercises it.
