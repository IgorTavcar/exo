Runtime internals

Managed agents & adapters

An Exo "managed agent" is a Markdown file whose YAML frontmatter plus body is parsed into one strict serde struct, stored as a versioned artifact on an ordinary exoharness agent, and served through a single route table. Adapters (today: only Slack) are long-lived clients of that same API that turn chat events into durable inbox records, threads and turns.

Overview and crate map

Everything in this page hangs off one idea: a managed agent is data (AgentDefinition) stored next to an agent record, and every runtime behavior (harness choice, MCP servers, permissions, adapters) is re-derived from that data. There is no separate "managed agent" table, no content hash and no version number of its own; the exoharness artifact store provides the history.

The agent-definition schema

The file must begin with ---\n, contain a closing --- line, and have a non-empty body. The BOM and CRLF are normalized first (crates/managed-agents/src/lib.rs:70-95). The body, trimmed, becomes instructions; a literal --- inside the body is fine because only the first closing delimiter ends the frontmatter (the test at crates/managed-agents/src/tests.rs:181-195 parses a body containing ---).

The struct is generic over the resource type R because of a serde limitation called out in a comment: flattened tagged enums lose their leaf paths in error messages, so the parser first deserializes a literal ResourceInput and then builds the real ResourceDefinition (crates/managed-agents/src/frontmatter.rs:78-125).

From Markdown to a validated definition

  1. Split. AgentDefinition::parse strips BOM and CRLF, requires a leading ---\n, finds the first line equal to ---, and keeps the original text in a OnceLock<String> (crates/managed-agents/src/lib.rs:70-95).
  2. Deserialize with locations. frontmatter::parse runs serde_path_to_error over serde_yaml_ng; on failure it builds a Diagnostic with the field path, line:column and a source excerpt with a caret (crates/managed-agents/src/frontmatter.rs:127-222). A test pins the output: agent.md:4:9: invalid agent frontmatter at model.name (crates/managed-agents/src/tests.rs:399-412).
  3. Validate. validate() checks non-empty harness/model.name/instructions, MCP names and URLs, resources, and adapters (crates/managed-agents/src/lib.rs:97-111). The same validate() runs on every JSON path, including the HTTP create (crates/executor/src/managed_agents/service.rs:438) and update (crates/executor/src/managed_agents/service.rs:540).
  4. Serialize. to_json() emits a flat object (#[serde(skip)] on source and path), so the stored artifact and the HTTP bodies carry no frontmatter wrapper (crates/managed-agents/src/lib.rs:63-66, crates/managed-agents/src/tests.rs:425-449). source() returns the original Markdown if it was parsed from one, otherwise regenerates it from the struct (crates/managed-agents/src/lib.rs:151-156); regenerated YAML loses comments and ordering.

Strictness is the compatibility policy

Every layer carries deny_unknown_fields: the frontmatter, AgentModelConfig, PermissionPolicy (even {type: always_allow, ask: true} fails, crates/managed-agents/src/permissions.rs:98-104), MCP entries (an embedded token: or url: on a provider server fails, crates/managed-agents/src/tests.rs:111-125), and the stored JSON. The docs state the reason: a typo or an unimplemented feature must not silently change how the agent runs (exoharness/docs/managed-agents.md:19-21).

A leftover shim: two stored shapes are accepted

from_json deserializes an untagged enum of Flat(AgentDefinition) or Nested { frontmatter, instructions } (crates/managed-agents/src/lib.rs:113-132), and a test asserts that old nested artifacts are read and re-exported flat (crates/managed-agents/src/tests.rs:451-464). The website docs say there is no frontmatter wrapper at all (website/docs-src/agent-definition.md:41-43); that is true of what is written, not of what is read. This reads as support for artifacts saved before the flattening commit.

Stored agent, identity and versions

There is no content-hash identity. A managed agent is an ordinary exoharness agent (UUIDv7 id, unique slug, display name) with one agent-scoped artifact at a fixed path:

Creation and update are both "write an artifact, then run backend configuration, then compensate on failure":

  • Create (crates/managed-agents/src/lib.rs:163-196): new_agent with the slug/name, then configure_agent and write_artifact; if either fails the half-made agent is deleted again.
  • Update (crates/executor/src/harness_executor.rs:1042-1087): remember the previous definition, write the new artifact, call provider.configure_agent; on failure, write the previous definition back as a new artifact version (or empty bytes if there was none) rather than deleting history. This is why an empty latest artifact means "no definition" (crates/managed-agents/src/lib.rs:281-283).
  • Upsert from the CLI (crates/cli/src/managed_agents.rs:193-222): exo run FILE.md resolves a slug, then update_managed_agent if the agent exists, else create_managed_agent. A string is treated as a file if it ends in .md or has more than one path component (crates/cli/src/managed_agents.rs:96-101); everything else is a saved-agent name or ID.

Idea worth stealing: rollback by appending, not deleting

Because the definition is just the latest artifact version, a failed update restores the old one as a new version, and a failed first upload is neutralized by an empty artifact. The artifact history stays append-only, and "current" is always max_by_key(version). The adapter supervisor reuses the same pair (artifact_id, version) as a cache key (crates/executor/src/managed_agents/adapters/definitions.rs:21-50), so reloading is a single list call, not a parse, in the steady state.

"Identity" in this crate means a person, not an agent

crates/managed-agents/src/identity.rs defines IdentityRecord {id, email, vault}, SlackIdentityPin and IdentityCommand::{BindVault, BindSlack, UnbindSlack, TrustSlack}: the mapping from a human (email, Slack workspace+user) to a private vault. It is exposed at POST /exo/identity/manage (crates/executor/src/native/http_service.rs:192) and consumed by adapters; see below. The agent itself is identified only by its random id and slug.

Turning the definition into runtime config

impl AgentBackend for LocalProvider (crates/executor/src/managed_agents.rs:32-247) is where the definition meets the executor. Three hooks matter:

configure_agent: operator gate, then AgentConfig

When the provider has a caller (authenticated server, adapters), any definition that is not a plain stock configuration requires the operator permission: a harness outside basic | rlm | codex | claude-code | cursor | cursor-sdk | pi, or non-empty tools, or tool_creation, or any adapters (crates/executor/src/managed_agents.rs:43-52). Rationale is visible in what those fields mean: they load arbitrary TypeScript or open outbound chat connections on the host. The adapter caller's policy always refuses check_operator (crates/executor/src/managed_agents/adapters/access.rs:107-109). The config itself comes from agent_config_with_modules (crates/executor/src/managed_agents/config.rs:275-360); resources are resolved relative to the agent file's directory and relative paths require a local file (crates/executor/src/managed_agents.rs:60-72).

configure_thread

Runs on every open/resume (crates/managed-agents/src/lib.rs:355-399 calls it, deleting a just-created thread if it fails). It merges, in order: the agent config, a per-thread model override (--model), harness override (resolved with the operator check at crates/executor/src/managed_agents/config.rs:207-213), environment (which fixes sandbox provider and image, crates/executor/src/managed_agents.rs:151-180), resource mount-overlap validation, and finally configure_managed_thread on the executor, which connects MCP servers and returns the tool count the CLI prints (crates/executor/src/managed_agents.rs:200-203).

Per-turn refresh of permissions

For saved agents, thread_config.permissions = definition.permissions() is re-read from the stored definition on every turn that is not a recovery (crates/executor/src/harness_executor.rs:689-692), and again in configure_thread (crates/executor/src/managed_agents.rs:132-134). Editing a policy therefore applies to existing threads on their next turn, which the docs state at exoharness/docs/managed-agents.md:338-341.

The hosted-agent HTTP API

All routes live under RUNTIME_PATH = "/exo" (crates/managed-agents/src/http.rs:9). One function, route(), matches on (method, path-segments) and is shared by the native Actix server and hosted workers; each host implements the small Platform trait (account id, streaming on/off, previews, cancel, frontend-tool results) (crates/executor/src/managed_agents/http.rs:11-47, crates/executor/src/managed_agents/http.rs:105-306). A path that matches under a different method yields 405 via the routes! macro (crates/executor/src/managed_agents/http.rs:119-136).

Is it Anthropic- or OpenAI-compatible? No.

It is Exo's own REST+SSE protocol. A search of the managed-agents crate and the docs finds no claim of compatibility with either vendor's agent or Responses API (the only "Anthropic" hit in the docs is a vault secret for Claude Code). What is shared is vocabulary: permission_policy: {type: always_allow | always_ask}, MCP entries with type: url, allowed_tools, and an event-stream/session model. Treat that as resemblance, not emulation. The one place a hosted-agent product is named is an unexplained "CMA" in the planned list (website/docs-src/agent-definition.md:536).

Semantics worth knowing

  • The protocol is a superset of what local supports. SubmitTurnBody carries parent, endpoint_name, reasoning_effort, auto_approve_tools, page_scope, reset_history and delivery_callback; prepare_turn rejects all of them with UnsupportedRequest (HTTP 501) on the local runtime (crates/executor/src/managed_agents/service.rs:95-107). Same for CreateThreadBody's thread_id, visibility and source (crates/executor/src/managed_agents/service.rs:45-54). The shapes are shared with a hosted runtime that does honor them.
  • Error mapping. A typed RequestError carries its status; UnsupportedRequest is 501; any other error is 400, not 500 (crates/executor/src/managed_agents/service.rs:170-178).
  • Flat turn options. SubmitTurnBody flattens TurnOptions (attention: wake|interrupt|..., idempotency_key); a test pins this wire shape (crates/managed-agents/src/http/protocol.rs:253-267). The idempotency key is what makes a retried POST return the same turn.
  • Live chunks are not durable. forward_progress republishes model chunks and status messages on a broadcast channel as synthetic Events; watch_events subscribes before loading durable history and selects the two streams. Lagged receivers silently skip chunks (crates/executor/src/managed_agents/service.rs:767-844, with a test at crates/executor/src/managed_agents/service.rs:851-889).
  • Single-agent scoping. exo run FILE --serve builds Service {agent_id: Some(id)}; every agent() lookup for another id is 404 and mutations that are global are 403 (crates/executor/src/managed_agents/service.rs:180-202).
  • Doctor is client-only here. RuntimeClient::diagnose_agent calls agent/{id}/doctor and turns a 404 into an empty list (crates/managed-agents/src/http/client.rs:155-178); the shared route table has no such route.

Permissions and approvals

Two policy values only: always_allow and always_ask (crates/managed-agents/src/permissions.rs:5-16). The interesting part is the resolution order, which differs for built-in and MCP tools:

Tool kindLookup orderFinal default
Built-in / registered tooltop-level tool_policies[name]top-level permission_policy (default always_allow)
MCP tooltop-level tool_policies[exposed_name], then mcp_servers[s].tool_policies[original_name], then mcp_servers[s].permission_policyalways_ask; the agent-level default does not apply (test at crates/managed-agents/src/permissions.rs:136-153)

The MCP wrapper chooses between the two at call time: McpToolRuntime::permission_policy looks up the tool in its connected tool set and delegates to for_mcp_tool only if found (crates/executor/src/mcp.rs:41-50).

Approval flow is event-sourced

permissions::authorize (crates/executor/src/permissions.rs:124-286) never holds state in memory:

  1. If the policy is always_allow and this is not an approval resume, return.
  2. Otherwise scan the turn's events for an existing agent_runtime.approval_requested matching the same tool_call_id and round; require the saved request to equal the new one (crates/executor/src/permissions.rs:150-166).
  3. If an approval_response exists: approved means continue, denied means the tool call errors "tool call denied by the user" (crates/executor/src/permissions.rs:187-197).
  4. With no existing request, check session-wide allowances: any approved response in this session whose allowed_tool_name equals the function name auto-approves (crates/executor/src/permissions.rs:198-222).
  5. Else append approval_requested (id = fresh UUIDv7), emit ExecutionStreamEvent::ApprovalRequested to any live observer, and watch_events from that event until a matching response or TurnEnded (crates/executor/src/permissions.rs:223-285).

A client answers with POST .../approval-response {session_id, approval_id, approved, allow_for_tool}; respond() checks that the approval is actually pending for that turn and session, rejects "denied but allow for tool", and writes an approval_response event (crates/executor/src/permissions.rs:94-122). Because the pending set is recomputed from events (pending_from_events, crates/executor/src/permissions.rs:69-92), a restarted server resumes waiting turns correctly for harnesses that support it; ManagedExecutor advertises resume only for Basic (crates/executor/src/native/managed_executor.rs:132-134).

Downgrading a policy does not revoke an allowance

"Allow for tool" is stored as an allowed_tool_name on a response event and honored for the rest of that session. Per-turn policy refresh applies the new definition, but a session-wide allowance already granted still short-circuits always_ask; the docs admit this (exoharness/docs/managed-agents.md:346-348).

Per-harness enforcement caveats (Codex and Cursor reject native always_ask they cannot enforce; Claude Code uses a native PreToolUse hook; custom harnesses must call context.authorizeTool) are in exoharness/docs/managed-agents.md:350-361 and belong to Native harnesses. The hosted Worker is stricter still: Codex there requires always_allow and empty tool_policies (crates/worker-runtime/src/execution.rs:63-69).

Adapters

An adapter is not a harness feature and not a tool. It is a supervised client of the managed-agent API that lives in the server process: it owns the external connection and delivery, while the provider owns threads, sandboxes, vault selection and execution. A harness never sends a Slack message; replies are delivered from the event stream (docs/managed-adapters.md:8-14).

AdapterService: a reconcile loop plus a work loop

  • Started by the server. exo run ... --serve constructs it, hands a reference to the HTTP service for webhooks, and runs it beside the Actix server (crates/cli/src/serve.rs:82-91, crates/cli/src/serve.rs:127-129). --adapters-only runs supervision without HTTP but refuses HTTP-transport Slack adapters (crates/cli/src/serve.rs:91-95).
  • Desired state is polled. Every 2s reconcile() lists all agents, loads each definition through the version-keyed DefinitionCache, and diffs against running Deployments (crates/executor/src/managed_agents/adapters/mod.rs:304-376, crates/executor/src/managed_agents/adapters/mod.rs:377-413). A definition that fails to load keeps already-running deployments alive instead of tearing them down (crates/executor/src/managed_agents/adapters/mod.rs:342-361). The docs list the polling as an open performance item (docs/managed-adapters.md:422-435).
  • Deployment id = sha256("{agent_id}/{adapter_name}") (crates/executor/src/managed_agents/adapters/store.rs:316-318). Renaming an adapter is therefore a new deployment with new routes; removing one shuts the connection and keeps threads.
  • Fingerprint. A deployment restarts when digest((definition, [(secret_id, revision)...])) changes (crates/executor/src/managed_agents/adapters/mod.rs:440-453), so rotating a bot token in the vault reconnects without touching the agent file. Credentials are read from the adapter's own vault with the owner's authority, never from thread vaults, and the global vault is forbidden (crates/executor/src/managed_agents/adapters/mod.rs:428-434, crates/managed-agents/src/adapters.rs:86-89).
  • Everything durable. Inbox, outbox, routes, decisions and caller authorities are JSON objects in provider storage under adapters/v1/{deployment}/... (crates/executor/src/managed_agents/adapters/store.rs:316-333). A cached pending-set index avoids rescanning history and is invalidated by a WriteGuard if a write is cancelled mid-flight (crates/executor/src/managed_agents/adapters/store.rs:170-247).

Admission filters, in order (crates/executor/src/managed_agents/adapters/slack.rs:196-356): ignore bot messages, subtypes, hidden and edited events; ignore the bot's own user; apply allowed_users; call conversations.info to learn is_ext_shared (fail closed if absent); drop Slack Connect unless allow_slack_connect and the channel is listed; apply direct_messages / allowed_channels; in mentions_only mode require an @mention or an already-tracked route (so follow-ups in a thread the bot joined need no new mention).

Then submit() maps the route to a thread and starts the turn:

  • Thread identity is a slug, not a lock. Two racing first messages cannot create two threads because the thread slug is slack-{sha256(route_key)} and lookup is by slug; a per-route in-process Weak<Mutex> serializes the rest (crates/executor/src/managed_agents/adapters/mod.rs:237-246, crates/executor/src/managed_agents/adapters/mod.rs:670-717). The route key is sha256(account/conversation) (crates/executor/src/managed_agents/adapters/store.rs:322-327); account is team_id/bot_user_id, so replacing the bot account starts new namespaces.
  • The input is plain text with a speaker tag ([slack user U123]). The model sees who spoke; no structured Slack metadata is passed.
  • Each message is its own session (session_id = inbox.accepted, a UUIDv7). That has a consequence for approvals: Slack always sends allow_for_tool: false (crates/executor/src/managed_agents/adapters/mod.rs:1378-1383), and "allow for session" would be scoped to that single message anyway.
  • Exactly-once admission comes from the idempotency key adapter:{deployment}/{message id} plus retain_receipt; on restart submit sees inbox.turn and calls watch_turn(thread, turn, inbox.cursor) to resume streaming instead of resubmitting (crates/executor/src/managed_agents/adapters/mod.rs:759-768).
  • Per-sender isolation without per-sender threads. The vaults for a turn come from the caller's Runtime (see below), not from the thread. turn_vaults are attached to the thread (shared) but a sender's private vault never is (crates/executor/src/managed_agents/adapters/mod.rs:739-758; policy comment at docs/managed-adapters.md:217-218).

Output: streaming, receipts, retry

drain_stream polls the turn's ExecutionStream (up to 4096 events without awaiting, via now_or_never), feeds each event through Progress::event to produce SlackStreamChunks (text deltas in 4000-char chunks, task cards for tool calls, "Waiting for your approval", "Paused", "Responding"), and writes the chunks and the new observer cursor into one Outbox::Stream object as a StreamReceipt (crates/executor/src/managed_agents/adapters/mod.rs:810-901, crates/executor/src/managed_agents/adapters/progress.rs:22-83). If saving the inbox fails afterwards, restore_receipt reads the cursor back from the outbox (crates/executor/src/managed_agents/adapters/mod.rs:637-656), which is what stops a restart from replaying or double-posting. Delivery (deliver_one) uses Slack's native streaming API (chat.startStream / appendStream / stopStream), marks a delivery permanently failed on invalid_thread_ts | thread_not_found | message_not_found, honors Retry-After, and otherwise backs off 2^attempts seconds capped at 2^8 (crates/executor/src/managed_agents/adapters/mod.rs:1161-1260, crates/executor/src/managed_agents/adapters/slack.rs:437-561).

Error handling for the observer: transient errors schedule a reconnect with delay min(2^attempts, 60) s; a serde_json error five times in a row (INVALID_PROGRESS_RETRY_LIMIT) stops delivery with "Updates unavailable" but leaves the turn intact (crates/executor/src/managed_agents/adapters/mod.rs:29, crates/executor/src/managed_agents/adapters/mod.rs:930-975); a failed turn posts "Turn failed: ..." instead of a fabricated answer (crates/executor/src/managed_agents/adapters/mod.rs:903-928).

Approvals through Slack

An ApprovalRequested stream event becomes an Outbox::Approval with Approve/Deny buttons whose action_ids are exo_approve / exo_deny and whose value is the outbox id (crates/executor/src/managed_agents/adapters/slack.rs:529-551). A click arrives as a BlockActions interaction, and accept_decision enforces: the message belongs to this account and channel and matches the stored Slack message ts; only the sender of the message that started the turn may answer; the identity grant (if any) is still valid; the decision is idempotent and cannot flip (crates/executor/src/managed_agents/adapters/mod.rs:1261-1327). The decision is persisted as a Decision record and applied later by apply_decision through the same respond_to_pending_approval an HTTP client uses (crates/executor/src/managed_agents/adapters/mod.rs:1356-1405). Typing "yes" in chat is never treated as approval.

Authority, access policy and sender vaults

Each unique (deployment, agent, thread, adapter, sender context, identity grant) is an Authority; its JSON hash is the caller principal adapter-{sha256} (crates/executor/src/managed_agents/adapters/access.rs:172-177). AdapterService::caller_runtime builds and caches (5-minute idle prune) a Runtime whose exoharness handle is wrapped in an AdapterPolicy (crates/executor/src/managed_agents/adapters/mod.rs:152-215). That policy is re-evaluated on every access check against the current stored definition:

  • sender still in allowed_users; external (Slack Connect) senders only if allow_slack_connect and the channel is explicitly listed; DM vs channel rules (crates/executor/src/managed_agents/adapters/access.rs:62-82);
  • resources are limited to this agent (and, for thread scope, this thread) (crates/executor/src/managed_agents/adapters/access.rs:94-104); operator operations and vault creation are refused (crates/executor/src/managed_agents/adapters/access.rs:107-111, crates/executor/src/managed_agents/adapters/access.rs:158-160);
  • vault visibility: the global vault; the sender's personal vault, renamed to personal in what the thread sees; and only those turn_vaults named on this adapter, never the adapter's own transport vault (crates/executor/src/managed_agents/adapters/access.rs:113-157); default_vault is the sender's vault if granted, else global (crates/executor/src/managed_agents/adapters/access.rs:161-169).

The sender's private vault comes from an IdentityGrant resolved only when use_sender_vault: true. resolve_slack prefers an explicit (workspace, user) pin; otherwise it requires the workspace to be explicitly trusted and an exact, unique, case-insensitive email match against known principals; grants carry a revision hash of (principal, pin, trusted) so any change invalidates queued work with IdentityAccessChanged (crates/executor/src/native/remote/identity.rs:206-297). Queued input whose access was removed completes with "Access removed" rather than running under another context (crates/executor/src/managed_agents/adapters/mod.rs:603-612).

Idea worth stealing: authority-as-principal

Instead of threading a sender through a shared runtime, the adapter mints a caller whose principal is a hash of everything that determines its authority, persists that authority, and installs a policy object that re-checks it against live config on every access. Revocation is then just a config change: the next check fails, and in-flight records complete with AccessRemoved. Recovery after restart is recover_caller(principal) reading the stored authority back (crates/executor/src/managed_agents/adapters/mod.rs:144-151).

MCP failures are tolerated only for adapter callers

connect_mcp picks connect_available_with_connector (skip servers that cannot authenticate) when the thread's caller principal starts with "adapter-", otherwise connect_with_connector (fail the thread) (crates/executor/src/managed_mcp.rs:36-49). A string-prefix check carries a real behavioral difference: a Slack user without a personal Notion token still gets an agent, minus the Notion tools.

Webhooks

For transport: http the webhook is built in, never configured: POST /exo/adapter/{name} on a single-agent server or POST /exo/agent/{agent}/adapter/{name} (crates/executor/src/managed_agents/adapters/mod.rs:115-136). slack_webhook verifies the Slack signature with the vault's signing-secret, answers url_verification challenges, and dispatches form-encoded interactions or JSON events to the same code as Socket Mode (crates/executor/src/managed_agents/adapters/mod.rs:1448-1539). If the secret is not yet in the vault the endpoint answers only the URL challenge, which lets you register the URL before creating the app. A signature error is 401; a payload parse error is 400; anything else is 503 so Slack retries (crates/executor/src/native/http_service.rs:232-241).

Managed executor vs the native executor

"Native" is the Rust-side machinery (BasicExecutor, RlmExecutor, TypeScriptExecutor); ManagedExecutor is the HarnessExecutor that the local provider installs (crates/executor/src/native/constructors.rs:60-70). It does not run turns itself. It is a per-thread factory and cache:

  1. Connect MCP first. On first use for a thread, connect_mcp loads the saved definition, resolves mcp_servers (it always passes the no-op resolver (), so type: provider entries fail here with "this provider does not supply a built-in MCP server"; a host that supplies a resolver must call resolve_mcp_servers itself), computes or loads the thread's VaultSelection, and connects (crates/executor/src/managed_mcp.rs:14-60).
  2. Validate the thread. Non-local sandboxes may not mount host secret paths; with LocalProcess sandboxes, vault-backed MCP credentials or multiple vaults are refused because the process could read host credentials (crates/executor/src/native/managed_executor.rs:279-306).
  3. Pick the executor from AgentHarnessKind: Basic to BasicExecutor, Rlm to RlmExecutor, TypeScript to TypeScriptExecutor (Codex/Claude Code/Pi are TypeScript modules), Exo to TypeScriptExecutor with ExoToolRuntime (crates/executor/src/native/managed_executor.rs:73-102). Each gets McpToolRuntime wrapped around its tool runtime so MCP tools and their approval policies appear uniformly.
  4. Guard drift. Every call revalidates that the resolved MCP server list still equals the connected one, otherwise "MCP configuration changed; start a new thread" (crates/executor/src/managed_mcp.rs:63-73). A thread's vault selection is saved as an artifact and cannot be changed (crates/managed-agents/src/vaults.rs:123-138).
  5. Record the tool inventory. configure_thread appends an mcp_tools custom event whenever the inventory differs from the last one, so the thread log shows which tools the model could see (crates/executor/src/managed_mcp.rs:75-107).

Capabilities are declared per harness kind: resume pending approval only for Basic; suspend a turn for Basic and TypeScript; reconcile an unresolved tool call only for TypeScript (crates/executor/src/native/managed_executor.rs:132-145). The hosted counterpart WorkerExecutor shares the same ExecutorCache and PreparedMcp but its worker_agent_config refuses anything beyond basic/codex, custom tools, adapters, tool creation and Braintrust, and requires model.credential (crates/worker-runtime/src/execution.rs:45-80).

Idea worth stealing: bind credentials to MCP destinations, pin them per thread

VaultSelection::from_vaults maps each MCP server to a secret by asking whether the secret's destination policy permits the server URL, preferring an exact destination match, scanning attached vaults from last to first (later vaults override earlier ones), and erroring if two secrets in one vault tie. The result is saved on the thread; if the server URL later changes, validation fails instead of sending a credential somewhere new (crates/managed-agents/src/vaults.rs:49-111). See Egress & vaults for the proxy side.

CLI and examples

  • exo run FILE.md upserts then opens a thread; exo agent create requires a new slug, exo agent update an existing one, and get/doctor inspect (crates/cli/src/main.rs:611-640). Slugs come from slugify(name) unless --slug is given (crates/cli/src/managed_agents.rs:53); new thread slugs are 1 to 128 chars of ASCII alphanumerics, - and _, and a UUID-shaped unknown reference is "not found" rather than a new thread name (crates/cli/src/managed_agents.rs:16-31).
  • check_model_credentials pre-flights model.credential: found in a thread vault, has a destination policy, and the policy permits the model endpoint, else it prints the exact exo vault secret update ... --allow-origin fix (crates/cli/src/managed_agents.rs:329-383).
