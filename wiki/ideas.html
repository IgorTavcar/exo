Distilled

Ideas worth stealing

The design and engineering techniques in Exo that transfer to other systems, grouped by theme. Each one names the code that implements it and the wiki page with the full context.

These were picked while reading every subsystem: they are the places where the code solves a problem in a way that is not the obvious one. Most come down to one habit. Treat the append-only event log as the only source of truth, and make every other piece of state either derivable from it or a disposable cache. The sections below start with what that habit buys (recovery), then the log's own design, then security, portability, and finally agent and prompt techniques.

Durability and recovery

Commit the recovery payload with the turn-start event

start_local_turn serializes a TurnWork (resolved agent config, thread config, request, streaming flag) and passes it as initial_events to begin_turn. It lands in the same write as TurnStarted and the user input. Recovery needs no side table: scan for started-but-not-ended turns, parse the work back out of the log, call resume_turn.

crates/executor/src/harness_executor.rs:44-72 · crates/executor/src/harness_executor.rs:745-762 · crates/exoharness/src/types.rs:397-406 · harnesses · data model

Completion marker committed with the final answer

The last model response and exo.runtime.turn_completed go into one add_events call. If the process dies between "answer written" and "turn ended", the queue sees the marker and only writes TurnEnded; the model is not called again.

crates/executor/src/basic.rs:197-205 · crates/executor/src/harness_executor.rs:824-854 · crates/executor/src/turn_queue.rs:731-742

Turn status is a pure function of events; the queue holds only scheduling state

journal_status_from_events yields Unstarted / Running / Finished from TurnStarted, TurnEnded and Error. The queue stores order, control (Run / Cancel / Suspend) and idempotency receipts, nothing about progress. A crashed, suspended or cancelled turn is classified identically at runtime and at startup recovery, and when the two disagree the journal wins.

crates/executor/src/turn_queue.rs:843-892 · crates/executor/src/turn_queue.rs:706-812 · crates/exoharness/src/turn_coordinator/stored.rs:13-27

A round marker so recovery never re-samples the model

BasicExecutor writes exo.basic.tool_round before a round's tool_requested events. On recovery load_turn_progress rebuilds the saved round and finishes its tools instead of calling the model again, because a second sample "could produce a different set of tool calls".

Write-ahead intent around a non-idempotent RPC

The Codex harness appends codex_turn_start_intent before calling turn/start and codex_turn_started (with the native turn id) after. An intent with no start means the outcome is unknowable, so recovery fails the turn rather than risk executing it twice.

Idempotent projection with per-item markers

Every native Codex item projected into Exo events is followed by a codex_item_projected marker keyed turnId:itemId. Recovery pages backwards through only the unfinished turn, collects the markers, and re-projects just what is missing from a thread/read snapshot.

Suspend only at a tool-quiescent boundary

HarnessTurn tracks in-flight tool_call_ids from acknowledged events. suspension_boundary() returns a mutex guard only when none are pending, and the caller drops the execution future while holding it. No new tool_requested can be journaled in between, so a suspend can never lose a tool request.

Executors declare can_resume_pending_approval, can_suspend_turn and can_reconcile_unresolved_tool_call; the default resume_turn bails. restore_recovery_tools replays the tool and approval events and permits resume only when the unresolved call is parked at an approval or is a client tool. A live Codex turn waiting on an approval holds the request on a connection that no longer exists. assertNativeToolSafety fails recovery if any commandExecution, mcpToolCall, dynamicToolCall, webSearch or fileChange item is still in progress, so recovery fails fast instead of hanging.

Event-log design

One id as cursor, clock and filename

EventId is a UUIDv7. Event.created_at is derived from id.timestamp(), every cursor and watch bound is an event id, and event objects are named by id, so a directory listing is already a sorted log. Thread "recency" is latest_event_id.unwrap_or(thread.id).

crates/exoharness/src/uuid7.rs:8-22 · crates/exoharness/src/basic.rs:2475 · crates/exoharness/src/basic.rs:1375-1377

Atomic multi-event commit is one object PUT with a self-describing name

A multi-event append is a single <first>_<last>.batch.json object. The id range in the name lets get_event, pagination and watch prune without a separate index, and there is no transaction layer over the dumb key-value store.

crates/exoharness/src/basic.rs:2482-2497 · crates/exoharness/src/basic.rs:158-162 · crates/exoharness/src/basic.rs:85-156

Derive the head from the log; record.json is a commit marker

load_conversation_record overwrites latest_event_id with the max id parsed from the events/ keys ("the event log is authoritative if a crash preceded the metadata write"). Appends never rewrite record.json, and a thread exists once record.json is written, which happens last.

crates/exoharness/src/basic.rs:2820-2832 · crates/exoharness/src/basic.rs:2846 · crates/exoharness/src/basic_tests.rs:1163-1165

Subscribe before you list: gapless replay-then-live

watch_events creates its broadcast(64) subscription first, then lists stored batches after the bound. A lagged observer resubscribes and rescans storage from its last emitted key. Fast consumers cost zero storage reads, and a test pins that.

crates/exoharness/src/basic.rs:1833-1932 · crates/exoharness/src/basic_tests.rs:39-110

Durable plus ephemeral stream, with checkpoints

The SSE watch is select(durable watch_events, in-memory progress broadcast). Text deltas and "Preparing workspace" statuses are minted with fresh UUIDv7s and never persisted. turn_stream emits a Checkpoint{event_id} after each durable event so a client knows where to resume with ?after=.

Credentials and network security

Put the destination policy inside the AEAD's associated data

Vault secrets are AES-256-GCM encrypted with AAD = (vault_id, SecretMetadata), and the metadata includes the destination policy. Editing vaults.json to widen a secret's allowed hosts, or moving a ciphertext to another vault, makes decryption fail. "Where may this be sent" is as tamper-evident as the secret itself.

crates/exoharness/src/vault/local.rs:262-270 · crates/exoharness/src/vault/local/tests.rs:287-305 · egress & vaults

Validate placeholders before resolving anything

validate_credentials strips every placeholder this destination may resolve and fails if any exo_egress_ text remains. A placeholder aimed at the wrong host is rejected with zero resolver calls and zero upstream connections.

crates/exoharness/src/egress_credentials.rs:126-162 · crates/exoharness/src/egress/tests.rs:795-815

Bind names to ids at attach time, resolve values at use time

Sandbox bindings are named by the secret's UUID. find_secret runs once at sandbox creation and the SecretReference is persisted. Rotation (same id, new revision) is live on the next request, deletion fails closed, and a new same-named secret in a higher-precedence vault cannot hijack a running sandbox.

crates/executor/src/sandbox_policy.rs:146-165 · crates/exoharness/src/basic/sandboxes.rs:1777-1790 · crates/exoharness/src/basic/egress.rs:9-46

Narrow a broad secret policy to the one destination a harness needs

CredentialPolicy::for_destination replaces a secret's multi-origin policy with exactly the model origin, Git origin or MCP URL for that sandbox binding, and errors if the secret does not allow it. A key that is allowed at three hosts is only injectable at one inside any given sandbox.

crates/exoharness/src/credential_policy.rs:114-121 · crates/executor/src/sandbox_policy.rs:53-242

A throwaway CA whose key is dropped

tls_configuration generates a CA per sandbox, signs exactly one leaf with SANs for the intercepted hosts, and returns only the CA certificate PEM and an acceptor. The CA private key never leaves the function. Trust is injected through env vars pointing at a copied bundle, not by editing the system store.

crates/exoharness/src/egress/mod.rs:555-584 · crates/exoharness/src/egress/mod.rs:823-830

In unrestricted mode, only MITM the credential hosts

The proxy peeks the TLS ClientHello SNI and tunnels unrelated HTTPS bytes untouched, so public TLS stays end-to-end and only the hosts that carry credentials are intercepted.

crates/exoharness/src/egress/mod.rs:656-717 · crates/exoharness/src/egress/tests.rs:1782-1867

DNS as policy

In limited mode the proxy's own DNS service returns NXDOMAIN for names that are not allowed. On Firecracker it also admits the resolved IPs into a per-VM nftables set (1 h timeout) before answering the guest, so a connection cannot race the firewall rule.

crates/exoharness/src/egress/transport.rs:394-462 · crates/exoharness/src/sandbox_provider/firecracker.rs:3592-3661

Refresh tokens rotate, so detach refresh from the caller

OAuth refresh runs on a spawned host task under a file lock, with a revision compare-and-swap when persisting. For chat callers, each (deployment, agent, thread, adapter, sender context, identity grant) is serialized and hashed into a principal adapter-{sha256}. The stored authority is re-checked against the live agent definition on every access, so revoking access is a config edit.

One request enum, three transports, one handler

protocol::Request is served by ExoHarnessServer::handle_request whether it arrives as POST /request, as an exo_request JSONL line from a TypeScript harness, or inside wasm. Warm process reuse recorded in the event log

startSandboxProcess({reuseKey}) appends a typescript_sandbox_process_reuse event. A new runner, even after a restart, finds the newest generation for that key, re-attaches at the cursor of its last output event and never resurrects an older generation. Agent design and prompting

Prompt text is collected on its own page; the transferable techniques are these.

Recompute instructions every round instead of storing them

Instructions are prepended to the replayed history on each model call, and the harness instructions hook is async. The prompt can carry the current game screenshot, todo list, memory block or skill index without any of it accumulating in the log. The Game Boy harness uses this: tools return only text, and a fresh screenshot plus RAM state is injected each round, so stale frames never pile up.

exoharness/typescript/harness/index.ts:754-762 · exoharness/typescript/model-runtime/turn-loop.ts:150-155 · exoharness/examples/gameboy-agent/agent/harness.ts:82-104

Context as a variable (recursive language model)

The root prompt holds only the latest request, the transcript length and a 400-character preview. The model reads the flattened transcript with code in a JS REPL and recurses via a tool-less subquery. It finishes by setting globalThis.Final. Everything is logged as rlm_* custom events.

Pick the failure mode per store by regenerability

Memory (not regenerable) throws on write when corrupt but degrades its read path to a "memory unavailable, do not assume it is empty" developer message so prompt assembly never bricks. Todos (regenerable) silently reset. Skills publish content before the index entry for the same reason.

Sandboxes and isolation

Traits that bail by default, plus a declared restore set

ManagedSandboxHandle and ManagedSandboxBackend make only the core mandatory. Managed processes, terminals, TCP, fork and snapshot deletion all default to bail!("... does not support ...") or Ok(None). Restore compatibility is a declared list (consumable_snapshot_formats) that the harness checks before dispatch, so producers and consumers never need to know about each other. SandboxProvider and SnapshotFormat are open-string newtypes, so a third party can add a backend or a private format without touching a core enum.

Shared immutable lower layer, sparse per-VM upper

One digest-cached read-only ext4 image is hard-linked into every Firecracker jail. Each VM only gets a lazily formatted sparse ext4 that serves as the OverlayFS upper, and the guest moves the merged mount over /. No base-image copy at boot.
