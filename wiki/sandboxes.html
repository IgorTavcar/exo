Runtime internals

Sandboxes

A sandbox is a named, restartable execution environment that the harness owns and a provider implements. This page covers the two provider traits, what each of the ten backends actually does, the lifecycle and idle-TTL rules, the process model, mounts and resources, snapshots, and the Firecracker stack end to end (OCI image to ext4, jailer, vsock guest agent, Lima on macOS).

Overview: who owns what

Three layers, each with a narrow job. The executor decides what sandbox a thread should have (image, provider, mounts, policy, ports, idle seconds). The harness (BasicExoHarness) persists a StoredSandbox record per sandbox, keeps a per-process map of live handles, and records lifecycle in the thread's event log. A provider implements ManagedSandboxBackend (factory) and ManagedSandboxHandle (one live sandbox). The harness never inspects provider internals; it only stores an opaque provider_state JSON blob and hands it back on the next acquire.

The identity of a sandbox is sandbox_id; the identity of a configuration is sandbox_spec_hash(&SandboxSpec), a DefaultHasher hash of image, resources, mounts, durable filesystems, egress policy, workdir and TCP ports crates/exoharness/src/sandbox.rs:80-91 crates/exoharness/src/sandbox.rs:513-517. Every local backend keys its warm instance on (sandbox_id, spec_hash), so changing any spec field replaces the warm instance instead of mutating it. The executor mirrors this: ConversationSandboxInfo::matches_spec compares the same fields before reusing a recorded sandbox crates/executor/src/conversation_sandbox.rs:29-41.

The provider abstraction

Two async traits in crates/exoharness/src/sandbox.rs. The design rule is visible in the defaults: every optional capability has a default body that fails loudly (bail!("sandbox backend does not support ...")) or returns "unknown" (Ok(None), false), so a provider implements only what it can honestly do and callers probe via supports_tcp(), consumable_snapshot_formats() or by handling the error.

The factory trait crates/exoharness/src/sandbox.rs:350-507 has six required methods (is_local, consumable_snapshot_formats, acquire, attach, acquire_from_snapshot, suspend) and optional ones for explicit terminate, fork_sandbox, materialize_resources, resolve_image, with_external_proxy, and reconnect/stop hooks for stateless remote IDs (resolve_existing, stop_existing, stop_requires_provider_state, invalidates_handle). Two contract sentences in the doc comments carry real weight: acquire must "enforce request.spec.policy before returning a usable handle. Attach, restore, and fork must provide the same guarantee or reject the policy", and terminate "must be idempotent".

Idea worth stealing: capability by default-bail plus a declared restore set

A backend declares exactly which snapshot formats it can consume (consumable_snapshot_formats), and the harness checks that before dispatch (ensure_snapshot_format_supported, which lists the supported formats in the error). Cloudflare is a different animal

The Cloudflare harness does not go through the Rust provider registry. ExoSandbox is a Durable Object wrapping a Cloudflare Container: acquire stores a SandboxConfig, picks the smallest of standard-2/3/4 that satisfies the requested SandboxResourceShape, and starts the container with entrypoint: ["sleep", "infinity"] and enableInternet: false; all HTTP/HTTPS is intercepted into ExoEgress exoharness/cloudflare/src/sandbox.ts:158-214 exoharness/cloudflare/src/sandbox.ts:286-321. Idle handling is an alarm: scheduleIdle sets a Durable Object alarm at idleMs and an inactivity timeout 60 s later; the alarm calls stop(), which closes processes, takes a snapshotContainer() checkpoint, and destroys the container. The next start restores from that snapshot. The SandboxActivity guard from the Rust trait maps onto beginActivity/endActivity leases that postpone the alarm exoharness/cloudflare/src/sandbox.ts:243-285 exoharness/cloudflare/src/sandbox.ts:445-469.

Idle TTL, and the "honor sandbox idle TTL" change

The TTL is a single optional duration, SandboxLifecycleConfig::idle_ttl crates/exoharness/src/sandbox.rs:25-28. Its path: the executor chooses idle_seconds (environment.idle_seconds, default 300; agent-scoped sandbox fixed at 300) crates/executor/src/conversation_sandbox.rs:302, the harness stores it on StoredSandbox (default 60 when a raw CreateSandboxRequest omits it crates/exoharness/src/basic/sandboxes.rs:1799), and sandbox_request() converts it with idle_ttl: Some(Duration::from_secs(sandbox.idle_seconds)) crates/exoharness/src/basic/sandboxes.rs:2624-2626. Note it is always Some on this path.

Idea worth stealing: the lease is a file mtime

Firecracker records the TTL in the immutable machine manifest and the last-use time as the mtime of a tiny lease file, refreshed by writing a temp file and renaming it over the lease (readers see the old or new time, never a torn one). Any later process, including a fresh CLI invocation, can compute expiry from disk and reap a VM it never started, with no daemon and no shared memory. crates/exoharness/src/sandbox_provider/firecracker.rs:3003-3034

Surprise: idle_seconds = 0 is not "no TTL"

The harness always builds idle_ttl: Some(Duration::from_secs(idle_seconds)). A zero therefore means "expired immediately" (Docker's check is last_used_at + ttl <= now), while the true one-shot mode (None) is unreachable through BasicExoHarness. Only direct backend users and tests exercise the one-shot paths.

Process execution model

Three levels, from raw to durable.

  1. exec: run argv to completion, return SandboxCommandOutput { ok, exit_code, stdout: String, stderr: String, command, cwd } crates/exoharness/src/sandbox.rs:103-120. Output is lossy-UTF-8 text. On Firecracker the guest caps each stream at 4 MiB (MAX_CAPTURE_BYTES) and reports "Command output exceeded the guest capture limit" crates/firecracker-guest/src/linux.rs:35 crates/firecracker-guest/src/linux.rs:562-642.
  2. start_process: returns SandboxProcessParts { stdout, stderr, stdin, wait } (boxed async readers/writer plus a future yielding the exit code) crates/exoharness/src/types.rs:1246-1251. This is the primitive every provider implements.
  3. Harness processes: start_sandbox_process wraps the parts in a RunningSandboxProcess with an id (process-<uuid7>), a cursor-numbered event vector, and an event-log writer. Every chunk is appended as EventData::SandboxProcessEvent (Stdout/Stderr/Exit/Error/Cancelled, each with a monotonically increasing cursor), so a restarted server or an unloaded Durable Object can rebuild a finished process from the log; a process still running when its host died errors with "lost its live connection" crates/exoharness/src/basic/sandboxes.rs:2169-2255 crates/exoharness/src/basic/sandboxes.rs:1185-1260. Stdin is a mode (Open/None) and callers use write_sandbox_process_input / close_sandbox_process_input; polling is get_sandbox_process_events(after_cursor).

with_process_management crates/exoharness/src/sandbox_process.rs:27-34 is a second, provider-side adapter: it wraps any stream-backed handle in a ProcessRegistry and implements start_managed_process, process_events(after), wait_process and cancel_process with the same cursor semantics. Its drain logic is careful about background children that keep a pipe open after the parent exits: it waits at most 2 s for both streams to drain, then aborts the readers crates/exoharness/src/sandbox_process.rs:179-195. Every in-repo backend (local and remote) installs it on the handles it returns. Within this repository only the module's own tests call the start_managed_process-family methods; the harness's process API (above) is what production paths use. The doc comment says providers with their own process service implement these methods directly instead of installing the adapter.

Mounts, durable filesystems, and resources

Three distinct things reach SandboxSpec.

  • Host mounts (SandboxMount { host_path, guest_path, access, internal }): bind mounts of host directories. Supported by Docker/Apple (--volume host:guest[:ro]), smolvm, and local_process (cwd mapping only). Every remote provider and Firecracker reject non-internal mounts crates/exoharness/src/sandbox/native.rs:1600-1608.
  • Durable filesystems (DurableFileSystem { name, mount_path, mode }): named persistent storage owned by the sandbox. Docker/Apple turn each into a host directory root/<fnv1a(sandbox_id\nname)> under EXO_DURABLE_FILE_SYSTEM_ROOT (or the backend-configured root) and mount it; Firecracker allocates one workspace.ext4 disk mounted at the workdir; AgentCore maps one to managed session storage crates/exoharness/src/sandbox/native.rs:930-970.
  • Resources (git repos, local directories): prepared by the executor before the sandbox exists. The strategy depends on the provider: uses_host_resource_mounts is true for apple_container, docker, local_process, firecracker, smolvm crates/exoharness/src/resources.rs:272-281.

Mechanics that differ from what you might assume:

  • Payload is a reference, not bytes, for most providers. Firecracker, smolvm, Daytona, E2B and Sprites return a small manifest naming a capture that lives in the backend's namespace; only Docker returns real bytes (the docker save tarball, held in memory as Bytes and written to payload.bin). The harness inlines the payload into manifest.json only for backend-owned captures (smolvm-filesystem-ref-v1, firecracker-host-ref, firecracker-filesystem-ref-v1, per snapshot_capture_provider), so the reference and its metadata publish in one write and so delete_owned_snapshots can call the backend's delete_snapshot when the thread or agent is deleted. Other reference formats (Daytona, E2B, Sprites, legacy smolvm pack) are skipped by that cleanup crates/exoharness/src/basic/sandboxes.rs:1346-1357 crates/exoharness/src/basic/sandboxes.rs:1615-1667.
  • Docker: docker commit -p (pause for consistency), docker save, remove the temp tag. Restore docker loads, swaps spec.image for the loaded tag and creates a fresh warm container; it requires a warm lifecycle and refuses Apple container crates/exoharness/src/sandbox/native.rs:1962-2036 crates/exoharness/src/sandbox/native.rs:496-551.
  • Teleport: start_sandbox with a different provider and a snapshot whose format the new backend consumes. Daytona consumes docker-image-tar, so a local Docker sandbox can resume remotely.
  • Firecracker filesystem capture: sync every writable mount in the guest, pause the VM, reflink the root overlay, workspace and resource disks, pin the immutable base image by sha256, publish an immutable capture atomically, resume. It supports mounts and egress proxies (a fresh proxy binding is created at restore). suspend(Filesystem) is the same capture plus killing the paused VM crates/exoharness/src/sandbox_provider/firecracker_filesystem.rs:479-587.
  • Restore validation: Firecracker refuses a snapshot whose recorded FirecrackerRuntimeFingerprint (arch, protocol version, sha256 of firecracker, jailer, kernel, initramfs, vCPU, memory, network device policy, guest-root flag) differs from the running host crates/exoharness/src/sandbox_provider/firecracker.rs:258-307 crates/exoharness/src/sandbox_provider/firecracker.rs:1207-1218.
  • Storage budgets: Firecracker and smolvm share capture_store (staged directory, atomic publish, flock-based SnapshotLease); total retained captures are capped at 64 GiB by allocated blocks and are not evicted automatically; delete explicitly with delete_snapshot crates/exoharness/src/sandbox_provider/capture_store.rs crates/exoharness/src/sandbox_provider/snapshot_lease.rs crates/exoharness/src/sandbox_provider/firecracker.rs:137.
  • Not a conversation rewind: the event log is untouched, and forking a thread does not restore its sandbox (the architecture doc says the same).

Docs overstate the proxy restriction

website/docs-src/architecture/sandboxes.md says SmolVM and Firecracker "reject snapshots with an egress proxy". In code the rejection (PROXIED_SNAPSHOT_UNSUPPORTED) applies to Firecracker Full capture and restore only; Filesystem snapshots go through EgressRuntime::acquire(AcquisitionMode::Restore, ...) and get a fresh egress binding crates/exoharness/src/sandbox_provider/firecracker.rs:1078-1080 crates/exoharness/src/sandbox_provider/firecracker_filesystem.rs:321-345. A credential-substituting sandbox can therefore be filesystem-snapshotted and restored.

The Firecracker stack

This is the largest backend (about 5.8 k lines plus image, Lima, bridge, filesystem and guest crates). The design goal, from support/firecracker/README.md: the only host-to-guest channel is a bounded JSON protocol over vsock, the host never mounts or parses guest-controlled data, and each VM is contained by KVM, the jailer, seccomp, a per-VM UID, PID/network namespaces and cgroup v2.

1. OCI image to immutable ext4

resolve_image accepts either a trusted local .ext4 path or an OCI reference crates/exoharness/src/sandbox_provider/firecracker_image.rs:116-309. For a registry reference it:

  1. Checks the registry allow-list, then looks in state_root/images/v6/<platform>/<digest>. A digest-pinned reference hits the cache with no registry request.
  2. Otherwise authenticates from the Docker credential config (exact registry origin, root-owned paths only, helper executed only at its validated absolute path), pulls the manifest and config, and validates the platform matches the host arch.
  3. Preflights the whole manifest before any download: at most 512 layers, no layer larger than 2x the image size, total compressed size at most 4x.
  4. Downloads up to 4 layers concurrently into a content-addressed blob store (each verified against its sha256 with size budgets), applying them in order with OCI whiteout handling, checking bytes and inode budgets after every layer.
  5. Creates the guest-owned directories and runs mkfs.ext4 -q -F -d <rootfs> <image>, which populates the filesystem without ever mounting attacker-controlled content on the host. The result is chmod 0444 and published by atomic directory rename crates/exoharness/src/sandbox_provider/firecracker_image.rs:728-858.

The OCI runtime config (ENTRYPOINT, CMD, USER, env, working dir) is stored in rootfs.config.json and surfaced via resolve_image, but it is not applied: commands and env come from the sandbox API, and workloads start as UID/GID 10001 support/firecracker/README.md. Default image size is 8 GiB (DEFAULT_IMAGE_SIZE_GIB) and caps how much host disk one materialization may consume.

2. Boot: jailer, VM config, overlay root

Per VM, prepare_and_launch_blocking builds a jail root, hard-links the immutable base image as rootfs.ext4 (read-only), creates a sparse overlay.ext4 upper layer with lazy mkfs, hard-links the kernel and initramfs, optionally attaches workspace.ext4 and resource disks, writes vm-config.json (root-owned, mode 0400), and spawns Firecracker through the jailer crates/exoharness/src/sandbox_provider/firecracker.rs:3942-4049. No base filesystem copy ever happens; the guest's initramfs mounts base (read-only) and upper as OverlayFS, moves the merged mount over /, then chroots so container runtimes see the right mount namespace crates/firecracker-guest/src/linux.rs:1054-1108.

Idea worth stealing: shared immutable lower, sparse per-VM upper

One digest-addressed, read-only ext4 per image is hard-linked into every jail; each VM gets only a sparse ext4 for its OverlayFS upper layer (mkfs.ext4 with lazy init on a set_len file). Boot never copies the base image, per-VM disk cost is the delta, and a snapshot's base is pinned by sha256 and shared across captures. crates/exoharness/src/sandbox_provider/firecracker.rs:3966-4002

The VM is described declaratively. Notable choices in firecracker_vm_configuration crates/exoharness/src/sandbox_provider/firecracker.rs:4225-4376:

  • Drives, in order: rootfs (read-only, cache_type: "Unsafe"), overlay (Writeback), optional workspace, then resource_N disks. The guest finds them by letter (/dev/vda, vdb, vdc...).
  • Boot args carry configuration to the guest: rdinit=/init 8250.nr_uarts=0 ... exo_allow_guest_root=1 exo_guest_ip=... exo_workdir=... exo_workspace=... exo_resource_mounts=<base64 JSON>. Hence the 4096-byte check and the "workdir must not contain whitespace" rule.
  • vsock guest_cid = slot + 3; track_dirty_pages: true and smt: false; a rate-limited virtio-rng entropy device (for clone reseeding); per-VM token-bucket rate limiters on the NIC (DEFAULT_NETWORK_BYTES_PER_SECOND = 100 MiB/s).
  • VMM stdio goes to /dev/null, never a growable file, "because a compromised guest kernel can reactivate the serial device" crates/exoharness/src/sandbox_provider/firecracker.rs:4189-4202.

Readiness is event-driven: before launch the host binds a Unix listener at <vsock>_10053; when the guest agent is listening it connects to host CID port 10053 and writes one byte, so the host waits on a socket edge rather than polling pings crates/firecracker-guest/src/linux.rs:965-1000.

3. Guest agent and the vsock protocol

The guest is a static Rust binary running as PID 1 from an initramfs (support/firecracker/build-guest.sh then build-initramfs.sh). run() mounts pseudo filesystems, sets up the overlay root, hostname, network, workspace and resource mounts, spawns an orphan reaper, binds a vsock listener on port 10052, signals readiness, and serves one request per connection on a new thread crates/firecracker-guest/src/linux.rs:902-955. Hard limits: 32 concurrent connections, 128 managed processes, 45 s socket timeout; connections whose peer CID is not the host (VMADDR_CID_HOST) are dropped, so a workload cannot ask PID 1 to run something by connecting to itself.

Framing is a 4-byte big-endian length followed by JSON wrapped in Message { protocol_version, payload }; requests are capped at 1 MiB and responses at 16 MiB (decode_frame_length). The host side, vsock_request, opens the VMM's Unix socket, sends Firecracker's host-initiated handshake CONNECT 10052\n, reads a bounded OK ... acknowledgement (reads at most 129 bytes so a hostile VMM cannot grow the buffer), then writes the frame and reads one response crates/exoharness/src/sandbox_provider/firecracker.rs:5574-5615. Because every call is a fresh connection, streaming is done by the ProcessBridge long-poll (Write, CloseStdin, Recv { timeout_seconds }, Resize), not by holding a socket open. The generic parameter B lets the host reuse process_bridge::Request as the bridge payload while the guest uses GuestProcessRequest.

Handshake identity: Ping returns GuestIdentity { implementation_version, build_id }; the host rejects empty values, and also rejects any response whose protocol_version differs crates/exoharness/src/sandbox_provider/firecracker.rs:5296-5321 crates/exoharness/src/sandbox_provider/firecracker.rs:5349-5361. Timeouts are enforced in the guest by SIGKILL to the command's process group; explicit cancellation is also process-group based, so a descendant that creates a new session can survive until the VM stops (documented limitation).

4. Network

Each VM with networking gets a network namespace fc-<slot>, a veth pair, a TAP inside the namespace, and an nftables table exo_fc_<slot>. Addresses are carved from 10.240.0.0/14 as two /30 blocks per slot (a transit pair and a guest pair) crates/exoharness/src/sandbox_provider/firecracker.rs:3292-3312. The default firewall drops IPv6, anti-spoofs source addresses, rejects the whole Exo range (guest-to-guest), and rejects the BLOCKED_EGRESS_CIDRS list (RFC1918, link-local/metadata, CGNAT, multicast, ...) unless an operator adds --firecracker-allowed-egress-cidr crates/exoharness/src/sandbox_provider/firecracker.rs:144-156 crates/exoharness/src/sandbox_provider/firecracker.rs:3506-3600. With a configured egress proxy the rules change to proxy-endpoints-only (proxy_network_firewall_rules); see Egress and vaults for what the proxy does with the traffic. When networking is disabled no TAP device exists at all; exec still works because control is vsock.

5. Full snapshots and forks

A Full capture (capture_snapshot_template) is the delicate path. Sequence: refuse if host swap is enabled; take snapshot-capture.lock; enforce the 64 GiB retained budget and a free-disk reserve; pause the VM via the jailed API socket; seed the memory file with a reflink of the previous capture (or the restore template); ask Firecracker for a Diff snapshot (dirty pages only); reflink the overlay disk while still paused; resume; then copy state and memory out of the jail, seal them root-owned 0444, drop a complete marker and publish.

Two crash-safety details: a snapshot-pending marker blocks further captures from the same sandbox until it is restarted ("Firecracker may already have cleared dirty bits, so repeating a diff against the previous base would be unsafe"), and the published snapshot is a copy, never a hard link, because a compromised VMM could hold an open fd to a hard-linked file and keep writing a "trusted" template crates/exoharness/src/sandbox_provider/firecracker.rs:5002-5013.

fork_sandbox uses the same capture with SnapshotTemplateLifecycle::Machine (a single-use template tied to the target) and immediately restores it into a different sandbox id, holding both sandboxes' lifecycle locks in deterministic order. The clone gets its own TAP/IP slot; after boot the host sends ConfigureNetwork so the restored guest stops using the source's in-memory address crates/exoharness/src/sandbox_provider/firecracker.rs:1567-1634 crates/exoharness/src/sandbox_provider/firecracker.rs:2168-2180. Forks need guest kernel 5.18+ with VMGenID to reseed the CSPRNG.

6. Machine records, fingerprints, adoption

Each VM has a MachineRecord manifest (machine_id, spec_hash, runtime fingerprint, resolved_image, network slot, idle_ttl_seconds, optional snapshot template) written under state_root/manifests crates/exoharness/src/sandbox_provider/firecracker.rs:396-411. machine_id is derived from the sandbox id and spec hash, which is how a new process finds a VM started by an earlier one. ensure_machine adopts a running VM only if the pid file is live, the spec hash and runtime fingerprint match, and a vsock Ping succeeds; otherwise it cleans up and relaunches crates/exoharness/src/sandbox_provider/firecracker.rs:2044-2100. Lifecycle is serialized with per-machine and per-sandbox async locks (MachineLifecycleLocks), and a capacity reservation (max_machines) is held from admission until the VMM is up or cleaned up.

The exposed state returned to the harness is deliberately tiny: FirecrackerProviderState { machine_id, spec_hash, guest_ip } crates/exoharness/src/sandbox_provider/firecracker.rs:245-255. Preview traffic uses guest_ip: connect_tcp is a plain TcpStream::connect((guest_ip, port)) via a host route to the VM's /30 crates/exoharness/src/sandbox_provider/firecracker.rs:1799-1806.

7. macOS: Lima as the outer VM

Firecracker needs Linux and KVM. On Apple M3+ the backend factory selects LimaFirecrackerSandboxBackend at compile time (cfg(target_os = "macos")) crates/exoharness/src/sandbox_provider/mod.rs:144-177. The native CLI stays on macOS; a dedicated Lima VM (--vm-type=vz --nested-virt) runs the same FirecrackerSandboxBackend code inside a root process, reached over stdio.

macOS (native exo CLI)                       Lima VM "exo-firecracker" (vz, nested KVM)
+-------------------------------+   limactl   +---------------------------------------+
| LimaFirecrackerSandboxBackend |   shell --  | firecracker-bridge  (root, sudo -n)   |
|  - EgressRuntime + vault      |   sudo      |   run_firecracker_bridge()            |

  • Bring-up: prepare_bridge lists Lima instances and refuses to continue if the named one does not exist, because limactl start <name> silently creates a default VM that mounts the user's whole home directory. Then it starts the VM, checks /dev/kvm read/write, installs xfsprogs, builds the firecracker-bridge example with cargo inside the VM (low-memory flags: one job, lld linker), and installs it to the root-owned /usr/local/libexec/exo-firecracker-bridge so sudo never runs a binary the build user can replace crates/exoharness/src/sandbox_provider/firecracker_lima.rs:666-770.
  • Protocol: FirecrackerBridgeRequest is one variant per backend operation (Acquire, Exec, StartProcess, ConnectTcp, Snapshot, Fork, MaterializeResources, EgressCreate/Bind/Accept/Close, ...) with the full FirecrackerConfig and request attached to each call; the bridge process keeps a BridgeBackendCache that builds one FirecrackerSandboxBackend per distinct config (and runs the XFS storage preparation on first use). Server frames add StreamOpened/StreamData/StreamClosed with channels Stdout, Stderr, Tcp; frames are capped at 16 MiB and stream chunks at 64 KiB crates/exoharness/src/sandbox_provider/firecracker_bridge.rs:18-24 crates/exoharness/src/sandbox_provider/firecracker_bridge.rs:26-170 crates/exoharness/src/sandbox_provider/firecracker_bridge.rs:220-250.
  • Egress stays on the Mac: the EgressRuntime and credential resolver are constructed in the macOS process; the VM only exposes listeners, and accepted proxy connections are relayed back over the bridge as Tcp streams (EgressAccept) crates/exoharness/src/sandbox_provider/firecracker_lima.rs:1590-1645. Vault secrets never need to enter the VM.
  • Storage: resource and snapshot features need XFS with reflink=1. Exo provisions a sparse XFS image inside Lima at the state root on first start (mkfs.xfs -m reflink=1 on a sparse file sized to 80% of the free space) crates/exoharness/src/sandbox_provider/firecracker_lima_storage.rs:20-100. support/firecracker/lima-admin.sh restarts the VM or wipes per-microVM state, refusing any state root outside /var/lib/exo/firecracker/.
  • Gaps vs native Linux: the Lima handle implements no start_terminal; one-shot (no TTL) Lima sandboxes cannot be stopped, snapshotted or TCP-connected. The README says plainly this is a development path, not a production trust boundary (the Lima user has passwordless sudo and a writable checkout mount).

Surprise: the "bridge" is the real backend

The macOS backend does not reimplement anything. run_firecracker_bridge instantiates the ordinary Linux FirecrackerSandboxBackend and maps each frame to a trait call, which is why snapshot payloads cross as base64 strings and why even MaterializeResources and ResolveImage are bridge requests: the OCI pull and mkfs.ext4 run inside Lima, never on macOS.

Preview and port forwarding

A sandbox publishes TCP ports through tcp_ports on its environment (nonzero, no duplicates) and they become part of sandbox identity. Reaching them is a two-step capability: the provider must implement connect_tcp (smolvm, Firecracker, Firecracker-over-Lima only), and a host-side proxy must route to it.

  • Browser previews: PreviewProxy listens on 127.0.0.1 (port persisted in previews/listener.json so URLs survive restarts), routes by Host header, and for each service port serves http://<port>.<slug>-<sha256(thread_id)[..8]>.<domain>:<listener_port>. previews_for derives the hostnames; register installs one route per port plus a "Sandbox services" index page crates/executor/src/previews.rs:36-88 crates/executor/src/previews.rs:206-232.
  • Per-request resolution: on each request handle parses headers with httparse (32 KiB cap, exactly one Host), finds the running sandbox that publishes the port (published_sandbox), calls thread.connect_sandbox_tcp, replays the already-read request bytes, then copy_bidirectional. A miss yields 502 "Preview unavailable. Start the sandbox and its services."; the sandbox id is cached but dropped on error crates/executor/src/previews.rs:259-270 crates/executor/src/previews.rs:311-387.
  • CLI: exo sandbox forward does the same for a local TCP port (SandboxCommands::Forward to port_forward::run) crates/cli/src/port_forward.rs:8-33.
  • The agent is told the URLs in its instructions ("Use these browser origins for links, API URLs and CORS ... Previews live while the owning Exo process runs") crates/executor/src/previews.rs:91-104.

Provider-specific wiring: smolvm publishes each port to a host ephemeral port when the machine is created (host_ports), with --outbound-localhost-only when outbound networking is off; harness code special-cases smolvm in connect_sandbox_tcp so a probe never restarts the machine crates/exoharness/src/basic/sandboxes.rs:659-696. Firecracker requires networking enabled and warns that the host route makes in-sandbox services reachable by any local process.
