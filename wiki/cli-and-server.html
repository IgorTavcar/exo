Runtime internals

CLI, server & tooling

The exo binary is a thin clap front-end over one executor::Runtime, built either in-process on local files or as an HTTP client of a remote runtime. This page covers how exo run works, the provider/env config model, the three terminal UIs, the test strategy, and the engineering workflow (hooks, CI, fuzzing, docs site, Harbor evals).

The shape of the binary

crates/cli is one crate that produces exo (crates/cli/src/main.rs, 2.8k lines, mostly the clap tree and a giant match) plus an optional exo-provider-contract test binary (crates/cli/src/bin/provider_contract.rs:1-25) that runs executor::contract_tests::test_provider against any managed-agent HTTP endpoint. There is no daemon and no background service: every invocation builds its own runtime, does one thing, and shuts it down (crates/cli/src/main.rs:2005-2007). Almost every command is written against Runtime; whether that runtime is backed by local files or by HTTP is decided once, up front.

Command tree

Top-level names are in crates/cli/src/main.rs:536-608. How exo run works end to end

There is no service auto-start. exo run agent.md constructs the full runtime inside the CLI process (state under ~/.exo, sandbox backends registered, model calls made directly), runs the turn loop, and exits. The only long-lived server is exo run --serve, which is something you start yourself. The alternative to in-process is a saved provider profile that points at an HTTP runtime; the same run code then talks to it through HttpProvider.

Step by step

  1. Parse and progress setup. For run without --serve, turn_display::init_progress installs a tracing subscriber whose only job is to turn log events with target exoharness::progress into spinner text (crates/cli/src/main.rs:1000-1014, crates/cli/src/turn_display.rs:14-66).
  2. Provider selection. run loads providers.json, then picks a profile (or none). run --serve deliberately ignores any saved selection unless --provider is passed explicitly (crates/cli/src/main.rs:1043-1053). A Connection::Local { root } profile simply rewrites cli.root, so a "local provider" is just a named state directory (crates/cli/src/main.rs:1082-1085).
  3. Stderr banner for mutations. Except for read-only commands (list/get/events/doctor), the selected provider and account are printed to stderr as provider: NAME; account: ID, keeping stdout machine-parseable (crates/cli/src/main.rs:1087-1125; asserted in crates/cli/tests/provider_workflow.rs:6-14).
  4. Alias resolution. Saved agent/thread aliases are rewritten to remote IDs (crates/cli/src/providers.rs:567-588), then --env-file is loaded and the agent Markdown (AgentDefinition) parsed.
  5. Runtime construction. providers::runtime branches HTTP vs local (code below). Local mode builds BasicExoHarness at <root>/exoharness, registers every sandbox backend (crates/cli/src/main.rs:453-468), loads the LiteLLM price table (cached at <root>/cache/litellm_prices.json), and hands the CLI's harness/model/mount flags to the provider as LocalAgentSetup.
  6. Open thread. open_thread resolves --environment/--environment-file, attaches --vaults, then either resumes a saved thread (by slug or ID) or creates one; new names are validated to 1–128 ASCII [A-Za-z0-9_-] chars (crates/cli/src/managed_agents.rs:16-31, crates/cli/src/managed_agents.rs:224-327). It prints agent:, thread:, vault:, model:, and mcp: lines on stdout; tests parse the thread: slug (id) line.
  7. Pre-flight. Locally, check_model_credentials verifies the model credential exists in the thread's vaults and its policy permits the model endpoint, and prints the exact exo vault secret update ... --allow-origin fix if not (crates/cli/src/managed_agents.rs:329-383). Then start_inline_previews and the preview URLs are printed.
  8. Front-end. One of three UIs, chosen at crates/cli/src/main.rs:1209-1224 (see below). The thread slug is pinned as an alias to the provider/account if a provider was selected.
  9. Teardown. The command body is wrapped in an async block so harness.shutdown() always runs; the command's error wins, otherwise the shutdown error is returned (crates/cli/src/main.rs:1160, crates/cli/src/main.rs:2003-2007).

No daemon, and --tui degrades silently

Two things differ from what you might expect. First, nothing is auto-started: preview links and scheduled/Slack work only exist while an Exo process owns the root (crates/cli/src/previews.rs:31). Second, --tui on a non-TTY quietly falls back to the plain REPL (the interactive check above), whereas --tui with an HTTP provider is a hard error (crates/cli/src/providers.rs:122). --prompt conflicts with --tui and --serve at the clap level (crates/cli/src/main.rs:577-584).

What only works locally

  • --egress-policy FILE is rejected with a remote provider ("put the policy in the remote environment definition"), and conflicts with an environment that already carries a policy (crates/cli/src/main.rs:1142-1149, crates/cli/src/managed_agents.rs:238-265). The file may be JSON, YAML or TOML, picked by extension (crates/cli/src/main.rs:390-404).
  • Sandbox overrides and mounts are refused remotely because "remote providers manage their own sandboxes" (crates/cli/src/managed_agents.rs:136-143). Mounts are canonicalized and must be existing directories; mount paths must be absolute (crates/cli/src/main.rs:2216-2280).
  • Default sandbox is smolvm (crates/cli/src/main.rs:480-482), the default Cargo feature (crates/cli/Cargo.toml:9-13). Firecracker args exist only with --features firecracker; for commands that do not flatten them, the CLI builds defaults by parsing an empty argv through the same clap struct (crates/cli/src/main.rs:417-425).

Server mode: exo run --serve

crates/cli/src/serve.rs:40-183 (args at crates/cli/src/serve.rs:15-38) is the whole server entry point. It wires executor::http_service::RuntimeHttpService (the managed-agent HTTP API; see managed agents) to an actix server, plus an AdapterService that supervises Slack and other adapters, plus the browser preview proxy.

Mutual exclusion is a plain file lock: serve takes <root>/service.lock with try_lock ("another agent service is using this root") (crates/cli/src/serve.rs:52-62), and exo identity in local mode tries the same lock and refuses to run if the server holds it (crates/cli/src/identity.rs:99-115). Those are the only two users of the lock; a plain exo run does not take it. Shutdown handling is two-phase: the first SIGINT/SIGTERM cancels adapters and stops the HTTP server gracefully, and a second Ctrl-C calls process::exit(130) (crates/cli/src/serve.rs:150-183).

Provider profiles

Connection is a two-variant serde-tagged enum, Local { root } or Http { endpoint } (crates/cli/src/providers.rs:337-342). A Profile adds an api_key_env name or stored_credentials (keychain OAuth), the authenticated account_id, and a free-form context string map that is sent as JSON in the X-Exo-Context header and otherwise not interpreted (docs/providers.md; crates/cli/src/providers.rs:344-357). Selection precedence in Store::selected (crates/cli/src/providers.rs:491-553):

  1. A saved thread or agent alias (it carries its own provider, endpoint, account, context). An explicit --provider that disagrees is an error.
  2. Explicit --provider NAME (uses that profile's context).
  3. Nearest directory default (walks cwd.ancestors(); set by provider switch --local).
  4. The global default (provider switch).
  5. None: built-in local Exo.

Aliases pin. After agent create or run, the agent/thread slug is stored with the provider name, connection, account and context at that moment (crates/cli/src/providers.rs:590-648). A later endpoint change makes the alias fail with "provider configuration changed for this alias" instead of silently pointing the name at a different server, and a different logged-in account is rejected with "belongs to a different account" (crates/cli/src/providers.rs:519-523, crates/cli/src/providers.rs:567-588).

The closure runs against a freshly reloaded config under the lock, so unrelated changes by another process survive. Profile edits additionally compare-and-swap against the profile the command started from and bail with "changed in another process; retry" (crates/cli/src/providers.rs:434-442); login compares the keychain contents before and after the browser round-trip (crates/cli/src/providers/oauth.rs:325-368). These are covered by the "stale store" unit tests in crates/cli/src/providers/tests.rs:294-395. Credentials: an api_key_env profile reads a bearer token from that env var every run; otherwise OAuth credentials (via rmcp's AuthorizationManager) are stored in the OS keychain under service exo-provider, keyed by the profile's UUID, with a per-profile lock file (crates/cli/src/providers/oauth.rs:20-93). On a headless box without a keychain, the error tells you to use --api-key-env (crates/cli/src/providers/oauth.rs:39-41).

When a server answers 400 {"code":"context_required", ...}, request_error turns that into a ready-to-paste repair command that depends on where the selection came from (provider update for explicit profile, provider switch for global, a cd dir && ... --local form for directory selections, or an explanation for pinned aliases) (crates/cli/src/providers.rs:294-335).

Idea worth stealing: secret flags take variable names, never values

--token-env, --api-key-env, --client-secret-env are validated by parse_env_var_name, which rejects anything that is not an identifier with "pass an environment variable name such as OPENAI_API_KEY, not the secret value" (crates/cli/src/main.rs:2510-2519). A pasted key therefore fails fast instead of landing in shell history or ps. Resolution order is env-file first, then process env (crates/cli/src/main.rs:2521-2537).

Slash commands are a clap tree

The TUI's /quit /cost /verbosity /shell /snapshot /snapshots /rewind /teleport /help are not a hand-rolled match on strings. They are a clap Subcommand parsed in multicall mode, so aliases, per-command usage, argument types (SnapshotKind is a real parsed enum) and /help output all come from the derive (crates/cli/src/tui_app.rs:35-150). The line REPL implements the same commands with plain string matching (crates/cli/src/tui.rs:444-561), and both reuse the same *_lines helpers that return Vec<String> so a screen-owning UI never writes to stdout directly.

Rendering: verbosity, folding and the progress side-channel

  • Three verbosity levels (--verbosity, /verbosity): minimal hides tools, compact (default) shows one line per tool call with its primary argument (first of command, cmd, code) and result status, full expands every argument and result (crates/cli/src/render.rs:22-36).
  • Result folding. For history replay in compact mode, TranscriptFold pre-scans the whole message list, maps each tool-call ID to its result status (✓, ✗ exit 2) and appends it to the call line, then suppresses the standalone result (crates/cli/src/render.rs:86-138, crates/cli/src/render.rs:210-253). Live streaming does the same with a pending_tool_calls map (crates/cli/src/tui.rs:736-774).
  • Streaming dedupe. Token deltas are written as they arrive; when the final Messages event lands, only the part of the text not already streamed (strip_prefix(&streamed_message)) is printed (crates/cli/src/tui.rs:697-710). AssistantLine tracks whether a label is open so tool lines interleave cleanly (crates/cli/src/tui.rs:34-64, with unit tests at the bottom of the file).
  • Spinner and backend progress. TurnProgress::wait races a future against Ctrl-C and a 120 ms tick that paints \r\x1b[2K- status to stderr (only when stderr is a TTY). Backend code reports sub-steps ("Pulling image...") by emitting tracing::info!(target: "exoharness::progress", ..); a custom layer stores the last message in a global mutex that the spinner swaps into its label. When stderr is not a TTY the same events print as plain log lines (crates/cli/src/turn_display.rs:14-130).
  • Usage line. After each turn, UsageTracker::refresh pages through messages events by cursor, groups UsageRecords by turn, and prints ttft, duration (tok/s), tokens [total], cost [total]; unmetered assistant messages count as a record with unknown fields so totals degrade to "unavailable" rather than silently under-reporting (crates/cli/src/turn_display.rs:174-262, crates/cli/src/turn_display.rs:311-348). /cost shows the same data per model.

Replayed history is stamped with "now"

render_message_lines calls compact_timestamp() when it renders each message (crates/cli/src/render.rs:145), and that function formats the current UTC time-of-day (crates/cli/src/render.rs:268-277). So /history or a resumed thread shows every old message with the time you printed it, not the time the event was recorded. Event IDs are UUIDv7, so the real time is recoverable (snapshots_lines does exactly that for snapshot IDs, crates/cli/src/tui.rs:1030-1036), it just is not used here.

Idea worth stealing: the TUI never owns turn state

The thread's event log is the only source of truth. Background-event display (scheduled-task wake-ups, Slack-initiated messages) is a polling watcher over get_events(cursor) that is paused while busy is set, because the streaming path already rendered those messages and the cursor only advances on Completed (crates/cli/src/tui_app.rs:1151-1158). Only user messages starting with Scheduled task ` are shown from the log (crates/cli/src/tui.rs:932-940). Clipboard copy is OSC 52 from the rendered ratatui buffer, with a tmux set-clipboard check that warns when the escape would be swallowed (crates/cli/src/tui_app.rs:1085-1113, crates/cli/src/tui_app.rs:1328-1345).

Other CLI pieces worth knowing

  • Mounts. --mount HOST:GUEST[:ro|rw] (read-only by default) is parsed by parse_mount_spec (crates/cli/src/main.rs:2216-2240); agent mount/thread mount edit the saved config and, when no guest path is given, choose /home/exo/workspace/<basename>[-N] via default_mount_path (crates/cli/src/main.rs:2263-2280; the constant is crates/exoharness/src/sandbox.rs:511). Thread mounts are refused when the thread has an environment, since the environment owns them (crates/cli/src/main.rs:1731-1734). Unit tests: crates/cli/src/mount_tests.rs.
  • Thread names. Auto slugs are word-word-<last 8 hex of a UUIDv7> (e.g. north-anchor-70b08878), with the words picked from two 24-word lists by UUID bytes (crates/cli/src/main.rs:2551-2580; tests in crates/cli/src/naming_tests.rs).
  • sandbox forward opens a local TCP listener and bridges each connection with copy_bidirectional to conversation.connect_sandbox_tcp, after checking the provider supports TCP (crates/cli/src/port_forward.rs:8-61). Browser previews are the HTTP counterpart, set up by start_inline_previews and printed by crates/cli/src/previews.rs; their implementation is in sandboxes.
  • agent doctor merges CLI-side checks (definition loads, each adapter's transport vault holds required secrets) with the agent's own diagnose(), prints ok/warning/error: name: message plus a fix: line, and exits 1 on any error (crates/cli/src/main.rs:1413-1438, crates/cli/src/main.rs:2305-2410).
  • MCP auth errors are rendered as one friendly line with the exact exo vault secret create ... --from-agent FILE command to run, unless --verbosity full (crates/cli/src/main.rs:922-998; tests crates/cli/tests/mcp_auth_error.rs).
  • thread complete-rebuild-update is plumbing for the self-improving example: a guardian process reports the result of a rebuild_and_restart_exo, written first to a side-channel file and then appended to the thread as a host event (crates/cli/src/main.rs:1921-1963).

There are no real LLM calls and, by default, no real sandboxes. How the Fixture works (crates/cli/tests/support/mod.rs:49-125): it starts a wiremock model server, builds a BasicExoHarness + LocalProvider + Runtime in the test process, serves that runtime over actix at 127.0.0.1:0/exo behind a bearer token (RuntimeHttpService::new(runtime, Some("workflow-token"))), and records every request's x-exo-context header. It then invokes the real exo binary to create two provider profiles, local (--local-root at the same directory) and remote (--url at the in-process server). Because both profiles ultimately drive the same runtime code, a test body can loop over ["local", "remote"] and assert identical behaviour: permissions.rs does it for approval prompts on shell and MCP tools with y/n answers piped to stdin; environments.rs does it for named-thread resume.

Idea worth stealing: parity testing is the architecture's payoff

Because Runtime hides local vs HTTP behind one Provider trait (crates/executor/src/provider.rs:19), the CLI's e2e coverage doubles for free: every workflow test is two tests. The same trick also gives a conformance tool: exo-provider-contract (feature contract-tests) points test_provider at an arbitrary HTTP endpoint with a token, so a third-party implementation can be checked with the same code (crates/cli/src/bin/provider_contract.rs:7-25).

Smaller conventions: every spawn has a 20 s timeout (crates/cli/tests/support/mod.rs:250) and kill_on_drop; tests reach PATH but nothing else from the host env; the master key is a file in a tempdir (--secret-backend file) so the macOS keychain is never touched. CI fails rather than skips when a live runtime is missing (crates/cli/tests/integration_chat.rs:5-9).

Fuzzing

There is exactly one target, firecracker_protocol (fuzz/fuzz_targets/firecracker_protocol.rs:1-36), run manually with cargo +nightly fuzz run firecracker_protocol --fuzz-dir fuzz (fuzz/README.md). It feeds arbitrary bytes to the two things that parse untrusted data on the vsock between host and microVM guest: the 4-byte length-prefix decoder decode_frame_length (bounded by MAX_REQUEST_BYTES = 1 MiB and MAX_RESPONSE_BYTES = 16 MiB, crates/firecracker-protocol/src/lib.rs:14-15, crates/firecracker-protocol/src/lib.rs:143) and the typed Message<GuestRequest<GuestProcessRequest>> / Message<GuestResponse> JSON envelopes. The corpus is two seed files (ping-request.json, ping-response.json). It is not wired into CI.

Harbor evals (eval/harbor)

This runs Exo as a Harbor external agent against Harbor's benchmark catalog (Terminal-Bench 2.0 and variants, plus local datasets: a lifecycle smoke test, a four-task self-evolution-smoke-test, and a generated SWE-bench Lite) (eval/harbor/eval.py:19-40, eval/harbor/README.md). It measures the task pass rate of the Exo agent including its ability to change itself between tasks.

How Exo plugs in

  1. eval.sh creates a Python 3.12 venv, installs the exo-harbor package, and re-execs itself under sg docker if needed. eval.py builds exo with cargo build -p exo, runs pnpm install --frozen-lockfile (the TS harness runner imports tsx), and launches harbor run --env docker --agent exo_harbor.agent:ExoAgent --plugin exo_harbor.plugin:ExoSessionPlugin with --ak kwargs (eval/harbor/eval.py:270-318).
  2. ExoSessionPlugin runs once per job: requires Docker, a single agent, and n_concurrent == 1 for the exo harness (trials share one self-evolving agent), then creates the shared agent harbor-eval (eval/harbor/src/exo_harbor/plugin.py:24-53).
  3. ExoAgent runs per trial: find Harbor's main container by Compose labels (refusing to guess if there are zero or several), optionally install Node and Pi into it for the pi arm, create a fresh thread trial-<context_id>, exo sandbox attach the container as the thread's sandbox, and exo thread send the task instruction as one turn. Harbor owns the container's lifetime; Exo only borrows it (eval/harbor/src/exo_harbor/agent.py:78-135, eval/harbor/src/exo_harbor/exo.py:79-110).
  4. Afterwards, even on timeout, export_trial_trajectory calls thread events --type messages --type tool_requested --type tool_result, validates with pydantic, and converts to Harbor's ATIF trajectory format, including per-turn usage and cost (eval/harbor/src/exo_harbor/trajectory.py:160-190, eval/harbor/src/exo_harbor/agent.py:107-129).

Three arms: exo (default; uses examples/self-improving-agent/harness.ts with memory, skills and tool creation), basic (shell-only control), and pi. The self-evolution dataset checks that tools installed in trial 1 (install_agent_tool) are reusable in trial 2, and exercises restart and timeout handling (eval/harbor/datasets/self-evolution-smoke-test).

The Harbor integration is stale against the current CLI

It still drives an older command surface that no longer exists in crates/cli. eval.py calls exo secret create ... --env and exo model create ... (eval/harbor/eval.py:411-437); there is no top-level secret or model command (secrets are now exo vault secret create, and models are plain names in the agent spec). ExoClient.ensure_agent runs agent create "Harbor eval" --model --provider docker --sandbox-scope agent --module ... --tool-creation enabled (eval/harbor/src/exo_harbor/exo.py:34-61), but agent create now takes a Markdown spec file and only --name/--slug (crates/cli/src/main.rs:614-618). _argv puts --harness before the subcommand (eval/harbor/src/exo_harbor/exo.py:201-209) although --harness exists only on run and thread send; and sandbox attach --provider docker would be consumed by the global --provider profile flag (crates/cli/src/main.rs:73), where the sandbox flag is --sandbox (crates/cli/src/main.rs:789). The newest commit to eval/harbor predates the agent-definition refactor (#401). Treat it as a design reference for the plug-in shape, not a working harness.

Takeaways

Idea worth stealing: validate remote support by exhaustive pattern, not by convention

validate_http_command lists every allowed command shape as a match arm, and for thread update it destructures ConversationSandboxRuntimeUpdateArgs without a trailing .. (crates/cli/src/providers.rs:124-147). Adding a new sandbox flag to that struct fails to compile until someone decides whether it is legal against a remote runtime.

Idea worth stealing: progress as a tracing target

Backends never import UI code. They log with target: "exoharness::progress"; the CLI turns that single target into spinner text (TTY) or plain lines (non-TTY) and routes exoharness::egress* logs to stderr only in --verbosity full (crates/cli/src/turn_display.rs:16-45). The library stays headless and the UI stays decoupled.
