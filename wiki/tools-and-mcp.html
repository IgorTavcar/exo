Runtime internals

Tools, MCP & skills

How an agent gets its tools (TypeScript modules, client-executed tools, MCP servers), how a model's tool call is authorized, executed and recorded as events, and how an interrupted call is reconciled after a restart. Skills are covered at the end.

The big picture

Exo has no single "tool system". A tool is a ToolDefinition (name, description, JSON-schema parameters) that the model sees, plus one of three ways of executing it. The durable record is always the same pair of events, tool_requested and tool_result crates/exoharness/src/types.rs:601-610, regardless of who ran the call.

Routing a tool call

TypeScript path: HarnessToolRegistry

The shared Responses turn loop rebuilds a fresh registry every model round (this is why a newly installed tool is "available next round") exoharness/typescript/model-runtime/turn-loop.ts:122-127. After registering built-ins, library modules from agentConfig.typescript.toolModulePaths, and installed tools, it registers every Rust-supplied definition in context.tools (MCP tools + client tools) as a pass-through instance exoharness/typescript/model-runtime/turn-loop.ts:128-143. It then calls validateToolPolicies, sends tools.definitions() to the model, appends the response events, and executes each returned call exoharness/typescript/model-runtime/turn-loop.ts:197-206.

Any exception (unknown tool, denied approval, handler error) is caught in executeToolCallOrError and turned into { ok: false, error } so a failing tool never crashes the turn exoharness/typescript/harness/tools.ts:90-105. Denial surfaces to the model exactly this way: the Rust side throws tool call denied by the user: NAME.

Idea worth stealing: authorization: "runtime" avoids double approval

A tool that delegates to Rust (shell, MCP, client tools) would be authorized twice: once by the TS registry, once inside Rust's execute_tool handler. Instead of de-duplicating at the Rust side, ToolInstance carries a one-value flag exoharness/typescript/harness/tools.ts:29-34 and delegating tools set it. The TS registry skips authorizeTool; handle_request authorizes exactly once crates/executor/src/typescript_runtime.rs:173-199. TS-native tools (no flag) use the explicit AuthorizeTool runtime request, which returns null after the same authorize gate.

Every TS-path result is wrapped before it reaches the event log. compactToolResult always writes the full JSON to an artifact tool-results/<tool>/<callId>/result.json, additionally writes stdout.txt / stderr.txt when the result has those string fields, and returns an envelope exoharness/typescript/harness/tools.ts:156-182:

The Rust-only BasicExecutor does no compaction; it stores the raw tool result (and wraps errors as {"ok": false, "error": "..."}) crates/executor/src/basic.rs:237-300.

MCP isError is not ok: false in the registry envelope

resultOk only inspects a boolean ok field. An MCP CallToolResult with "isError": true contains no such field, so in the TS registry path its envelope says ok: true; the error is only visible inside value / preview. The Claude runtime-tool bridge, by contrast, checks both ok === false and is_error === true exoharness/typescript/harness/client-tools.ts:6-13. Whether the model is misled depends on it reading the payload, not the envelope flag.

Rust path: BasicExecutor and handle_request

In the Rust-only Basic harness the loop is: build the request (shell definition from ConversationConfig.shell_program + ToolRuntime::definitions() + client tool definitions), call the model, append the response events preceded by a exo.basic.tool_round marker, then execute_tool_round crates/executor/src/basic.rs:150-235. For each call it runs permissions::authorize, then branches: client tool → frontend_tools::execute, otherwise ToolRuntime::execute crates/executor/src/basic.rs:237-280.

Which runtime sits underneath is decided in ManagedExecutor::thread: Basic and RLM harnesses get McpToolRuntime::new(BasicToolRuntime, mcp.tools); the Exo harness swaps in ExoToolRuntime crates/executor/src/native/managed_executor.rs:66-105. BasicToolRuntime executes only shell. ExoToolRuntime adds schedule_sandbox_task, list_scheduled_tasks, cancel_scheduled_task, delete_scheduled_task, list_conversation_events, get_sandbox_status, list_sandbox_snapshots, snapshot_sandbox, rewind_sandbox crates/executor/src/native/harness_tool.rs:81-190.

Rust executes tools whose definitions it does not own

ExoToolRuntime::definitions() is not overridden, so it returns the trait default (empty). The model-facing schemas for the sandbox-control tools live in TypeScript (examples/self-improving-agent/tools/sandbox-tools.ts), registered through hostTool(), a bridge that forwards execute to context.executeTool with authorization: "runtime" examples/self-improving-agent/tools/host-tools.ts:23-37. Adding a Rust-backed tool is therefore two edits in two languages: a match arm in ExoToolRuntime::execute and a TS definition.

TypeScript tools

Shape of a tool

A Tool separates the model-facing definition from initialization parameters (host-side configuration, never shown to the model) and a handler factory exoharness/typescript/harness/tools.ts:41-49:

initializeTool validates before a tool can be registered: name matches /^[A-Za-z0-9_-]+$/ and ≤ 64 chars, non-empty description, parameters.type === "object" with additionalProperties: false; the initialization arguments are checked against initializationParameters by a small built-in JSON-schema subset; the returned handler must have execute (a handler with invoke gets a pointed error) exoharness/typescript/harness/tools.ts:266-329, exoharness/typescript/harness/tools.ts:388-399. For source === "agent" it also applies strict-mode validation: every key in properties must be in required, optional params must be typed nullable, recursively exoharness/typescript/harness/tools.ts:331-386.

Idea worth stealing: reject strict-mode violations at install time

The model runtime sends every tool with provider strict mode on, so one non-strict schema makes the model API reject every turn. The comment on validateStrictToolParameters explains the placement: it runs in manage_tool (reject the install) and again at registration (skip just the broken tool and keep the turn alive) exoharness/typescript/harness/tools.ts:331-336. Note the asymmetry: Rust MCP tool definitions are sent with strict: Some(false) crates/executor/src/mcp.rs:28, since third-party schemas cannot be expected to satisfy it.

The workspace tool registry (.exo/tools)

Agent-installed tools are an on-disk package registry with a lockfile. A source directory holds exo-tool.json with exactly {schemaVersion, id, module}; ids must match ^tool:[A-Za-z0-9][A-Za-z0-9._/-]{0,127}$ exoharness/typescript/harness/tool-registry.ts:366-389. Sources are either workspace-relative local paths (symlink-resolved and required to stay inside the workspace) or git with a pinned 40–64 hex commit that is re-verified with rev-parse HEAD after checkout exoharness/typescript/harness/tool-registry.ts:233-275, exoharness/typescript/harness/tool-registry.ts:284-339.

  1. Copy/clone into .exo/tools/.staging/candidate-*, read the manifest, check the module path stays inside the source root.
  2. Validate by actually loading the module (loadAgentTool with the proposed initialization) and reject names of built-in tools exoharness/typescript/harness/built-in-tools.ts:381-391.
  3. Under a cross-process lock file (registry.lock, O_EXCL, stolen after 60 s, 10 s acquire timeout) re-read the lockfile, re-validate the other installs, and reject duplicate model-facing tool names across different ids exoharness/typescript/harness/tool-registry.ts:108-136, exoharness/typescript/harness/tool-registry.ts:432-483.
  4. Move into store/<id>/<uuid>, atomically write tools.lock.json (temp file + rename), then delete the replaced store directory. Installing an existing id is an upsert.

The lockfile is validated on read, including that each installPath lies under store/ exoharness/typescript/harness/tool-registry.ts:517-528. A broken installed tool is logged and skipped rather than failing the turn exoharness/typescript/harness/tool-modules.ts:127-132.

Idea worth stealing: secrets by reference in persisted tool config

Agent tool initialization is persisted in the lockfile, so any string value that is exactly "${NAME}" is resolved from the host environment each time the tool loads; a missing variable is a load error, and everything else passes through exoharness/typescript/harness/tool-modules.ts:261-296. The manage_tool description tells the model to use this form instead of literal secrets exoharness/typescript/harness/built-in-tools.ts:191-195. Only agent-source tools get the expansion; library tools receive their initialization verbatim exoharness/typescript/harness/tool-modules.ts:244-259.

Trust model

Tool modules run in the harness process with the full TurnContext: they can start sandbox processes, read events, write artifacts. There is no capability sandbox for the module itself; exoharness/docs/tools.md:16 says so explicitly. The conversation sandbox only constrains what a tool does through shell / startSandboxProcess (sandbox-process.ts wraps that process handle as web streams).

The shell tool end to end

The TS side defines the schema and a handler that forwards to Rust. The Rust side parses ShellToolArguments {command}, ensures a sandbox exists, runs [shell_program, "-lc", command] and drains stdout / stderr / exit code into ShellToolResult crates/executor/src/shell_tool.rs:33-54, crates/executor/src/executor_types.rs:376-383. Under the Exo harness, execute_exo_shell_tool picks the sandbox: the conversation sandbox if one is attached (or scope is Conversation), otherwise the shared agent sandbox crates/executor/src/native/harness_tool.rs:826-854. The shell program is part of ConversationConfig; if it is unset, shell is simply not exposed. There is no timeout or output cap in read_shell_process; the cap comes from TS result compaction.

The JS "repl" is an RLM internal, not a general tool

harness_js_repl.rs embeds the Boa JavaScript engine. JsReplState::execute builds a fresh BoaContext per call, re-injects the persisted globals (JSON-roundtripped), defines context, getMessages(role), print and a Final variable, evals the code, then serializes surviving JSON-safe globals back crates/executor/src/native/harness_js_repl.rs:27-111. State persists only as JSON values: functions and non-serializable objects are silently dropped between calls. It is used solely by the RLM executor (rlm.rs), where setting Final ends the turn.

RLM turns do not use canonical tool events for internal tools

RLM records its own tools as custom events rlm_tool_call / rlm_tool_result crates/executor/src/native/rlm.rs:163. Only client tools get real tool_requested / tool_result events there, because those are the ones external consumers must see. Policies still apply: RLM calls authorize for every tool, but with tool_call_id: None (see approvals for why that matters).

Docs vs code: the "default" built-in tools

exoharness/docs/tools.md:102-108 says the default Responses harness registers shell, inspect_tools and manage_tool. In the code defaultBuiltInToolNames returns ["shell"], plus the two legacy tools when enableAgentToolCreation is on exoharness/typescript/model-runtime/turn-loop.ts:78-87. Only the example harness profiles (examples/self-improving-agent/profiles/bootstrap.ts, practical.ts) list all three names. Likewise exoharness/docs/design/tool-support.md proposes tool_policy_decision / tool_invocation_* events; none exist in code. Approvals were built as agent_runtime.approval_* events instead.

Client tools

A client tool is declared by the HTTP caller on each turn request as frontend_tools (name, description, parameters, and a defer_loading flag) crates/managed-agents/src/http/protocol.rs:129-139. The executor merges them into AgentConfig.frontend_tools crates/executor/src/managed_agents/service.rs:109-112, appends their definitions to every model request (frontend_tools::definitions), and rejects empty names or names that collide with runtime tools crates/executor/src/frontend_tools.rs:39-52.

Execution is a durable rendezvous on the thread's event log:

  1. The model's tool_requested event is committed first. frontend_tools::execute asserts that exactly this request is already persisted ("client tool call must be persisted before execution") crates/executor/src/frontend_tools.rs:151-170.
  2. It scans the turn's events for a matching agent_runtime.frontend_tool_response; if none, it subscribes with watch_events from the last seen event and blocks. A TurnEnded while waiting is an error crates/executor/src/frontend_tools.rs:171-192.
  3. The application posts {session_id, tool_call_id, result} to .../turn/TURN_ID/frontend-tool-result crates/managed-agents/src/http/protocol.rs:279-284. LocalProvider::frontend_tool_result requires the caller to be the one who started the turn, takes a provider-wide lock, and calls frontend_tools::respond crates/executor/src/provider.rs:331-364.
  4. respond verifies the call is still pending, belongs to a declared client tool in the saved TurnWork, and appends the response event. Re-posting an identical result returns the existing event id; a different result is rejected ("client tool already has a different result") crates/executor/src/frontend_tools.rs:194-250.

The result is frontend_tool_success {output, model_input?} or frontend_tool_error {output, error{type: execution_error|user_rejected|aborted, message}} crates/managed-agents/src/http/protocol.rs:174-200. Errors become {ok:false, output, error} tool results. The optional model_input (text or base64 data-URL images) is fed to the model as an extra user message alongside the tool result: history materialization re-injects it as a user message when rebuilding the prompt crates/executor/src/message_history.rs:24 (RLM does so inline via model_input_for_call); the Claude bridge converts it to MCP content blocks exoharness/typescript/harness/client-tools.ts:31-69.

Client tools hide inside the "MCP" and "runtime" plumbing

For TS harnesses the client tool is just another entry in context.tools, so the Responses loop registers it as a pass-through authorization: "runtime" instance; its execute calls context.executeTool, which in Rust ends up in frontend_tools::execute and parks until the HTTP caller answers crates/executor/src/typescript_runtime.rs:204-219. For Claude Code, client and Exo runtime tools are exposed to the Claude Agent SDK as one in-process MCP server named exo_runtime, with synthetic call ids claude-runtime-<uuid> and hand-written tool_requested / tool_result events exoharness/typescript/harness/claude-runtime-tools.ts:22-100. That server name is reserved: a user MCP server with that name is rejected.

Parsed but not wired

defer_loading defaults to true in the wire type but nothing outside tests reads it. auto_approve_tools is accepted by the HTTP type but the local runtime rejects any request that sets it crates/executor/src/managed_agents/service.rs:93-104. The docs also list "tool declarations in agent frontmatter" as planned website/docs-src/agent-definition.md:514-515; today tools: in frontmatter is a list of module paths (Vec<PathBuf>) crates/managed-agents/src/lib.rs:57.

MCP servers

Declaration

MCP servers are declared in the agent definition as a tagged enum: type: url (explicit URL) or type: provider (URL resolved at runtime by a McpServerResolver; the default resolver refuses) crates/managed-agents/src/mcp.rs:8-30, crates/managed-agents/src/mcp.rs:79-108. Each has allowed_tools (allow-list), blocked_tools, and flattened per-server permission fields. Names are restricted to [A-Za-z0-9_-] and unique; URLs must be http(s) with no userinfo or fragment crates/mcp/src/config.rs:37-72.

Connecting

crates/mcp is a thin layer over the rmcp crate. There is exactly one transport: streamable HTTP (StreamableHttpClientTransport) crates/mcp/src/native.rs:87-99. No stdio servers, no SSE-only legacy transport. Redirects are disabled outright (Policy::none()), connect timeout 30 s, initialization 60 s, tool discovery 60 s, each tool call 300 s crates/mcp/src/native.rs:57-106. McpConnector is a trait so hosts can substitute their own HTTP clients (DNS pinning, destination policy) via connect_with_http_clients crates/mcp/src/client.rs:178-196.

McpToolSet::connect_servers connects every server concurrently, lists tools, fails if an allowed_tools/blocked_tools entry names a tool the server does not have, filters, and refuses duplicate exposed names across servers crates/mcp/src/client.rs:214-283. On the Exo side connect_mcp wraps this: it loads the vault selection, resolves the agent's servers, builds VaultMcpCredentials, and connects crates/executor/src/managed_mcp.rs:14-60. Callers whose principal starts with adapter- (Slack etc.) use connect_available, which silently omits servers that need auth when no credential was selected, but still errors if a supplied credential is rejected crates/mcp/src/client.rs:167-176.

Two thread-level guards pin the MCP world once a thread starts. validate_configuration errors with "MCP configuration changed; start a new thread" if the agent's server list differs from what the thread connected with crates/executor/src/managed_mcp.rs:63-71. And configure_thread appends a custom mcp_tools event holding the tool inventory (only when it changed from the last such event), making the exposed tool set part of the durable history crates/executor/src/managed_mcp.rs:75-107.

Tool-name namespacing

The hash input is server \0 tool, so two distinct pairs cannot collide by concatenation (a__b+c vs a+b__c), which is also why a server name containing __ always takes the hashed path. The model sees the exposed name and a description with an appended line MCP server: S; tool: T crates/executor/src/mcp.rs:24-37. Native harnesses translate their own naming back: Claude's mcp__server__tool maps to exposedName, other Claude tools become claude.<Name>; Codex built-in MCP resource tools become codex.<name> exoharness/typescript/harness/native-mcp.ts:3-31. Policies are keyed by those exact strings: a test shows a policy key Bash fails validation against an inventory that names the tool claude.Bash crates/managed-agents/src/permissions.rs:87-95.

Credentials and OAuth

Credentials never appear in the agent definition. They are resolved from vaults by URL match:

  1. At first thread start VaultSelection::from_vaults walks the thread's vaults (last vault wins first) and, for each MCP server URL, finds secrets whose credential policy permits that URL as a destination, preferring secrets whose allow-list names it exactly. Two equally specific matches in one vault is an error: "narrow their policies to select one credential" crates/managed-agents/src/vaults.rs:49-86.
  2. The binding (server_name, destination, optional SecretReference) is saved as a thread artifact (managed-agents/vault[/principal].json). It can never change afterwards: "cannot change an existing thread's vault selection" crates/managed-agents/src/vaults.rs:13-19, crates/managed-agents/src/vaults.rs:123-139.
  3. On every HTTP request the transport asks McpCredentialProvider::resolve for a bearer token (CredentialClient overrides rmcp's own auth header) crates/mcp/src/auth.rs:40-88. If the server answers 401 / AuthRequired, send_authenticated calls refresh and retries once, but only if the refreshed token differs crates/mcp/src/client.rs:113-136.
  4. VaultMcpCredentials::credential tags each token with vault:secret:revision. On refresh it only refreshes the vault secret if the rejected token is still the current revision (so concurrent callers do not double-refresh), and returns None for non-refreshable secrets crates/managed-agents/src/vaults.rs:219-267.
  5. Authentication failures are annotated with an actionable message naming the server, URL, selected vaults and secret ids crates/managed-agents/src/vaults.rs:176-218.

OAuth acquisition is not in the MCP crate. It happens in the CLI (exo vault ... --url MCP_URL): prepare_mcp_login uses rmcp's AuthorizationManager for standard discovery, falling back to exo_mcp::probe_auth_challenge (an unauthenticated connect that captures the WWW-Authenticate challenge) crates/cli/src/vaults/login.rs:162-187, crates/mcp/src/native.rs:108-126. The browser flow lives in crates/cli/src/oauth.rs with a 300 s window; the resulting token response is stored with an OAuthRefresh record (token endpoint, client id/secret, scopes, resource) so the vault can refresh it later crates/cli/src/vaults/login.rs:189-240. A GitHub-style device flow and token import (--token-env) exist as alternatives.

Idea worth stealing: credential selection is pinned and destination-checked per thread

Instead of resolving a secret at call time by name, Exo resolves it once at thread start against the server's URL, stores the (server, URL, secret) triple, and on every later start checks that the agent's MCP destinations still match exactly; a rotated URL or edited server list fails with "start a new thread" crates/managed-agents/src/vaults.rs:88-107. Token rotation and revocation still work because only the secret reference is pinned, and the revision is looked up per request.

Permissions and approvals

The policy model

There are exactly two policies: always_allow and always_ask (deny_unknown_fields, so {"type":"auto"} or extra keys fail to parse) crates/managed-agents/src/permissions.rs:5-16. They are configured in agent frontmatter as top-level permission_policy, per-tool tool_policies, and per-MCP-server blocks. Resolution differs by tool kind:

The global permission_policy does not apply to MCP tools

Because for_mcp_tool never consults self.permission_policy, setting the agent default to always_allow still leaves every MCP tool at always_ask unless the MCP server block (or a tool-specific entry) says otherwise. The test builtin_tools_default_to_allow_and_mcp_tools_default_to_ask pins this crates/managed-agents/src/permissions.rs:136-153, and the user docs state it website/docs-src/agent-definition.md:96. Per-tool MCP keys may use either the exposed name (top-level tool_policies) or the server's raw tool name (inside the server block). prepare_conversation rejects policies naming unknown servers or tools crates/executor/src/mcp.rs:99-125.

Not every harness can honor every policy. The TS runner calls validateToolPolicies(..., nativeToolApprovals=false) for any harness that does not declare nativeToolApprovals: true; that variant throws on a default always_ask ("cannot enforce always_ask for all native tools") and on policies naming unknown tools exoharness/typescript/harness/runner.ts:302-312, exoharness/typescript/harness/index.ts:450-466.

The gate: permissions::authorize

Every execution path (Basic, TypeScript runtime requests, RLM) calls the same function with the resolved policy. Approvals are plain events on the turn, not in-memory state:

  • agent_runtime.approval_requested with {approval_id (UUIDv7), tool_call_id?, round?, request} crates/executor/src/permissions.rs:14-25
  • agent_runtime.approval_response with {approval_id, approved, allowed_tool_name?} crates/executor/src/permissions.rs:27-32

Who can approve. A client posts {session_id, approval_id, approved, allow_for_tool} to .../turn/TURN_ID/approval-response crates/managed-agents/src/http/protocol.rs:270-277. The provider requires that the authenticated caller be the principal recorded on the turn's TurnStarted event, that the turn is currently active in this process, and serializes responses behind a mutex crates/executor/src/provider.rs:283-326, crates/executor/src/permissions.rs:288-307. respond refuses an approval id that is not currently pending, and refuses "denied but allow for tool" crates/executor/src/permissions.rs:94-122. The REPL / TUI turns ApprovalRequested stream events into y / n / a prompts (a = allow_for_tool) crates/cli/src/tui_app.rs:949-956; the managed-adapter design specifies Slack approvals as buttons that identify the pending approval, turn and session, only the author of the originating message may press them, and a chat "yes" must never count docs/managed-adapters.md:398-403.

Scope of "allow for tool". The grant is the response event's allowed_tool_name, matched against any later request of that function name within the same session (not the turn, not the thread), regardless of arguments.

Persistence and resume across disconnects

Because the request/response pair lives in the event log, the HTTP client can disconnect, the process can restart, and the decision still lands:

  1. The waiting authorize call subscribes to the thread's event stream. A late approval_response from any connection resolves it. A reconnecting client re-derives pending approvals with pending_from_events (requests minus responses; a TurnEnded clears all) crates/executor/src/permissions.rs:69-92.
  2. If the process dies mid-wait, recovery (load_turn_progress) rereads the turn: which round was committed (exo.basic.tool_round), which tool calls have no result, and whether the first unresolved call has a matching saved approval (same tool_call_id, round and identical request) crates/executor/src/basic.rs:319-427.
  3. That sets resume_first_approval; authorize then runs in resume mode: it does not short-circuit on always_allow, requires the saved request to exist ("cannot safely resume tool call without its pending approval"), checks the request is byte-equal, and either returns the saved decision or re-emits ApprovalRequested and waits again crates/executor/src/permissions.rs:137-197.
  4. Remaining calls in the saved round are executed in order; the model is not re-called for that round.

Resumable approvals exist only for the Basic harness

Resume requires tool_call_id and round to be passed into authorize, and only basic.rs does that. The TypeScript runtime request path passes None, None, false crates/executor/src/typescript_runtime.rs:182-193 and RLM does the same. So can_resume_pending_approval is true only for AgentHarnessKind::Basic crates/executor/src/native/managed_executor.rs:132-134. For a TS harness, a pending approval in the log is orphaned after a restart: the replayed call creates a new approval (new id), after prior session-level "allow for tool" grants are checked.

Unresolved tool-call reconciliation

The problem. A turn is durable but a tool call is not transactional. If the host dies between tool_requested and tool_result, the call may or may not have had its side effect (a shell command, a ticket update). Blindly re-executing is unsafe; silently dropping it leaves the model's history inconsistent.

The rule. On recovery an unresolved call (tool_requested with no tool_result) is only tolerated if Exo can prove re-entering it is safe. Otherwise the turn fails with "cannot safely resume unresolved tool call". Each executor advertises capabilities crates/executor/src/harness_executor.rs:92-100:

can_resume_pending_approvalReplaying a call that is parked at an unanswered approval is safe (nothing has executed yet)Basic only crates/executor/src/native/managed_executor.rs:132

Two kinds of unresolved call are always considered safe: one parked at an unanswered approval (nothing ran) and a client tool (re-awaiting the same response event is idempotent). This check is skipped (!reconciles_tools) for executors that reconcile themselves crates/executor/src/harness_adapter.rs:191-195. For those, the TS runner double-checks: on init.recovering it requires the harness to export resumeTurn, and unless it declared reconcileUnresolvedToolCalls it scans the turn for requested-minus-resulted ids and refuses exoharness/typescript/harness/runner.ts:251-273, exoharness/typescript/harness/runner.ts:313-327.

Reconciliation itself is harness-specific. Codex's recovery compares unresolved Exo tool ids against the native Codex thread snapshot and refuses if a matching item is missing or still inProgress (assertNativeToolSafety); Claude Code and Pi currently fail an interrupted turn outright website/docs-src/architecture/harnesses.md:96-100. Suspension timing follows the same split: a reconciling harness can be suspended immediately, others wait for a "suspension boundary" between tool calls crates/executor/src/harness_adapter.rs:244-256. Details of each adapter are on Native harnesses.

Idea worth stealing: recovery by log projection, with fail-closed default

No separate "in-flight" table exists. Recovery is a pure function of the event log (tool_requested, tool_result, round marker, approval events) and the default answer to anything ambiguous is to fail the turn with an explanatory error. Capabilities are opt-in per harness, so a new harness is safe by default.

Skills

Skills follow the agentskills.io format: a SKILL.md with YAML frontmatter (name, description) and a markdown body, plus optional bundled text files. They are implemented as five TS built-in tools plus a prompt-injection helper in skill-tools.ts, with three-stage progressive disclosure:

  1. Catalog every turn. skillsInstruction(context) reads skills/index.json and returns a developer message listing - name: description with the standing order to call use_skill before a matching task; null if none installed exoharness/typescript/harness/skill-tools.ts:507-535.
  2. Body on demand. use_skill(name) returns {name, description, skillMd, files: [paths]} (paths only).
  3. Files on demand. read_skill_file(name, path) returns one bundled file.

Idea worth stealing: publish-after-write and degrade-on-read

install_skill writes the content artifact before publishing the index entry, so a listed skill always has readable content exoharness/typescript/harness/skill-tools.ts:299-304. On the read side, prompt assembly runs every model round, so a corrupt index does not throw; it emits a developer message telling the model skills are temporarily unavailable, while the write path still throws so nothing overwrites the corrupt artifact exoharness/typescript/harness/skill-tools.ts:507-528.

Skills are a library, not a platform feature

No default harness calls registerSkillTools or skillsInstruction; the only users are the self-improving-agent example (examples/self-improving-agent/harness.ts:130, profiles/practical.ts:32). "Skills in agent definitions" is an unchecked item in the planned list website/docs-src/agent-definition.md:533. Install is read-modify-write on the index with no compare-and-swap: concurrent installs from two conversations can lose an update (an in-code TODO) exoharness/typescript/harness/skill-tools.ts:95-98. "Discovery" is therefore only the index artifact; there is no filesystem scan or registry fetch (the design doc lists both as future work).
