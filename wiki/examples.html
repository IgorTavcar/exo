Applied

Examples & custom harnesses

What you can build on Exo, shown through the in-repo examples: a minimal TypeScript harness in about 15 lines, a Game Boy agent, a self-rebuilding long-running assistant (memory, scheduler, guardian), a recursive-language-model harness, and the Harbor eval wrapper that drives all of it.

The examples at a glance

Everything below sits on the same contract (see harnesses.html for the TypeScript harness API and tools-and-mcp.html for tools): a harness module exports defineHarness({ runTurn }); Exo's Rust side owns durable state (events, artifacts, sandboxes, secrets); your module owns prompt assembly, the tool registry, and when a turn ends. The examples differ only in how much of the loop they take over.

1. Writing a minimal harness

The smallest harness

The whole of exoharness/examples/typescript/basic-harness.ts:5-12 is a call into the stock loop. Everything interesting is in what runResponsesHarnessTurn does for you:

nativeToolApprovals: true declares that this harness routes every tool call through authorizeTool. When a harness does not set it to true, the runner calls validateToolPolicies(..., false) before the turn, which throws if the conversation uses the always_ask permission policy (exoharness/typescript/harness/runner.ts:302-310, exoharness/typescript/harness/index.ts:450-467). The Codex preset sets it to false (exoharness/typescript/codex/harness.ts:353).

What the stock loop does each round

runResponsesHarnessTurn (exoharness/typescript/model-runtime/turn-loop.ts:36-54) resolves the model and credential, builds a Responses runtime, and runs runResponsesTurnLoop. The loop body is the thing to internalize, because both hooks are called inside it, once per model round:

After the model call it appends the response events, and if there are tool calls it executes them through tools.executePending inside runtime.traceToolCall and loops (exoharness/typescript/model-runtime/turn-loop.ts:186-207). Three consequences that every example below exploits:

  • Dynamic tools for free. Because the registry is rebuilt per round, a tool installed by manage_tool in round N is callable in round N+1 of the same turn (exoharness/typescript/harness/tool-modules.ts:114 reads the installed-tools registry on every build).
  • State injection for free. Because instructions is re-run per round, anything you read from artifacts (todo list, memory, a screenshot) is always current and never piles up in history.
  • Tool names are unique. HarnessToolRegistry.register throws tool is already registered: <name> on a duplicate (exoharness/typescript/harness/tools.ts:63).

Surprise: budget exhaustion is silent here, loud elsewhere

The stock loop returns quietly when round > maxToolRoundTrips (exoharness/typescript/model-runtime/turn-loop.ts:114-120), ending the turn with whatever was last written. The RLM harness uses assertRoundBudget, which throws "<label> exceeded the configured round budget" (exoharness/typescript/harness/index.ts:482-496), and so does the Rust RLM executor (crates/executor/src/native/rlm.rs:84-89). Same knob, two failure semantics.

Hook 1 and 2: sysmon-harness

exoharness/examples/typescript/sysmon-harness.ts is the tutorial's "custom harness". It registers the built-in shell plus one defineTool tool, and its instructions hook appends live host memory utilization measured fresh each round (exoharness/examples/typescript/sysmon-harness.ts:61-75). A tool is a plain object with four parts: a definition (name, description, strict JSON schema), initializationParameters (schema for config bound at load time), and initialize() returning a handler with execute(args, execution) (exoharness/typescript/harness/tools.ts:41-53). The same shape is used by file-based tool modules with a manifest, e.g. exoharness/examples/typescript/tools/uppercase.ts plus exoharness/examples/typescript/tools/uppercase.manifest.json (initialization values supplied by the manifest), and the unreferenced demo exoharness/examples/typescript/tools/irc.ts that shows a networked integration with typed config.

Stateful tools: coding-agent-harness

exoharness/examples/typescript/coding-agent-harness.ts is the pattern behind the self-improving agent's memory and todo tools, in miniature: a tool writes state to a conversation artifact, and the instructions hook reads it back on every round.

Artifacts are versioned and append-only: readTodos lists every version and picks the highest (exoharness/examples/typescript/coding-agent-harness.ts:36-47). The tutorial text (website/docs-src/tutorials/custom-coding-agent.md) mirrors this code closely; two small drifts: the tutorial's final defineHarness omits nativeToolApprovals: true that the real file sets (code copied from the tutorial would therefore be rejected under always_ask) (exoharness/examples/typescript/coding-agent-harness.ts:168-170), and the file's readTodos has no version argument whereas the self-improving agent's equivalents pass one.

Sidecar pattern: the Game Boy agent

The Game Boy example (exoharness/examples/gameboy-agent/README.md, walkthrough in website/docs-src/tutorials/game-emulator-integration.md) wires an agent to an external stateful system in four parts: a headless PyBoy emulator behind HTTP (exoharness/examples/gameboy-agent/emulator/server.py:3-19: /frame, /press, /tick, /checkpoint/save|load, /view), a typed client, five tools (press_buttons, wait, save_checkpoint, load_checkpoint, list_checkpoints; exoharness/examples/gameboy-agent/agent/game-tools.ts:14-175), and a harness. The game only advances when asked (PyBoy(..., window="null"), ticked by the request handlers; exoharness/examples/gameboy-agent/emulator/server.py:89-106), so the world is turn-based and deterministic between tool calls.

Idea worth stealing: observation in instructions, results in tools

Tool results return only text (RAM-decoded state); the screenshot comes from the instructions hook (exoharness/examples/gameboy-agent/agent/game-tools.ts:1-3). That keeps the durable event log free of stale images while the model always acts on the current frame. Prompt text for this agent is covered in prompts.html; the interesting content there is that the RAM block is declared ground truth but meaningless during the intro (exoharness/examples/gameboy-agent/agent/harness.ts:45-52).

The agent definition is a markdown file with front matter (exoharness/examples/gameboy-agent/agent.md:1-8): harness: ./agent/harness.ts selects the TypeScript module, max_tool_round_trips: 20 bounds each turn, and each exo thread send is one turn. The tutorial's closing note says the evaluation this was extracted from added a self-rewritten playbook, memory files and an install_tool meta-tool, and the agent authored 14 tools and 2 skills (website/docs-src/tutorials/game-emulator-integration.md:367-375); that machinery is not in the repo example, but the self-improving agent below is the in-repo analogue.

2. The self-improving agent

examples/self-improving-agent/README.md describes "a persistent agent ... helpful wherever there is a task to do from a computer". Architecturally it is a TypeScript harness (examples/self-improving-agent/harness.ts, 144 lines), a set of tools, one Rust crate (the scheduler runner), and a pair of bash supervisors. The design argument is in examples/self-improving-agent/docs/RSI.md: recursion needs runtime support (state carried forward safely), which Exo provides as an append-only event log, lineage across clones, sandbox snapshots/rewind, and an exoharness core the agent cannot modify under default policy.

Harness assembly and profiles

harness.ts exports the default harness and its two hooks (registerExoTools, exoInstructions) so other harnesses can compose on top of it, as the comment says (examples/self-improving-agent/harness.ts:30-55). The Harbor eval does exactly this reuse by pointing at it (eval/harbor/src/exo_harbor/conventions.py:4).

Prompt assembly (examples/self-improving-agent/harness.ts:57-135) is a list of developer messages: basicHarnessInstructions, the identity prompt examples/self-improving-agent/prompts/me.md, the agent's display name, a capability overview, the self-map pointer, an optional local profile (examples/self-improving-agent/harness.ts:137-144, default .exo/exo-profile.md, git-ignored), then three dynamic blocks appended last: memoryInstruction, todoInstruction, skillsInstruction. The prompt wording itself is in prompts.html.

Surprise: the "bootstrap" recovery profile does not isolate import-time breakage

Profiles are chosen at runtime, but examples/self-improving-agent/profiles/index.ts:1-2 statically imports both profile modules, and examples/self-improving-agent/harness.ts:13-15 statically imports memory-tools and todo-tools. A syntax error the agent introduces in any of those files would fail module load regardless of EXO_PROFILE. Bootstrap protects against a bad tool set, not a bad tool file. This is my reading of the import graph, not something the docs claim.

The two-layer tool model: TS definition, Rust execution

The model only sees what the TypeScript registry registers; execution can stay in TypeScript or be delegated to Rust. hostTool is the bridge: its handler just forwards to execution.context.executeTool({ functionName, arguments }) (examples/self-improving-agent/tools/host-tools.ts:23-37), which lands in the match in ExoToolRuntime::execute (crates/executor/src/native/harness_tool.rs:113-194): shell, the four scheduler tools, list_conversation_events, get_sandbox_status, list_sandbox_snapshots, snapshot_sandbox, rewind_sandbox; anything else errors with tool execution is not configured for {other}. A Rust arm without a TS definition is therefore unreachable, and SELF.md says so (examples/self-improving-agent/SELF.md:81-97). The sandbox tools (examples/self-improving-agent/tools/sandbox-tools.ts) and list_conversation_events (examples/self-improving-agent/tools/introspection-tools.ts) are pure definitions; the logic is Rust. See sandboxes.html for what snapshot/rewind do underneath.

Doc vs code: "ambiguous" is actually "the installed tool loses"

SELF.md rule 4 says an agent-installed tool with the same name as a Rust-backed one makes "calls ambiguous" (examples/self-improving-agent/SELF.md:96-97). In code, register throws tool is already registered (exoharness/typescript/harness/tools.ts:63). Installed tools are registered last (examples/self-improving-agent/harness.ts:49-54) inside a try/catch that logs skipping broken installed tool and moves on (exoharness/typescript/harness/tool-modules.ts:114-131), so a colliding installed tool is dropped, not ambiguous. Install-time collision checking is also documented (examples/self-improving-agent/docs/tools-and-adapters.md:40-49).

Memory design

examples/self-improving-agent/tools/memory-tools.ts is a deliberately tiny memory: one JSON artifact memory/exo-memory.json on the agent handle (so it spans every conversation), entries {id, text, createdAt}, capped at 200 entries and 600 characters each (examples/self-improving-agent/tools/memory-tools.ts:19-22). Two tools, remember(text) and forget(id); the whole store is injected back as a developer message on every round, with ids visible so the model can forget them. examples/self-improving-agent/docs/SELF-CONTROL.md:83-93 states the choice outright: no embeddings or retrieval, because for short facts "always injecting the whole store is simpler and easier to audit"; the storage layer could stay if the read path later moves to query-time recall.

Related stores: todowrite (examples/self-improving-agent/tools/todo-tools.ts) is the same pattern but conversation-scoped and tolerant (a corrupt list is treated as empty, because it is "fully regenerable", examples/self-improving-agent/tools/todo-tools.ts:60-66), and only injected while at least one item is pending or in progress (examples/self-improving-agent/tools/todo-tools.ts:161-176). Skills (install_skill, use_skill, ...) store names and descriptions in agent artifacts and inject only the names each turn, loading bodies on demand (examples/self-improving-agent/README.md:168-182; design in exoharness/docs/design/skills.md).

Idea worth stealing: choose the failure mode per store by regenerability

Memory (not regenerable) fails closed on writes and loud-but-alive on reads; todos (regenerable) silently reset. Both avoid the worst case, a corrupt artifact that bricks prompt assembly "in every conversation" (examples/self-improving-agent/tools/memory-tools.ts:197-202).

Known limitation: read-modify-write without compare-and-swap

Agent-scoped memory is shared across concurrently running conversations, and remember/forget read the latest version then write a whole new one; the code carries a TODO(storage-rework) admitting a lost update is possible (examples/self-improving-agent/tools/memory-tools.ts:71-76). Each write also adds a new artifact version and the read path lists all artifact versions then filters client-side (examples/self-improving-agent/tools/memory-tools.ts:220-245), on every model round.

The scheduler

Scheduling is two halves. The model-facing half is four tool definitions that delegate to Rust (examples/self-improving-agent/tools/scheduler-tools.ts:39-219): schedule_sandbox_task (name, @every 10m / */N * * * * / @at <rfc3339>, missed policy, argv command, sandboxMode, optional setupCommand, reportPrompt, maxOutputBytes), list_scheduled_tasks, cancel_scheduled_task (disable, keep history) and delete_scheduled_task. The host half is the exo-scheduler-runner binary, an "example-local" crate (examples/self-improving-agent/scheduler-runner/src/main.rs:16-18) that builds a full Runtime with LocalProvider::typescript (examples/self-improving-agent/scheduler-runner/src/main.rs:170-196) and loops over run_due_tasks; the logic lives in crates/executor.

Semantics worth knowing, all in the executor:

  • Leases. claim_due_tasks stamps a lease (DEFAULT_TASK_LEASE_MS = 10 min) on up to limit due tasks, so a second runner or a crashed one does not double-fire until it expires (crates/executor/src/native/scheduler_store.rs:89-105, crates/executor/src/native/scheduler_types.rs:10). The runner also takes a pid lockfile exo-scheduler.lock and reclaims it if the recorded pid is dead (examples/self-improving-agent/scheduler-runner/src/main.rs:105-138).
  • Missed fires. MissedPolicy is Skip | Once (default) | All (capped at MAX_MISSED_FIRE_CATCHUP = 100), consulted only when more than one slot behind; fires land on the schedule's grid, not on last-finish time (crates/executor/src/native/scheduler_types.rs:72-90).
  • Sandbox modes. agent (default, shared sticky sandbox), conversation, task_fresh (crates/executor/src/native/scheduler_types.rs:131-138).
  • Result delivery is write-ahead. After a run, the output goes to a conversation artifact scheduled-tasks/<name>/<run>.json, then a pending-fire record is stored before the wakeup is sent, then marked delivered. On startup redeliver_pending_wakes replays unconfirmed ones; delivery is at-least-once, bounded to one repeat by the (task, slot) key (crates/executor/src/native/scheduler_runtime.rs:62-102, crates/executor/src/native/scheduler_runtime.rs:338-358).
  • Orphans. If the owning agent or conversation no longer exists, the task disables itself (crates/executor/src/native/scheduler_runtime.rs:176-181).

Idea worth stealing: record the wakeup before you send it

The in-code comment explains why: the wakeup "is the only thing that tells the conversation this run happened, and nothing retries a machine-sent event" (crates/executor/src/native/scheduler_runtime.rs:338-343). A tiny outbox (put_pending_fire then mark_fire_delivered) turns a silent-loss crash window into a replay.

The guardian and the rebuild/restart dance

The agent cannot restart host services from inside its sandbox, and should not kill its own process mid-turn. The solution is a facade tool plus a detached helper:

  1. Model calls rebuild_and_restart_exo({reason}) (examples/self-improving-agent/tools/guardian-tools.ts:47-75). The tool is "narrow": one fixed operation, the reason is the only argument.
  2. Durable "queued" record first. queueRebuildAndRestart mints a UUID updateId and writes .exo/guardian-updates/<id>.json (status queued, agent and conversation ids and slugs) via tmp-file plus renameSync (examples/self-improving-agent/tools/guardian-tools.ts:88-127, examples/self-improving-agent/tools/guardian-tools.ts:169-173).
  3. Spawn and return. It spawns scripts/deferred-rebuild-and-restart with detached: true, logs to .exo/exo-service-guardian-actions.log, and unref()s, then returns {status: "queued", deferred: true, updateId, pid, outcomePath, ...} immediately (examples/self-improving-agent/tools/guardian-tools.ts:129-167).
  4. Let the turn finish. The script sleeps DEFERRED_RESTART_DELAY_SECONDS = 2 s (examples/self-improving-agent/scripts/deferred-rebuild-and-restart:37), then runs exo-service-guardian restart-all --build.
  5. Build, then stop, then start. build_all runs cargo build -p exo and the scheduler-runner manifest, then writes .exo/exo-control.restart (examples/self-improving-agent/scripts/exo-service-guardian:109-124). restart_services drains the scheduler, SIGTERMs the adapter runner, and relaunches both with nohup (examples/self-improving-agent/scripts/exo-service-guardian:221-257, examples/self-improving-agent/scripts/exo-service-guardian:343-367).
  6. Record the outcome with the new binary. The script maps the guardian exit code to succeeded/failed and calls exo thread complete-rebuild-update using the freshly built target/debug/exo (examples/self-improving-agent/scripts/deferred-rebuild-and-restart:38-73). The CLI finalizes the outcome file first, then appends a rebuild_and_restart_exo custom event to the requesting conversation (crates/cli/src/main.rs:1921-1963, crates/executor/src/native/conversation_events.rs:69-120).
  7. The agent finds out by looking. list_conversation_events includes that event kind in its default set (crates/executor/src/native/conversation_events.rs:27-43). In the path I read, nothing wakes the conversation; the model has to ask.

Idea worth stealing: a failed build leaves the old system running

The guardian runs under set -euo pipefail (examples/self-improving-agent/scripts/exo-service-guardian:2), and restart-all calls build_all before restart_services (examples/self-improving-agent/scripts/exo-service-guardian:500-505). A compile error therefore aborts before anything is stopped, and the deferred script records status: failed with the exit code. The agent breaks its code, the old build keeps serving, and the failure is a durable event it can read next turn.

Graceful drain by marker file

Stopping the scheduler is a protocol, not a signal. The guardian creates .exo/exo-scheduler.restart, waits up to DRAIN_CLAIM_SECONDS (15) for the runner to claim it by deleting it (which it does between passes, after finishing in-flight tasks), then waits up to DRAIN_GRACE_SECONDS (300) for exit. An unclaimed marker (old build, wedged runner) or an overrun falls back to killing the process tree. Adapters get SIGTERM and the same 300 s wait; their durable inbox/outbox covers recovery (examples/self-improving-agent/SELF.md:125-129).

The runner side is four lines: claim_restart_marker is fs::remove_file(...).is_ok(), so removal is the claim (examples/self-improving-agent/scheduler-runner/src/main.rs:155-157); atomic unlink means exactly one claimant. The interactive REPL has its own marker: with exo.sh --control, a loop restarts only the child exo run when .exo/exo-control.restart appears, keeping the terminal open (examples/self-improving-agent/exo.sh:788-844).

Doc vs code: "validate" is just cargo build

The tool description, me.md and SELF-CONTROL all say the tool will "validate and rebuild" (examples/self-improving-agent/tools/guardian-tools.ts:53, examples/self-improving-agent/prompts/me.md:22). The only command run is restart-all --build (examples/self-improving-agent/tools/guardian-tools.ts:108): two cargo builds. No TypeScript type-check, no tests. A broken harness.ts will not fail the rebuild; it fails on the next turn. SELF-CONTROL.md section 8 itself notes that a canary path ("run the changed build against a cloned sandbox") is future work (examples/self-improving-agent/docs/SELF-CONTROL.md:189). Also: a drain grace of 300 s is shorter than the default per-command timeout of 10 min (crates/executor/src/native/scheduler_types.rs:11), so a long task running at restart time can be killed.

What makes the loop "somewhat safe"

Collected from examples/self-improving-agent/docs/SELF-CONTROL.md:16-27 and the code above:

  • State outside the thing you rewrite. The conversation event log, artifacts, scheduler records and secrets live under .exo/the secret backend, not in the sandbox. rewind_sandbox restores files only; history is not erased, so a rewound agent can still read what it already tried (examples/self-improving-agent/docs/SELF-CONTROL.md:78). The state table is at examples/self-improving-agent/docs/SELF-CONTROL.md:54-65.
  • Git as the second log. The repo is mounted into the sandbox at /workspace/exo, edits go through shell, and examples/self-improving-agent/SELF.md is the navigation map the harness points to every turn (examples/self-improving-agent/harness.ts:110-113).
  • Narrow host privilege. The sandboxed model gets one fixed host operation instead of a host shell; the system prompt says "do not manually kill host processes" (examples/self-improving-agent/prompts/me.md:22).
  • Reversible by default. The mutation principles (audit trail, named tools, disable over delete) are stated at examples/self-improving-agent/docs/SELF-CONTROL.md:16-27; cancel_scheduled_task versus delete_scheduled_task is the concrete instance.
  • Extension with validation. manage_tool installs a tool only after staging, loading, initializing and strict-schema checking it; failed installs leave no state (examples/self-improving-agent/docs/tools-and-adapters.md:40-49). Secrets in tool config are referenced as exactly ${ENV_VAR} and resolved from the host at load, never written to the lockfile (examples/self-improving-agent/docs/tools-and-adapters.md:72-77).

Host-side web tools

web_search (Brave if a key is in the vault or BRAVE_API_KEY, else DuckDuckGo HTML) and web_fetch (readability to markdown) run in the harness process on the host, so they work even when the sandbox has networking off (examples/self-improving-agent/tools/web-tools.ts:19-25). Because they are host-side they need their own SSRF guard: private IPv4/IPv6 are blocked, and the check is repeated at socket-connect time through a custom undici lookup to defeat DNS rebinding between preflight and connection (examples/self-improving-agent/tools/web-tools.ts:187-232). This is separate from the sandbox egress proxy covered in egress-and-vaults.html.

3. Recursive language models (RLM)

The idea: instead of putting a long conversation into the model's context, put it in a variable of a JavaScript REPL. The model is told "the prompt string in context is the external environment" and works by writing code that slices it, calling sub-LLMs over chunks, accumulating results in variables, and finally setting globalThis.Final. The long context never enters the root model's window except as a 400-character preview plus whatever print output the model chooses to surface (exoharness/examples/typescript/rlm-harness.ts:540-551). The system prompt text is in prompts.html.

The same design exists twice: as a TypeScript example harness and as a first-class Rust executor selectable with harness: rlm (crates/executor/src/managed_agents/config.rs:149, crates/executor/src/native/constructors.rs:30-35). Both emit the same custom events (rlm_context_initialized, rlm_model_response, rlm_tool_call, rlm_tool_result, rlm_final_answer) and write the final answer as an ordinary messages event.

"Persistent" is an illusion built from JSON round-trips: each call builds a new context seeded from the saved globals, runs the code, and harvests only values that survive isJsonValue (exoharness/examples/typescript/rlm-harness.ts:665-702). Functions, classes and Dates do not persist; strings, numbers, arrays and plain objects do. The root loop then checks repl.finalValue() after every tool call and ends the turn as soon as Final is non-null (exoharness/examples/typescript/rlm-harness.ts:200-203), or when the model replies with no tool calls and either FINAL(...), FINAL_VAR(name) or plain text (exoharness/examples/typescript/rlm-harness.ts:465-492).

So "recursive" here means one level: sub-LLM calls get the agent's base instructions, no tools, and no REPL, hence cannot themselves recurse. Depth comes only from the root model orchestrating many subqueries from code (chunk, map, reduce). subquery_variable is sugar for "read variable, append as Context:" (exoharness/examples/typescript/rlm-harness.ts:382-396).

Example harness vs. crates/executor/src/native/rlm.rs

The Rust executor is a port of the TS example into the native executor family, with the loop at crates/executor/src/native/rlm.rs:43-292, tool dispatch at crates/executor/src/native/rlm.rs:294-340, the subquery at crates/executor/src/native/rlm.rs:357-390, and the REPL in crates/executor/src/native/harness_js_repl.rs. Surprise: the REPL sandboxes differ in what they protect against

The Rust (Boa) REPL has no host objects, but also no execution cap in the code I read: harness_js_repl.rs contains no timeout or loop limit, so an infinite loop in model-written JS would hang that turn. The TS example caps at 2 s but runs in node:vm and injects host closures (print, console, getMessages) into the context (exoharness/examples/typescript/rlm-harness.ts:279-307); Node documents vm as not a security boundary, so "no filesystem access, no network access" in the prompt is a statement about what the model is told, not a verified isolation property. Treat the TS version as an experiment harness.

Idea worth stealing: make the context a variable, not a prompt

The root loop never feeds the transcript to the model as messages (exoharness/examples/typescript/rlm-harness.ts:106-123); it materializes conversation history once (materializeConversationMessages), flattens it to a USER:/ASSISTANT:/TOOL: transcript, and exposes both the string and a structured getMessages(role) view to code. Everything the harness does is logged as custom events, so the RLM's reasoning is fully replayable from the event log.

5. Harbor evals (short)

eval/harbor is a Python package, exo_harbor, that makes an Exo harness a Harbor external agent so it can be scored on Harbor's benchmark catalog (terminal-bench, SWE-bench Lite via a generator script, bundled smoke datasets). ExoSessionPlugin creates one shared agent per job (eval/harbor/src/exo_harbor/plugin.py:19-50); ExoAgent gives every trial a fresh conversation, attaches Harbor's task container to it with exo sandbox attach (Exo borrows it, never stops it), sends the task as one turn, and exports the trajectory (eval/harbor/src/exo_harbor/agent.py:78-135, eval/harbor/README.md:1-25). The default harness module is the self-improving agent (eval/harbor/src/exo_harbor/conventions.py:4); basic is a shell-only control and pi drives the Pi agent in the task container.

Surprise: concurrency is rejected on purpose

With the exo harness, --n-concurrent above 1 raises a ValueError in the plugin because trials share one self-evolving agent: memory, installed tools and source edits from trial N are meant to be visible in trial N+1, and parallel self-edits would race (eval/harbor/src/exo_harbor/plugin.py:33-40). The self-evolution-smoke-test dataset (eval/harbor/datasets/self-evolution-smoke-test: install-tool, reuse-tool, restart-and-observe, timeout-trajectory) checks exactly that persistence. Ordered datasets (task_order.json) exist for continual-learning sequences (eval/harbor/README.md).

What to copy

  • Start from runResponsesHarnessTurn with two hooks; reach for a custom loop only when the loop itself is the idea (RLM).
  • Keep durable agent state in artifacts, and surface it through instructions; choose strict or tolerant failure per store.
  • Give an agent self-modification only through narrow facades whose effects are durable records (guardian-updates/<id>.json plus a conversation event), and put the privileged work in a detached helper that outlives the turn.
  • For restarts, use claim-by-delete marker files with a kill fallback, and outboxes (pending-fire records) for anything that must not be lost across a restart.

For the contracts these examples rely on, see harnesses.html (harness API), tools-and-mcp.html (tools, approvals), sandboxes.html (snapshots, rewind, scopes), and prompts.html (the prompt text the examples inject).
