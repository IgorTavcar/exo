Runtime internals

Codex, Claude Code, Pi & Cursor

How the labs' own agent runtimes are driven from inside Exo's sandboxes while Exo's event log stays the canonical transcript: a JSON-RPC bridge to codex app-server, an Agent SDK whose child process lives in the sandbox, Pi's RPC mode with a tool-bridge extension, and a Cursor SDK worker. Also covers the plain Responses-API turn loop in model-runtime.

The common shape

All four "native" harnesses are ordinary TypeScript harnesses (see Harnesses for the generic contract): a module that default-exports defineHarness({ runTurn, resumeTurn? }). The Rust executor starts a Node runner for the thread, hands it a TurnContext, and the harness module does the rest. What makes these four special is that the model loop is not in the harness: it is a vendor runtime, and the harness's job is to (1) start that runtime inside the conversation's sandbox, (2) feed it history from Exo events, (3) translate whatever it emits back into canonical Exo events, and (4) route its approvals and tool calls through Exo's permission and tool machinery.

The presets codex, claude-code, pi and cursor (alias cursor-sdk) resolve to these modules and pin a default sandbox image per preset.

Codex

Where it runs and how it is driven

Codex is the only harness whose vendor runtime is a long-lived server with a real protocol. The harness never spawns codex on the host: it asks the Rust runtime for a sandbox process (context.startSandboxProcess) and talks JSON to that process's stdin/stdout. Model traffic therefore originates inside the sandbox, goes through the egress proxy, and needs networking: requireCodexSandboxNetworking aborts the turn with a codex_networking_required event otherwise (exoharness/typescript/codex/harness.ts:1459-1483).

  Rust executor              TS runner (Node, host)                    Sandbox
  -------------              ----------------------                    -------
  start_process  <---------  ctx.startSandboxProcess(reuseKey)
  (sandbox proc API)         CodexAppServer  (JSON lines)
        |  stdout events ->   readLoop -> notifications queue
        |  <- stdin writes     write(request | server-request reply)
        v
  sandbox process  ---------------------------------------------->  codex app-server
                                                                      |  model calls --> egress proxy (key substituted)
  event log: codex_*  <--  projectCompletedItem / appendCustomEvent    |  MCP servers (HTTP, bearer from env)
                                                                      |  thread state in $CODEX_HOME

Process lifecycle, step by step:

  1. Command. codexSandboxCommand runs $SHELL -lc with a guard that codex --version equals codex-cli <version> before exec codex app-server --listen stdio://. The expected version comes from exoharness/containers/codex-sandbox/version, which is also what the Dockerfile installs, so a stale image fails fast with "rebuild the Codex sandbox image" (exoharness/typescript/codex/harness.ts:1489-1498, exoharness/examples/typescript/codex-harness.ts:4-9).
  2. Warm cache. Within one runner, WarmResourceCache<CodexWarmSession> keeps the session keyed by a JSON blob of agent id, conversation id, model, reasoning effort, base URL, instructions, MCP servers and the whole sandbox runtime shape (image, mounts, cwd, command) (exoharness/typescript/codex/harness.ts:1567-1582). Change any of those and you get a fresh app-server.
  3. Cross-restart reuse. The key is also passed as reuseKey to the Rust side. Rust records a typescript_sandbox_process_reuse custom event on the conversation the first time it starts a process for a key, and later looks up the newest such event; if that sandbox process is still running it returns reused: true plus the cursor of the last process event so stdout is not replayed from the beginning (crates/executor/src/typescript_runtime.rs:306-396, crates/executor/src/typescript_runtime.rs:397-467).
  4. Attach vs. start. A fresh process goes through CodexAppServer.startInSandbox (sends initialize then initialized, declaring experimentalApi: true); a reused one goes through attachToSandbox, which skips the handshake because it already happened (exoharness/typescript/codex/app-server.ts:125-137, exoharness/typescript/codex/app-server.ts:171-183).
  5. Which thread. The newest completed codex_warm_session event for the same key and sandbox id tells the harness the native thread id. If the process was reused the thread is still loaded; otherwise the id becomes resumeThreadId and thread/resume is tried (exoharness/typescript/codex/harness.ts:937-988).

The protocol client

CodexAppServer is a small JSON-RPC-style client (no jsonrpc field; {method, id, params} per line). It exposes request() with a pending-promise map, notify(), and events(), an async generator over an AsyncQueue of notifications. Notable details:

  • Server requests are answered inline. A message with both id and method is a server-to-client request (an approval prompt, a dynamic tool call). It is pushed to the notification queue (so it is visible in the event stream) and answered by the registered onServerRequest handler. If the handler returns undefined the client falls back to a deny-everything default (exoharness/typescript/codex/app-server.ts:273-296, exoharness/typescript/codex/app-server.ts:469-484).
  • Partial JSON lines. The reader accumulates a line and retries parsing when JSON.parse fails with "Unterminated string" / "Unexpected end of JSON input", since sandbox process output can split a message mid-line (exoharness/typescript/codex/app-server.ts:223-243, exoharness/typescript/codex/app-server.ts:438-457).
  • Echo suppression. Any inbound message with an id and method equal to a still-pending client request is dropped as an echo of our own write (exoharness/typescript/codex/app-server.ts:298-304).
  • Full protocol log. Every message in both directions is numbered and buffered into codex_protocol_message custom events, except */delta notifications, flushed at the end of the turn and in finally (exoharness/typescript/codex/harness.ts:1685-1725).

The thread is created with Exo supplying everything Codex would normally load from its own config: a custom model provider named exo pointing at the agent's base URL with wire_api: "responses", the Exo MCP servers, Exo tools as dynamicTools, and the agent instructions as developerInstructions.

Two things to notice. default_tools_approval_mode: "prompt" is what makes Codex route every MCP call through an elicitation that Exo can intercept (see Approvals). And Codex's own sandboxing is switched off in favour of Exo's: the per-turn sandboxPolicy is { type: "externalSandbox", networkAccess: "restricted" }.

One turn

The sequence in runCodexTurn (exoharness/typescript/codex/harness.ts:398-740):

  1. Require networking; if recovering, fold the unfinished turn's events into a SavedCodexRecovery (below).
  2. Get or start the warm session; set the turn scope (context, protocol buffer, pending MCP calls) on it so the long-lived server's callbacks always talk to the current turn.
  3. Find a thread: reuse the warm one, thread/resume a saved one, or thread/start a new one. A failed resume appends a codex_resume_failed event and falls back to a new thread.
  4. If the thread is new, replayCodexHistory injects the prior Exo conversation (next section). A reused thread skips replay: Codex already holds that state.
  5. Append codex_turn_start_intent, call turn/start, append codex_turn_started carrying the native turn id.
  6. Loop over session.server.events(), drop notifications that do not belong to this thread and turn (notificationBelongsToTurn), and handle each until turn/completed.
  7. Always, in finally: append one usage event if any usage was seen, and flush the protocol log. After success, append codex_warm_session; on error, evict and close the cached session so the next turn starts clean.

Codex items to Exo events

Notifications are folded into the canonical stream in handleCodexNotification, and completed items are projected by projectCompletedItem (exoharness/typescript/codex/harness.ts:1109-1205, exoharness/typescript/codex/harness.ts:1322-1358). Each projected item is followed by a codex_item_projected marker keyed turnId:itemId, which is the idempotency token used on recovery.

Idea worth stealing: a write-ahead "intent" event around a non-idempotent RPC

turn/start cannot be retried blindly: if it ran but the response was lost, a second call would make Codex act twice. The harness appends codex_turn_start_intent before the call and codex_turn_started (with the native turn id) after. On recovery, an intent with no matching start is an unresolvable ambiguity, so the harness fails with "cannot safely resume Codex turn after turn/start was attempted without a saved native turn ID" instead of guessing (exoharness/typescript/codex/harness.ts:223-227; tested at exoharness/examples/typescript/codex-harness.recovery.test.ts:303-312).

Replaying Exo history into a Codex thread

When the harness has to build a thread from scratch (cold start, resume failed, or a changed warm key), the Exo transcript is converted to OpenAI Responses input items with linguaMessagesToResponsesInput (the Lingua message format is the common currency across providers) and injected with the Codex-specific thread/inject_items request. System and developer messages are dropped (instructions are given separately as developerInstructions), and function-call names are sanitised to [a-zA-Z0-9_-], so a dotted Exo name like codex.shell becomes codex_shell in replayed history (exoharness/typescript/codex/replay.ts:20-52).

Large histories are chunked so no single request is huge, but the chunks must not separate a function call from its output. Between chunks the thread is compacted via thread/compact/start and the harness waits for the resulting turn/completed, with a 600 s timeout.

Reasoning items do not survive a replay

The Responses requests Exo builds use store: false, so server-side item ids (rs_, fc_, msg_) would 404 on replay. linguaMessagesToResponsesInput therefore drops reasoning items entirely and strips ids from the rest (exoharness/typescript/model-runtime/responses.ts:996-1013). A Codex thread rebuilt from Exo events has the conversation but not the prior chain of thought; only a warm or resumed native thread keeps it.

Crash recovery and reconnect

Codex is the only harness that exports resumeTurn, and it declares reconcileUnresolvedToolCalls: true. Two layers cooperate:

  • Rust adapter. For a TypeScript harness the executor reports can_reconcile_unresolved_tool_call as true, so on recovering turns it does not run its own check that unresolved tool calls are safe to resume (crates/executor/src/native/typescript.rs:72-74, crates/executor/src/harness_adapter.rs:189-196). It delegates the judgment to the harness.
  • Runner. init.recovering routes to harness.resumeTurn, or fails if there is none (below).

savedCodexRecovery rebuilds the state by paging backwards through only the unfinished turn's events (page size 1000, stopping at turn_started), then folding them chronologically into: the last native thread/turn id, the set of already-projected items, tool calls with no result yet, and whether an approval request lacks a response (exoharness/typescript/codex/harness.ts:118-233).

The last row is the heart of the safety logic. The snapshot is only trusted if its item history is complete (itemsView === "full"), and tool safety is a pure function:

"Reconnect" means the old approval is gone, not the old turn

A live Codex turn blocked on an approval holds its server request open on the connection that is now dead. A new connection will never receive it, and waiting would hang forever. So the design is: reattach only when the native turn is between tool calls (or finished), and fail loudly otherwise (exoharness/examples/typescript/codex-harness.recovery.test.ts:314-336). Separately, codex_item_projected markers make projection idempotent: a snapshot read after a crash re-emits only items not already in the log (exoharness/typescript/codex/harness.ts:1223-1269).

On the Rust side, a suspended or interrupted turn for a TypeScript harness just tears down the cached runner (cancel_turn removes it and shuts it down). That does not touch the sandbox process: only an explicit CloseSandboxProcess request from the harness cancels it, and the Codex harness sends that only on its error path (codexSessions.delete(..., close)). So after a clean runner restart the app-server is still running and reusable_sandbox_process finds it again (crates/executor/src/native/typescript.rs:80-92, crates/executor/src/harness_adapter.rs:268-290, crates/executor/src/typescript_runtime.rs:270-291). The same Codex harness also runs unmodified on Cloudflare Workers, where runtime-io.ts calls resumeTurn when the payload says recovering (exoharness/cloudflare/src/runtime-io.ts:449-458).

Approvals and tool bridging

With approvalPolicy: "on-request" and an external sandbox, Codex asks the client whenever it wants to do something that needs permission. The registered onServerRequest handler (exoharness/typescript/codex/harness.ts:1019-1048) maps each request type:

Codex server requestExo handling
item/commandExecution/requestApprovalcontext.authorizeTool({functionName: "codex.shell", arguments: {command, cwd}}); success → accept, any throw → decline
mcpServer/elicitation/requestauthorizeMcpElicitation (below)
item/tool/callExo dynamic tool: append tool_requested, run context.executeTool, append tool_result, answer with contentItems (text, or images when a client tool supplies model input)
item/fileChange/requestApproval, item/permissions/requestApproval, item/tool/requestUserInput, anything elseHandler returns undefined, so the client default applies: decline / empty permissions / cancel

Which Exo tools become dynamicTools? buildCodexDynamicTools filters out any Exo tool already exposed through an MCP server (those go to Codex natively), leaving built-ins and client tools (exoharness/typescript/codex/harness.ts:1444-1457). Native MCP servers get their credentials the same way the model does: the Rust side adds an egress credential binding for each MCP secret, but only for the codex and claude-code modules (crates/executor/src/sandbox_policy.rs:47-49, crates/executor/src/sandbox_policy.rs:188-242). The tool registry itself is covered in Tools & MCP.

The interesting problem is MCP approvals. Codex's elicitation request identifies the call only by a human-readable message and its parameters, not by item id. The harness reconstructs the pairing: it tracks every mcpToolCall from item/started into a per-turn map, and matches the elicitation against that map by server name, the exact message string, and deep equality of the arguments.

Because matched calls are deleted from the map, two identical calls approved or denied out of order stay independent (exoharness/typescript/codex/mcp-approval.test.ts:43-127). An unmatched elicitation is declined, so the failure mode is "tool does not run", never "tool runs unapproved". Note the string-match on Codex's prompt wording: it couples Exo to a specific codex release, which is another reason the CLI version is pinned.

Finally, nativeToolApprovals: false is how the Codex harness tells the runner it cannot enforce a blanket always_ask policy over every native Codex tool (file changes, web search). validateToolPolicies(…, false) then rejects an always_ask default with an explanatory error, leaving the user to set per-tool policies explicitly (exoharness/typescript/harness/index.ts:450-467, exoharness/typescript/harness/runner.ts:302-311).

Usage and cost capture

Codex reports tokens but not dollars. For each thread/tokenUsage/updated notification already filtered to the active turn, CodexUsageAccumulator adds the last (single model call) numbers and uses total (thread-lifetime) only as a monotonic de-duplication key.

At the end of the turn (in finally, so a failed turn is still billed) the harness appends one empty-messages event whose usage is built by codexUsageEvent → modelUsageRecord (exoharness/typescript/codex/usage.ts:78-98, exoharness/typescript/codex/harness.ts:726-735). modelUsageRecord takes an explicit cost_usd if the runtime supplied one; otherwise it computes cost from a LiteLLM price table (exoharness/typescript/model-runtime/usage.ts:1-26).

exoharness/typescript/model-runtime/cost.ts is a self-contained port of the Rust cost crate: lookup is an exact match, else the longest key that is a prefix of the model name at a - or : boundary; Anthropic-family and azure_ai entries treat prompt_tokens as excluding cache reads (additive), all others as including them. The table is loaded once from $EXO_LITELLM_PRICES_PATH, else a 24-hour on-disk cache under $EXO_HOME/cache, else a 5-second fetch of LiteLLM's JSON, else a stale cache, else null (cost omitted) (exoharness/typescript/model-runtime/cost.ts:38-96, exoharness/typescript/model-runtime/cost.ts:98-135).

Doc and code disagree on what Codex usage counts

exoharness/docs/coding-agent-harnesses.md:48-50 says usage "counts upstream rawResponse/completed records, including local replay compaction". The code counts thread/tokenUsage/updated deltas for the active turn only, and its comment explains why: resumed app-servers do not emit raw response events. rawResponseItem/completed is used only to reconstruct the prompt for the trace span. Compaction during replay runs in waitForCompaction, which consumes its own notifications and never feeds the accumulator, so replay-compaction tokens appear not to be counted. The rawResponse/completed JSON fixture survives only as test data for the field names (exoharness/typescript/codex/usage.test.ts:2).

Claude Code

The Claude Code harness uses the Claude Agent SDK in a split arrangement. The SDK query() call, the hooks and the tool bridge all run in the harness (runner) process on the host. Only the Claude Code CLI itself runs in the sandbox. The seam is the SDK's spawnClaudeCodeProcess option: SandboxClaudeCodeProcess implements the SDK's SpawnedProcess interface by calling context.startSandboxProcess and pumping stdin/stdout between the SDK's streams and the sandbox process (exoharness/examples/typescript/claude-code-harness.ts:617-750). The binary path is hard-coded to /usr/local/bin/claude-code, the symlink the Dockerfile creates to the native binary shipped by the matching SDK platform package (exoharness/containers/claude-code-sandbox/Dockerfile:19-34).

History and options

  • History. There is no native session (persistSession: false). Each turn the whole Exo conversation, minus system/developer messages, is flattened by messagesToTranscript into a single user message of the form ROLE:\ncontent blocks and sent as the prompt; agent instructions go in systemPrompt (exoharness/examples/typescript/claude-code-harness.ts:152-163, exoharness/examples/typescript/claude-code-harness.ts:515-544, exoharness/typescript/harness/index.ts:774-778).
  • MCP. Exo MCP servers are passed as type: "http" servers with an Authorization: Bearer ${ENV} header whose variable is bound at the egress proxy; strictMcpConfig: true stops Claude from loading any other config; per-server disabledTools become disallowedTools (exoharness/examples/typescript/claude-code-harness.ts:265-298).
  • Exo tools. Tools that are not already MCP-exposed are served by exo_runtime, an in-process SDK MCP server built with createSdkMcpServer. Its CallTool handler mints an id claude-runtime-<uuid> (MCP transport ids are not canonical), appends tool_requested, calls context.executeTool, appends tool_result, and returns MCP content; the name exo_runtime is reserved (exoharness/typescript/harness/claude-runtime-tools.ts:22-101). Because the harness also observes Claude's own tool_use blocks, observedClaudeToolEvents filters out the duplicate events for these runtime tools (exoharness/examples/typescript/claude-code-harness.ts:414-442).
  • Names. claudeToolName maps mcp__<server>__<tool> to the MCP tool's Exo exposedName and everything else to claude.<Name> (exoharness/typescript/harness/native-mcp.ts:22-32).

Approvals

A PreToolUse hook covers every tool Claude is about to run. It denies if the SDK's init message has not yet reported the tool inventory (which is also when validateToolPolicies runs against the real tool names), allows exo_runtime tools unconditionally (the runtime authorises them itself before dispatch), and otherwise calls context.authorizeTool with the mapped name; any throw becomes permissionDecision: "deny" with the error as the reason (exoharness/examples/typescript/claude-code-harness.ts:299-352). That total coverage is why this harness can say nativeToolApprovals: true, which Codex cannot.

Events, cost and guard rails

  • Tool events are projected as they stream (projectAnthropicMessageToolEvents) and traced as "observed" tool spans.
  • Assistant text is stored once. Each assistant message overwrites state.finalText; a single messages event with the last text and the usage is appended after the query ends (exoharness/examples/typescript/claude-code-harness.ts:379-391, exoharness/examples/typescript/claude-code-harness.ts:444-470). Every non-stream SDK message is saved in one claude_sdk_messages custom event.
  • Cost comes from the SDK's final result: usage.input_tokens, output_tokens, cache read/creation counts, and cost_usd: result.total_cost_usd, so no price table is consulted.
  • Guard rails: a 60 s startup timeout if the SDK emits nothing (CLAUDE_STARTUP_TIMEOUT_MS), abort when api_retry reaches attempt 2 (CLAUDE_MAX_API_RETRIES) rather than sit through the SDK's backoff, and the first three stderr chunks of the CLI saved as claude_process_stderr events (exoharness/examples/typescript/claude-code-harness.ts:58-61, exoharness/examples/typescript/claude-code-harness.ts:472-487, exoharness/examples/typescript/claude-code-harness.ts:774-803).

Claude Code's SDK is on the host, its CLI is in the sandbox

It is easy to assume "Claude Code runs in the sandbox" the way Codex does. Only the CLI does; the SDK, its in-process exo_runtime MCP server and its hooks live in the runner. Practical consequence: the host-side dependency is a semver range ("@anthropic-ai/claude-agent-sdk": "^0.2.126", package.json:25) while the image installs the exact version in exoharness/containers/claude-code-sandbox/version (0.2.126), so host SDK and in-sandbox binary can drift apart if the range resolves higher.

Pi

Pi (@earendil-works/pi-coding-agent, pinned in its Dockerfile) is launched in its RPC mode, pi --mode rpc --no-session --no-extensions --provider P --model M, plus a generated extension via --extension. The model name's prefix selects the provider (google/gemini-…); a bare name means OpenAI (exoharness/examples/typescript/pi-harness.ts:122-144). The Rust side maps the same prefix to the env var the egress proxy binds: openai, anthropic or google; any other provider is an error at policy time (crates/executor/src/managed_agents/config.rs:82-96).

The launch command is a sh -c one-liner that reads one line from stdin (the JSON tool list) into $HOME/.pi/exo-<conversation>/tools.json, writes the extension source to exo.mjs, and then execs Pi, which inherits the rest of stdin for RPC (exoharness/examples/typescript/pi-harness.ts:145-157). The harness writes the tool list as that first line, then sends {type: "prompt", message: transcript}.

The tool bridge: RPC over a UI dialog

Pi extensions can register tools and hook tool_call, but have no channel back to Exo. The extension uses the one request/response primitive RPC mode offers, ctx.ui.input(title, placeholder), as a side-channel: the title carries the method and the placeholder carries a JSON payload. Pi emits an extension_ui_request event; the harness reads it, performs the Exo call, and writes an extension_ui_response whose value is the JSON reply.

Pi's built-in tools (read bash edit write grep find ls) are authorised via exo.authorize_tool under the name pi.<tool>; Exo tools registered by the extension are authorised and executed by Exo in one exo.execute_tool hop, which is why the hook skips them. Any other extension_ui_request (select/confirm/editor) is auto-cancelled so Pi never blocks on a UI that does not exist (exoharness/examples/typescript/pi-harness.ts:173-189). As with Claude, nativeToolApprovals: true is valid because every tool passes through a hook.

Events, cost

  • tool_execution_start/_end become tool_requested/tool_result (pi.<name> for built-ins). message_update text deltas stream. Each assistant message_end appends a messages event immediately, with usage; stopReason of error/aborted fails the turn at agent_settled (exoharness/examples/typescript/pi-harness.ts:234-298).
  • Cost: Pi computes dollars itself; usageRecord forwards usage.cost.total as cost_usd. It also normalises token semantics: for non-Anthropic providers prompt_tokens = input + cacheRead + cacheWrite, for Anthropic just input, matching the additive/inclusive split in cost.ts (exoharness/examples/typescript/pi-harness.ts:77-103).
  • Pi gets no native MCP bindings: add_native_mcp_bindings is only applied to the codex and claude-code modules.

The "Warm" worker is not warm for Pi

Pi reuses WarmJsonlSandboxWorker from shared.ts, but starts a fresh sandbox process per turn (no reuseKey) and closes the worker in finally (exoharness/examples/typescript/pi-harness.ts:146-157, exoharness/examples/typescript/pi-harness.ts:301-303). Only Cursor keeps its worker across turns, and then only in runner memory.

Cursor

Cursor is the thinnest integration and the only one that does not use a vendor binary. The harness starts node --import tsx exoharness/typescript/cursor/sandbox-worker.ts in the sandbox; that worker wraps @cursor/sdk and speaks a trivial Exo-defined JSONL protocol: one CursorWorkerRequest line in (prompt, model, cwd, name), a stream of run_started / delta / message events and a final completed or error out (exoharness/typescript/cursor/protocol.ts:3-43, exoharness/typescript/cursor/sandbox-worker.ts:14-74). This is why the Cursor image is different: its Containerfile copies the repository's typescript/ tree and runs pnpm install into /opt/exo so the worker has its dependencies (exoharness/containers/cursor-sdk-sandbox/Containerfile).

  • Session. The in-sandbox CursorSdkSession caches one SDK Agent per (api-key-present, cwd, model, name) and reuses it across requests, with Cursor's own sandbox and setting sources disabled (sandboxOptions: {enabled: false}, settingSources: []) so Exo's sandbox is the only boundary (exoharness/typescript/cursor/sdk.ts:31-80, exoharness/typescript/cursor/sdk.ts:112-134). On the host the worker handle is cached in module-level memory, keyed by agent/conversation/model/cwd/command (exoharness/examples/typescript/cursor-sdk-harness.ts:61, exoharness/examples/typescript/cursor-sdk-harness.ts:594-605).
  • Prompt. Even with a warm SDK agent, each prompt is rebuilt from scratch: a fixed preamble, the full prior transcript from Exo events and the current input (exoharness/examples/typescript/cursor-sdk-harness.ts:459-473).
  • Events. Only SDK tool_call messages are projected into tool_requested/tool_result (named cursor.<name>); the final assistant text becomes one messages event; raw SDK messages (minus assistant/thinking) go to one cursor_sdk_messages event (exoharness/examples/typescript/cursor-sdk-harness.ts:318-358, exoharness/examples/typescript/cursor-sdk-harness.ts:405-447).
  • No Exo tools, no MCP, no approvals, no cost. validateToolPolicies(context, [], false) declares an empty tool set, and the trace metrics only carry time-to-first-token and duration (exoharness/examples/typescript/cursor-sdk-harness.ts:65-71, exoharness/examples/typescript/cursor-sdk-harness.ts:549-561).

Cursor bypasses the credential-substitution proxy

For Codex, Claude Code and Pi the Rust side binds a vault secret to an env var (sandbox_model_credential_variable) and the sandbox never holds the real key. Cursor has no entry there. Its harness calls resolveModel, which resolves the secret in the runner, then copies the plaintext into the sandbox env: env.CURSOR_API_KEY = modelBinding.apiKey (exoharness/examples/typescript/cursor-sdk-harness.ts:67, exoharness/examples/typescript/cursor-sdk-harness.ts:571-592, exoharness/typescript/model-runtime/shared.ts:243-284, crates/executor/src/managed_agents/config.rs:71-99). Its image is also the only one not built by the publish workflow or pinned by digest. See Egress & vaults for what the other three get.

Why Claude Code, Pi and Cursor fail interrupted turns

The runner enforces resumability per harness. On a turn marked recovering it requires resumeTurn, and, unless the harness declares reconcileUnresolvedToolCalls, it also refuses to resume while any tool call lacks a result:

The reasons the other three do not implement it are structural, not an oversight in the gate:

  • No durable native state to reattach to. Claude runs with persistSession: false and a fresh child per turn; Pi with --no-session and a fresh process per turn (no reuseKey); Cursor's agent and worker live in runner/sandbox memory only. Nothing like Codex's persisted thread plus reusable process exists to be found after a restart.
  • The vendor loop owns tool execution and its outcome. After a crash, a Claude or Pi tool call in flight may or may not have run (shell, file writes). Exo has the tool_requested event but no way to ask the vendor runtime what happened, whereas Codex exposes thread/read with per-item status.
  • Single-shot persistence. Claude stores its assistant text only after the query finishes, and the transport is the SDK's private stdio protocol, so even the partial transcript of an interrupted turn is mostly absent from the log.

The failure is a TypeScript-layer decision, not a Rust one: TypeScriptExecutor::can_reconcile_unresolved_tool_call returns true for every TypeScript harness (crates/executor/src/native/typescript.rs:72-74), so the Rust adapter happily delegates and the runner is what says no. The product docs list safe recovery for Claude Code and Pi as an open TODO (website/docs-src/agent-definition.md:530-531); Cursor is not mentioned there but behaves the same.

Rust says "yes, I can reconcile", TypeScript says "no, I can't"

The capability flag on the Rust executor is per executor kind (any config.typescript.is_some()), not per harness module. The real per-harness truth is the presence of resumeTurn in the module, discovered only when the runner is already running the recovering turn. Adding recovery to Claude/Pi means writing a resumeTurn; no Rust change is required.

The model-runtime turn loop

Everything above wraps a vendor agent. The basic-style TypeScript harnesses (for example the tutorial exoharness/examples/typescript/coding-agent-harness.ts) instead use exoharness/typescript/model-runtime/turn-loop.ts, where Exo owns the model loop. runResponsesHarnessTurn loads the price table, resolves the model credential, picks a runtime, and delegates to runResponsesTurnLoop (exoharness/typescript/model-runtime/turn-loop.ts:36-52).

The loop

  1. Per round, rebuild the tool registry (built-ins, configured tool modules, installed agent tools, then every context.tools definition registered with authorization: "runtime" so execution goes through context.executeTool) and re-validate tool policies. Rebuilding every round is what lets a tool installed via install_agent_tool appear in the next round of the same turn (exoharness/typescript/model-runtime/turn-loop.ts:113-149).
  2. materializePromptMessages turns the event log plus instructions into Lingua messages; the request is sent streaming or not depending on context.streaming, forwarding first-chunk latency and text deltas to context.stream.
  3. responseToLinguaEvents turns the response into one messages event (carrying modelUsageRecord usage) plus a tool_requested per function call, or a synthetic tool_result error for arguments that are not valid JSON; these are appended to the turn.
  4. No tool calls → return, unless a synthetic result was produced, in which case loop once more so the model sees its own malformed call. Otherwise execute each call under a tool span and append results.
  5. Stop when round > maxToolRoundTrips (if configured) or the model stops calling tools (exoharness/typescript/model-runtime/turn-loop.ts:102-210).

Idea worth stealing: stateless Responses replay as the default

The loop never uses previous_response_id or server-side conversation storage. Every round re-renders the whole transcript from the durable event log and sends store: false; reasoning items and item ids are dropped so the replay works on reasoning models (exoharness/typescript/model-runtime/responses.ts:661-691, exoharness/typescript/model-runtime/responses.ts:996-1013). The cost is re-sent tokens (partly recovered by provider prompt caching); the benefit is that a turn can resume on any machine, any provider, with nothing but the event log. The Codex replay path reuses the very same conversion.

Tracing wraps all of this: traceExecutorTurn opens an executor_session / executor_turn Braintrust span pair (or attaches to context.braintrustParent if the Rust side passed one), and wrapOpenAI / wrapAnthropic auto-instrument the provider SDK calls (exoharness/typescript/model-runtime/responses.ts:588-660). Codex, Claude Code and Cursor reuse traceExecutorTurn too, hanging codex:<model>, claude-code:<model> and cursor-sdk:<model> LLM spans and "observed tool" spans under it.
