Architecture & crate map

How Exo splits a durable substrate (the exoharness) from the code that runs turns (the executor and the harness), how the Rust crates and TypeScript packages map onto that split, what one request does end to end, and where the trust boundaries sit.

The core split: exoharness, executor, harness

The design doc states the thesis in one paragraph: a harness conflates infrastructure (message history, secure access to privileged resources, sandboxes) with semantics (compaction, memory, which tools exist). Exo separates them. The exoharness keeps only what must be trusted and durable; the executor owns the turn loop; a harness is the pair. exoharness/docs/spec.md:3-11

The substrate API is four nested handles

Everything the substrate does is reachable from a root ExoHarness handle, which hands out agent handles, which hand out thread handles, which begin a turn and hand out a TurnHandle. A TurnHandle is deliberately tiny: add_events, write_artifact, finish. Writes through it are stamped with the turn's session and turn id, so the log records who wrote what. crates/exoharness/src/types.rs:47-74 crates/exoharness/src/types.rs:247-306

Two seams make the substrate portable

The substrate is not tied to a filesystem or to Tokio. Two small traits are the seams:

  • Storage — a byte KV (put/get/list_after/delete/copy). Keys and all metadata formats are owned by Rust; the host only places bytes. BasicObjectStore wraps it. Native uses object_store (local FS, memory); Cloudflare supplies Durable Object SQLite + R2. crates/exoharness/src/storage.rs:10-46 crates/exoharness/src/storage/native.rs:1-20 exoharness/cloudflare/src/storage.ts
  • RuntimeHost — spawn + sleep. All provider logic is written against it so it runs on Tokio natively and under waitUntil in a Worker. crates/exoharness/src/runtime_host.rs:1-16

The concrete substrate, BasicExoHarness, takes either path: new(config)/in_memory natively, or BasicExoHarness::hosted(storage, master_key, backends, host, oauth) for Workers, a constructor that is compiled only when basic-backend is off (#[cfg(not(feature = "basic-backend"))]). crates/exoharness/src/basic.rs:188-200 crates/exoharness/src/basic.rs:253-261 Multi-tenant callers are modeled by Caller { principal, policy: Arc<dyn AccessPolicy> } and ExoHarness::with_caller; every handle re-checks ResourceScope (Global / Agent / Thread) against it. crates/exoharness/src/access.rs:8-33 crates/exoharness/src/types.rs:24-37

The in-process "Harness" trait is the executor's plug point

Do not confuse the product word "harness" with the Rust trait exoharness::harness::Harness<T>. The trait is a tiny command/event interface: you submit(HarnessCommand::StartTurn(..)) and the implementation reports back through a HarnessEventSink with TurnEvents, TurnFinished and ExecutionStopped. It is generic in the work payload T, so the runtime can stack two of them: LocalProvider implements Harness<ProviderTurn> (accept a turn, enqueue it) and the inner ExecutorHarness implements Harness<ExecutorTurn> (actually run it). crates/exoharness/src/harness.rs:87-100 crates/executor/src/provider.rs:375-430 crates/executor/src/harness_adapter.rs:102-127

Idempotency means a retry can attach to a turn that already finished

TurnOptions.idempotency_key is principal-scoped and receipts live 24 hours. When enqueue reports duplicate: true, accept_local_turn re-registers the observer under the original turn id and, if the journal says the turn is finished, replays its completion through watch_turn from the start. HttpProvider does the symmetric thing on the client: with a key set, it first fetches error,turn_ended events for the turn and short-circuits if it already ended. crates/exoharness/src/turn_coordinator.rs:25-36 crates/executor/src/turn_queue.rs:437-482 crates/executor/src/native/http_provider.rs:72-103

Where durability lives for a queued turn

The CLI installs BasicExoHarness::turn_coordinator(), which persists turn_queue.json per thread; embedded LocalProvider::with_host uses StoredTurnCoordinator::in_memory() and loses its queue on restart unless you call with_turn_coordinator. On restart the runtime reconciles the saved head against the event journal: resume if started, re-run if not, ack if already complete. Event watch, SSE and reconnect semantics

The watch endpoint is the one place where two streams are merged. api::watch_events selects over (1) the thread's durable watch_events(Excluded(after)) and (2) an in-process tokio::broadcast of ephemeral progress events. Progress events (LinguaStreamChunk deltas, RuntimeStatus custom events like "Preparing workspace") are minted in forward_progress with fresh UUIDv7 ids and are never written to the log; a lagging subscriber just skips them. crates/executor/src/managed_agents/service.rs:811-826 crates/executor/src/managed_agents/service.rs:768-806

Inside BasicExoHarness::watch_events the durable half is replay-then-live without gaps: it takes the write lock, subscribes to a per-thread broadcast::channel(64) first, then lists stored event batches after the bound. If the receiver reports Lagged, it resubscribes and rescans storage from the last key it emitted. crates/exoharness/src/basic.rs:1833-1870 crates/exoharness/src/basic.rs:1912-1925

Framing

SSE with exactly three frame kinds: event: exo_event + one JSON-encoded Event in data:; event: error with {"error": "..."}; and a comment heartbeat :\n\n every 10 seconds. The decoder tolerates CRLF, multi-line data:, byte-at-a-time chunks, unknown event names, and treats a stream that ends mid-event as an error. Response headers disable proxy buffering (x-accel-buffering: no). crates/managed-agents/src/http/sse.rs:20-34 crates/managed-agents/src/http/sse.rs:74-129 crates/executor/src/native/http_service.rs:506-514 With an authenticated server, the watch also re-validates the session every second and ends the stream if it has been revoked. crates/executor/src/native/http_service.rs:482-503

Reconnect

The wire has no Last-Event-ID; resumption is explicit via ?after=<event_id> and the cursor is a UUIDv7 event id. The pieces:

  • turn_stream turns raw events into ExecutionStreamEvents, filters by turn id, and emits a Checkpoint{event_id} after every durable event so clients always know the last committed position. If the SSE connection drops it errors with "runtime progress disconnected; reconnect to retrieve saved history". crates/executor/src/harness_events.rs:322-394
  • Runtime::watch_turn(thread, turn, after) re-attaches from a checkpoint (or from just after turn_started) and re-seeds any earlier error event so partial text cannot be misreported as success. crates/executor/src/harness_executor.rs:540-596
  • Runtime::reconnect_turn is the "open the app again" path: find the latest turn_started/turn_ended; if the turn is live, replay pending approvals and attach. The inline REPL calls it at startup. crates/executor/src/harness_executor.rs:465-538 crates/cli/src/tui.rs:659-668
  • The remote client opens the watch from result.thread.latest_event_id (the head at submit time) after the 202. crates/executor/src/native/http_provider.rs:111-122

`Bound::Unbounded` means different things on the two sides of the wire

In BasicExoHarness::watch_events, Unbounded is live-only: it is rewritten to Excluded(latest_event_id) and no history is scanned. But RuntimeTransport::watch_events maps Unbounded to after = None, and the server turns None into Excluded(Uuid7(0)), i.e. a full replay. The behaviors only line up if callers always pass an explicit cursor, which the turn code does. crates/exoharness/src/basic.rs:1841-1850 crates/executor/src/native/http_provider.rs:601-615 crates/executor/src/managed_agents/service.rs:817-821

The raw `HttpExoHarness` client cannot watch or begin turns by default

ExoHttpTransport::watch_events defaults to unsupported("watch_events"), and the stock RpcTransport does not override it, so the "store RPC over HTTP" client has no event streaming at all; the docs say so ("unary only"). Event watching works only with transports that implement it: RuntimeTransport (SSE) and the Worker's AccountTransport (DO RPC subscription). In the other direction RuntimeTransport::request maps only a subset of protocol::Request onto REST routes and bail!s on the rest with "runtime HTTP does not expose …". crates/exoharness/src/http/client.rs:47-66 crates/exoharness/src/http/client.rs:114-145 crates/executor/src/native/http_provider.rs:596-598 exoharness/docs/http.md

crates/worker-runtime

worker-runtime exists to run the same Runtime, LocalProvider and BasicExoHarness inside a Cloudflare Worker. Rust is built as a cdylib with the worker cargo profile and bound with wasm-bindgen. crates/worker-runtime/Cargo.toml:9-10 Cargo.toml:109-114 exoharness/cloudflare/scripts/build-runtime.mjs

The design is "sans-IO": there is no Tokio runtime and no threads. Rust owns all logic; JavaScript owns every side effect. WorkerRuntime keeps a FuturesUnordered of in-flight operations. JS calls submit(op) to start an operation, then poll(), which advances the futures and returns a Progress value: calls (host I/O Rust wants performed), cancelled, completed operations, a pending flag and emitted runtime events. JS performs each call and answers with resolve(id, result, error). crates/worker-runtime/src/lib.rs:36-60 crates/worker-runtime/src/lib.rs:200-243

The inbound side is the mirror enum Operation: Request (store RPC), Http (the shared route table), HarnessRequest, ProxyHeaders (egress credential substitution), SandboxPolicy, DrainQueue, WatchState/WatchNext/WatchClose. crates/worker-runtime/src/operations.rs:10-47 A Worker has no sandbox providers of its own, so only one backend is registered, cloudflare, implemented by sending HostRequest::Sandbox to JS. crates/worker-runtime/src/lib.rs:81-85

Idea worth stealing: poll-driven Rust futures instead of a runtime in wasm

Rather than shipping an async runtime into wasm, poll() drains a task list, polls a FuturesUnordered in a loop until nothing woke, and returns the new host calls as data. The Host struct doubles as the RuntimeHost (spawn/sleep) and as an ArcWake, so a reply arriving from JS re-arms the loop. The result: the same LocalProvider code that runs with Tokio natively runs unchanged in a DO, and the JS side is a thin, testable switch statement. crates/worker-runtime/src/lib.rs:200-243 crates/worker-runtime/src/host.rs:133-150 exoharness/cloudflare/src/runtime.ts:49-183

The pending-watch hold keeps a Durable Object resident

While any operation is pending (for example an SSE read), the JS wrapper hands a never-resolving promise to ctx.waitUntil so the object is not evicted and its in-memory progress broadcast subscription survives; disconnecting aborts the watch and releases the hold. This is why ephemeral streaming chunks work at all on a platform that otherwise evicts idle objects. exoharness/cloudflare/src/runtime.ts:145-158

The "harness" that Codex/Claude Code run under is host-side glue; the agent is in the sandbox

It is easy to assume a Codex preset runs Codex "inside Exo's process". It does not: the TS harness module is the trusted adapter (it translates Codex app-server messages into Exo events and handles recovery), while the Codex binary runs in the sandbox and talks to the adapter over stdio via the host's start_sandbox_process bridge. That is why harness replacement keeps the thread (state lives in the exoharness) but recovery quality still depends on the adapter. exoharness/typescript/codex/harness.ts:255-270 crates/executor/src/typescript_runtime.rs:539-560

Queue ownership is not a write fence

The design doc is explicit: a turn lease token does not fence event or tool writes; "TypeScript turn requests carry durable turn ids, but there is no separate turn lease token". Single-host exclusion comes from local session leases (with_local_sessions) and the stored coordinator requiring one owner, not from per-write fencing. A competing-worker coordinator must bring its own atomicity and report lost ownership through the control watch. exoharness/docs/design/architecture.md crates/exoharness/src/turn_coordinator.rs:113-135 crates/cli/src/providers.rs:55-58
