Data model & event log

Everything durable in Exo is either a small JSON record (agent, thread) or an entry in a per-thread, append-only event log keyed by UUIDv7. Sessions and turns are not stored objects at all: they are ids stamped onto events. This page walks the types, the on-disk layout, the write/ordering rules, forking, watching, and how an interrupted turn is represented.

The mental model in one screen

The reference implementation of the exoharness traits is BasicExoHarness (crates/exoharness/src/basic.rs). It stores everything through a tiny key/value trait (Storage) and exposes four handle traits that mirror the hierarchy: ExoHarness → AgentHandle → ThreadHandle → TurnHandle (crates/exoharness/src/types.rs:46-74, crates/exoharness/src/types.rs:173-295, crates/exoharness/src/types.rs:299-305). The legacy name “conversation” is a type alias for “thread” throughout (crates/exoharness/src/types.rs:297, crates/exoharness/src/types.rs:384-388).

The conceptual docs (website/docs-src/architecture/data-model.md) describe sessions and turns as first-class concepts. In the code they are purely a labelling scheme on the log; there is no session table to query and no turn status column. Everything below follows from that.

Identifiers: UUIDv7 everywhere

Every id except sandbox/process/tool-call ids is a Uuid7 newtype around uuid::Uuid created by Uuid::now_v7() (crates/exoharness/src/uuid7.rs:8-15). The type aliases are in crates/exoharness/src/types.rs:1540-1553; SandboxId, SandboxProcessId and ToolCallId are plain Strings.

Because UUIDv7 sorts by creation time, the project leans on that three ways:

  • Ordering and cursors. Events are ordered by EventId comparison; EventQuery.cursor, watch_events(Bound<EventId>), up_to_inclusive and thread-list pagination all take event ids. There is no separate sequence number.
  • Derived timestamps. Event.created_at is set from id.timestamp() at append time, and HasUuid7Id::created_at() is a default method (crates/exoharness/src/uuid7.rs:60-66, crates/exoharness/src/basic.rs:2475).
  • File names. Event objects are named by id (see layout), so a directory listing is already a sorted log and the head can be recovered without opening any file.

Idea worth stealing: the id is the cursor, the clock and the filename

One field does triple duty, which removes a whole class of consistency bugs (sequence numbers vs. timestamps vs. keys). The thread “recency” used for listing is literally latest_event_id.unwrap_or(thread.id), so a thread bubbles to the top of the list by appending any event (crates/exoharness/src/basic.rs:1375-1377). The cost: ordering across processes is only as good as their clocks, and ids are re-minted on fork (see Forking).

The event envelope and EventData

Serialization is plain internally-tagged serde ("type": "turn_started"), with #[serde(alias = ...)] so logs written under the old “conversation” names still load while new writes use “thread” (crates/exoharness/src/types.rs:1636-1693). EventData::kind() maps every variant to an EventKind string; EventKind::matches canonicalises the four legacy names so a filter on conversation_created still hits thread_created (crates/exoharness/src/types.rs:468-483, crates/exoharness/src/types.rs:694-724). EventKind is a transparent Cow<'static, str> so EventData::Custom { event_type, .. } kinds are filterable with EventKind::custom(..) (crates/exoharness/src/types.rs:427-466).

Surprise: two “event” variants never reach the log

ThreadUpdated has no producer at all, and LinguaStreamChunk is produced only as a transient Event with a throw-away id for HTTP/SSE watchers (crates/executor/src/managed_agents/service.rs:768-790). A test asserts the persisted history contains no stream chunks (crates/executor/src/native/http_tests.rs:545-551). Likewise runtime_status custom events are progress-only. The persistent log is therefore smaller than the type suggests, and streamed text is reconstructed from the final Messages event, not from chunks.

What is stored where

The storage abstraction

Storage is a byte store with five required methods, put(key, bytes, blob), get, list_after(prefix, after), delete, copy, plus defaulted list and list_directories (crates/exoharness/src/storage.rs:11-40). Its doc comment states the contract: mutations are serialised by the harness, and the host must provide read-after-write consistency. BasicObjectStore wraps it with JSON helpers; every JSON write is serde_json::to_vec_pretty, and payloads over 64 KiB are flagged blob = true as a placement hint for hosts (crates/exoharness/src/storage.rs:46-107).

Event objects: single and batch

A single appended event becomes events/<event_id>.json. Several events appended together become one events/<first>_<last>.batch.json holding {"events":[...]} (StoredEventBatch, crates/exoharness/src/basic.rs:80-83, crates/exoharness/src/basic.rs:158-162). The range lives in the file name, so listing keys is enough to find which objects can contain an id, to compute the head, and to prune pagination. In memory, EventBatchIndex keeps batches sorted by first with a running max_last so get_event(id) can binary-search the right object (crates/exoharness/src/basic.rs:85-156).

Idea worth stealing: atomic multi-event commit via one object put

“One object put commits the whole batch.” Rather than build a transaction layer over a dumb key/value store, a multi-event append is a single PUT of a batch object; the inclusive id range in its name makes it self-indexing (crates/exoharness/src/basic.rs:2490-2497). begin_turn uses this to commit SessionStarted + TurnStarted + turn_work + input messages as one unit, which is exactly what recovery relies on.

The write path: ordering, locking, head tracking

One function appends everything

Every event written by the thread, turn and sandbox handles funnels through append_events_to_conversation (crates/exoharness/src/basic.rs:2446-2505). It mints ids with Uuid7::now() in order, writes either one object or one batch, publishes the events to in-process subscribers, and updates the in-memory record's head. Note what it does not do: it does not rewrite record.json (a test pins this, crates/exoharness/src/basic_tests.rs:1163-1165).

Where the “head” actually comes from

The head (latest_event_id) of a thread is derived from the object keys, not read from record.json. load_conversation_record loads the record and then overwrites latest_event_id with the max id parsed out of the events/ listing (crates/exoharness/src/basic.rs:2820-2832, crates/exoharness/src/basic.rs:2887-2902). The comment on refresh_conversation_record states the rule: “The event log is authoritative if a crash preceded the metadata write” (crates/exoharness/src/basic.rs:2846). Thread titles follow the same pattern: a derived title.json cache with a checked_through watermark, recomputed from the first user message when absent (crates/exoharness/src/basic.rs:2835-2885, crates/exoharness/src/basic.rs:3042-3070).

Serialisation layers

Writes are ordered by stacked locks, from outermost to innermost:

  1. Process ownership lease (claim_local_scope): when the harness was built with_local_sessions(root), the first operation on a thread takes an OS file lock sessions/<agent>/<thread>.lock via try_lock; a second process fails with “thread … is owned by another local process; use its HTTP provider”. The OS releases it on crash, and the new owner stops VMs the dead one left running (crates/exoharness/src/basic/sessions.rs:86-109, crates/exoharness/src/basic/sessions.rs:181-219).
  2. Resource locks: a per-scope RwLock map; the documented order is “agent resources, thread resources, then write_lock” (crates/exoharness/src/basic.rs:213-250).
  3. write_lock: a single AsyncMutex<()> on the whole harness, held across the storage PUT and (for appends) the head load (crates/exoharness/src/basic.rs:199). It serialises metadata writes for all agents and threads in the process.

Surprise: the head check is unreachable in the reference implementation

append_events_to_conversation takes an expected_head and fails with ConversationHeadMismatch (“turn is stale and cannot be resumed: conversation head advanced outside this turn”, crates/exoharness/src/basic.rs:2507-2556). But every caller passes the head it just loaded under the same write_lock: begin_turn (crates/exoharness/src/basic.rs:1747), TurnHandle::add_events (crates/exoharness/src/basic.rs:2307-2337), finish (crates/exoharness/src/basic.rs:2380-2426), write_artifact, and sandbox events (crates/exoharness/src/basic/sandboxes.rs:1305-1312). add_events on a thread and start/end_session pass None. So the comparison is a record against itself and the error cannot fire (grep finds one call to ensure_conversation_head). A test is explicit that interleaved writes are allowed: turn_artifact_write_allows_interleaved_conversation_writes (crates/exoharness/src/basic_tests.rs:1178-1255), and record_host_event notes it is safe because “BasicTurnHandle::add_events re-reads the head under the write lock” (crates/executor/src/native/conversation_events.rs:152-156). The architecture docs say “head tracking and write ordering stay inside the exoharness” (website/docs-src/architecture/data-model.md:46-50); in practice ordering is enforced by the lock stack plus per-thread turn serialisation upstream, not by optimistic concurrency.

The one place that does use head tracking to decide behaviour is the asynchronous snapshot publication path. A turn handle keeps BasicTurnState { latest_event_id, finished }; when a snapshot completes, if the turn is finished or the thread head has moved past the turn's last event, the SandboxSnapshotted event is downgraded from a turn-scoped sink to a thread-scoped one (no turn_id), so it never lands inside a closed turn (crates/exoharness/src/basic/sandboxes.rs:546-585, crates/exoharness/src/basic.rs:2282-2285).

Turn lifecycle on the log

Two details worth noting. First, the caller supplies the TurnRecord (ids are allocated by the queue before execution, crates/executor/src/turn_queue.rs:402-405), so a turn’s identity exists before any event does and survives a crash between queue acceptance and begin_turn. Second, TurnHandle is only a facade: turn_handle(record) rebuilds one by scanning all events of the thread for that session+turn to recover latest_event_id and finished, failing with “turn … was not found” if there are none (crates/exoharness/src/basic.rs:1776-1813). That is O(thread size), used only on recovery.

Reading events: pagination and watch

get_events

EventQuery has six knobs: cursor, direction (Asc/Desc), limit, session_id, turn_id, types (crates/exoharness/src/types.rs:408-416). The result is { events, cursor } where cursor is simply the id of the last returned event — “a resume position, even on the final page” (crates/exoharness/src/basic.rs:1815-1831). An empty page has cursor: None, so loops must stop on an empty page, as materialize_conversation_messages does (crates/executor/src/harness_helpers.rs:104-130).

The implementation (crates/exoharness/src/basic.rs:2718-2802) lists every key under events/, parses (first,last) from each filename, drops objects that cannot intersect the cursor, orders objects by first (or by last reversed for Desc), loads up to 16 at a time (buffered(16)), filters events in memory by session/turn/kind/cursor, and stops loading once limit is satisfied and the next object lies strictly beyond. The cost per page is therefore one directory listing plus the objects touched; there is no secondary index.

Sharp edge: per-page cost is O(number of event objects)

Because a thread’s events are one file per append and every query starts with a full list_keys, a long-running thread pays a listing proportional to its object count on every call (including load_conversation_record on every write, crates/exoharness/src/basic.rs:2825-2830). Batching (as begin_turn does) reduces object count; the in-process EventBatchIndex only helps get_event.

watch_events

watch_events(Bound<EventId>) returns a Stream<Item = Result<Event>> that first replays persisted events after the bound and then follows live appends. The design is “persisted journal for catch-up, bounded broadcast for the hot path”:

  • Each thread gets a lazily created tokio::sync::broadcast::channel(64) (crates/exoharness/src/basic.rs:1855-1858). append_events_to_conversation sends an AppendedEvents { key, events } after the PUT succeeds (crates/exoharness/src/basic.rs:2567-2593).
  • Bound::Unbounded means live-only from now: it is rewritten to Excluded(current head) and the history scan is skipped. (matches_bound itself returns false for Unbounded, crates/exoharness/src/basic.rs:2624-2631.)
  • The subscription is created before listing keys, so appends racing the scan land in the receiver and are de-duplicated by comparing the batch key to last_key.
  • If the receiver reports Lagged, the stream resubscribes, lists only keys after last_key, and replays them from storage: slow consumers cost storage reads, fast ones cost none (crates/exoharness/src/basic.rs:2595-2622; the test filesystem_live_watch_delivery_performs_no_storage_reads pins the fast path, crates/exoharness/src/basic.rs:2636-2680).

Surprise: watch is in-process, and the plain HTTP transport has none

The broadcast map lives in BasicExoHarnessInner, so another process appending to the same files is invisible to a live watcher. The generic ExoHttpTransport::watch_events default is unsupported("watch_events") (crates/exoharness/src/http/client.rs:57-64); the runtime HTTP provider implements it over a dedicated watch endpoint that only accepts Excluded cursors (“runtime HTTP event cursors are exclusive”, crates/executor/src/native/http_provider.rs:601-616). The same pairing — get_events cursor for catch-up, watch with Excluded(last id) for tailing — is how turn streams resume (watch_turn, crates/executor/src/harness_executor.rs:538-598). See CLI & server for the endpoints.

Forking at the data level

ThreadHandle::fork(ForkThreadRequest { up_to_inclusive, slug, name }) is a physical copy, not a pointer into the parent’s log. Under the agent-change lock, thread resource lock and write_lock, it loads every source event, drops those with id > up_to_inclusive, creates a new thread id, copies the bindings/ and artifacts/ prefixes, then re-writes each event under a fresh UUIDv7 with the new thread_id, and finally appends a ThreadForked { source_thread_id, up_to_inclusive } event and writes record.json last (crates/exoharness/src/basic.rs:1995-2120).

Consequences you can rely on or trip over:

  • Ids are not stable across a fork. The child’s events have new EventIds, so a cursor into the parent is meaningless in the child, and up_to_inclusive is interpreted in the parent’s id space. session_id, turn_id, response_id and tool_call_id are copied unchanged.
  • Copied: events (as individual files, losing the batching), thread-level bindings/ and artifacts/, and the record’s environment and vaults. Not copied: sandboxes/, title.json and turn_queue.json. Copied SandboxCreated events are history only; the fork does not own that sandbox. The conceptual doc says as much (“Not automatically restored to the fork event”); use sandbox snapshots (Sandboxes) for filesystem restoration.
  • Crash safety by commit marker. Thread listing discovers threads by record.json, and fork/create write it last, so a crash mid-copy leaves an invisible directory rather than a half thread (crates/exoharness/src/basic.rs:1333-1350).
  • Not supported with filesystem resources: check_resource_fork bails with “forking a thread with filesystem resources is not supported yet” (crates/exoharness/src/basic/native.rs:1408-1419; same limitation as docs/resources.md).
  • Forking mid-turn copies an unfinished turn (TurnStarted without TurnEnded) into the child. History derivation tolerates that (below).

Idea worth stealing: fork = replay-with-filter into a new log

Because the log is the only truth and everything else is derived, a fork needs no copy-on-write machinery: filter by a cursor, rewrite ids, add a provenance event. The cost is O(history); the benefit is that every thread is independently deletable and every id is local to its log.

Artifacts

An artifact is addressed by path; the first write of a path allocates an ArtifactId, later writes to the same path reuse it and bump version (crates/exoharness/src/basic.rs:2922-2962). Metadata ({version}.json, an ArtifactVersion) and bytes ({version}.bin) are separate objects; a legacy format with contents embedded in the JSON is still read (crates/exoharness/src/basic.rs:2964-2982, test crates/exoharness/src/basic_tests.rs:1341). read_artifact picks the requested version or the max. Agents and threads each have their own artifact namespace; thread and turn writes also append ArtifactWritten to the log (with the turn’s ids when written through a TurnHandle), agent-level writes do not (crates/exoharness/src/basic.rs:1262-1270).

Turns, the durable queue, and interrupted turns

Queue data model

Turn admission is split from execution. exoharness::turn_coordinator defines the contract: TurnAdmission::{enqueue, cancel} and TurnQueue::{claim, get, peek, start, set_suspended, acknowledge, release_if_idle, pending_threads} (crates/exoharness/src/turn_coordinator.rs:91-177). The shipped implementation is StoredTurnCoordinator, generic over a TurnQueueStore that only has load/save/pending_threads (crates/exoharness/src/turn_coordinator/stored.rs:40-45). Its state is one value per thread:

TurnQueueState<Work> {
   pending:      VecDeque<QueuedTurn{ turn: TurnRecord, work, principal, started, control }>
   receipts:     Vec<TurnReceipt{ principal, key, turn, expires_at }>   // idempotency, 24h
   acknowledged: Option<TurnId>                                          // makes ack repeatable
}
control: Run | Cancel | Suspend            attention: Wake | Interrupt

On the local backend it is serialised to turn_queue.json in the thread directory, the whole file rewritten per mutation, under the thread resource lock and refusing if record.json is gone (crates/exoharness/src/basic/turn_queue.rs:49-92); pending_threads is a scan of turn_queue.json files for a non-suspended head (crates/exoharness/src/basic/turn_queue.rs:94-115). On the hosted path the same state lives under the single key turn_queue and each save carries an alarm flag so the host wakes the thread object (crates/worker-runtime/src/turn_queue.rs:35-52).

Per-thread serialisation

  • One head runs at a time. claim(thread) returns a TurnLease only if no live lease exists; ownership is a Weak<()> identity compared with Arc::ptr_eq, so a dropped lease releases the thread implicitly (crates/exoharness/src/turn_coordinator/stored.rs:257-266, crates/exoharness/src/turn_coordinator/stored.rs:58-100). TurnQueueLocks maps TurnThread to a weak ThreadState with an async mutex; entries disappear when unused.
  • FIFO with cooperative control. enqueue appends; Interrupt attention cancels the same principal’s claimed or started head atomically before appending (never an unclaimed one) (crates/exoharness/src/turn_coordinator/stored.rs:165-238). Cancel/suspend flip control and push through a watch channel to the running turn.
  • Idempotent admission. Duplicate = same turn id already pending, or same (principal, idempotency_key) receipt within 24h (or forever with retain_receipt). Duplicates never interrupt and return the original TurnRecord. The shared admission contract is executable (crates/exoharness/src/contract_tests.rs:31-133).
  • Execution loop. The executor’s run_queue peeks the head, starts it (setting started = true and persisting before any journal event exists), runs it, checks the journal, and only then acknowledges (pops the head and records acknowledged) (crates/executor/src/turn_queue.rs:581-704).

Surprise: durable by choice, in-memory by default

LocalProvider::with_host installs StoredTurnCoordinator::in_memory(); durability requires .with_turn_coordinator(...) (crates/executor/src/provider.rs:131-155). The CLI wires state.turn_coordinator() (file-backed) and the worker runtime a host-backed one (crates/cli/src/providers.rs:90-93, crates/worker-runtime/src/lib.rs:120). A test documents the default: after a restart an in-memory queue recovers nothing from the journal (crates/executor/src/turn_queue/tests.rs:585-612). Also note TurnQueueStore is documented as “single process/object owner”; competing workers need their own transactional coordinator.

There is no “interrupted” event or status field. The state of a turn is computed from its events by journal_status_from_events (crates/executor/src/turn_queue.rs:843-892):

Idea worth stealing: recovery state lives in the log, scheduling state in the queue

The queue says whether a turn is wanted and in what order; the journal says how far it got. By committing turn_work in the same atomic batch as TurnStarted (BeginTurnRequest.initial_events, crates/exoharness/src/types.rs:396-406), a crash can never leave a started turn without the information needed to resume it. Disagreement between the two is reconciled in one place: “the journal is authoritative” (restart_reconciles_completion_and_admission_before_journal_creation, crates/executor/src/turn_queue/tests.rs:456).

From events to prompts

The log is not the prompt. The Rust BasicExecutor derives message history on each model round with materialize_prompt_history: query only messages, tool_requested, tool_result and the frontend-tool-response custom event, Asc, starting after a per-thread cached cursor, then fold the new events into a cached Vec<Message> (crates/executor/src/basic.rs:80-134, crates/executor/src/basic.rs:29, crates/executor/src/basic.rs:582-586). The fold is extend_message_history (crates/executor/src/message_history.rs:15-128). TypeScript harnesses build their own views; see Harnesses.

The fold repairs what interrupted turns leave behind. It tracks pending_tool_call_ids from assistant tool-call parts and ToolRequested events; if a later non-tool message arrives (or the batch ends) with calls still pending, it synthesises a tool result so the transcript stays valid for the provider:

Surprise: the history cache bakes in the cancellation it fabricates

The doc comment says “each batch must contain complete tool rounds: calls still pending at its end receive cancellation results, and their later real results would be discarded” (crates/executor/src/message_history.rs:13-14). Combined with an incremental cursor cache, a prompt materialised while a tool call is still in flight caches the synthetic “did not complete” result; the late ToolResult is skipped because it is no longer pending (crates/executor/src/message_history.rs:96-101). The cache is a plain HashMap<ConversationId, _> and this file never evicts entries. Safe only because one turn runs per thread at a time.

Usage and cost on the log

Messages.usage carries an optional boxed UsageRecord (model, prompt/completion/cached/cache-creation/reasoning tokens, cost_usd, ttft_ms, duration_ms), boxed so the enum stays small (crates/exoharness/src/types.rs:522-545, crates/exoharness/src/types.rs:592-599). The design doc (exoharness/docs/design/cost-tracking.md) makes the key choice: the substrate stores usage verbatim and computes no money; cost is userspace policy provided by the standalone cost crate. That crate is pure math plus a loader: PricingTable::compute_cost_usd treats Anthropic-family providers as additive (prompt excludes cache) and everything else as inclusive (subtract cached first), with a token-boundary prefix match for model names (crates/cost/src/table.rs:59-115); cost::load resolves explicit path, then a fresh 24h cache, then a 5s HTTP fetch of the LiteLLM price JSON, then a stale cache, then an empty table, and never fails (crates/cost/src/loader.rs:16-58). The executor fills the record in build_usage_record (crates/executor/src/model_events.rs:32-72).

Code vs doc: the code prefers a provider-reported cost (response.provider_cost_usd, e.g. OpenRouter) and only falls back to the local table (crates/executor/src/model_events.rs:43-56); the doc does not mention this. The doc also says cache_creation_input_token_cost_above_1hr is “parsed but unused”, but ModelEntry has no such field (crates/cost/src/table.rs:8-20). When the CLI builds a provider without execution args, or the loader finds nothing, the table is empty and cost_usd stays null while tokens still persist (with execution args, cost::load runs and defaults to the public LiteLLM URL) (crates/cli/src/providers.rs:80-89).

Resources, environments, access (brief)

  • Environments (EnvironmentDefinition) are named, validated JSON files at environments/<name>.json; a thread’s ThreadRecord.environment embeds a copy (crates/exoharness/src/environment.rs:9-37, crates/exoharness/src/basic.rs:415-440). Details of what they configure are in Sandboxes.
  • Resources (ResourceDefinition = directory or git source, mount path, mode) are not events or object-store keys. ResourceStore uses plain std::fs under <root>/resources/{snapshots,threads,locks}; local sources are pinned to a content-keyed snapshot when the agent is registered, and each thread gets a private copy-on-write clone recorded in resources.json (crates/exoharness/src/resources.rs:10-60, crates/exoharness/src/resources/local.rs:90-215, docs/resources.md). materialize refuses to change a thread’s resources after the fact (“cannot change the resources of an existing thread”). The log only sees them as FileSystemMounts inside sandbox events.
  • Access. A Caller { principal, policy } wraps an AccessPolicy (check, created, check_operator, vault hooks) (crates/exoharness/src/access.rs:7-33). Every handle method begins with harness.check(ResourceScope::..); creation calls claim so the policy can record ownership; TurnStarted.user_id and queue principals carry the caller; caller.json tracks the last active principal and resets managed sandboxes when it changes (crates/exoharness/src/basic.rs:1488-1527).
