Prompts, verbatim

Every piece of LLM-facing text in the repo that is worth reading: system prompts, tool descriptions, per-round context injections, runtime notices and error strings, and eval task prompts. Each is quoted from the source, with where and when it is injected and what technique it uses.

How prompts reach the model

Exo has no global prompt. By default the model sees four things: the agent definition's markdown body as one system message, a few system messages appended by the runtime (filesystem resources, preview URLs), the durable event log replayed as conversation history, and tool definitions. Everything else on this page is added by a harness (a TypeScript instructions hook, or Rust code in an executor).

The load-bearing design choice is that harness-generated instructions are not written to the event log. They are recomputed and prepended on every model round. That is what lets a harness show the model the current game screen, todo list, memory block or skill index each round without the history growing.

 agent.md body --> AgentConfig.instructions = [ system(body) ]
                    + system("Filesystem resources...")  new threads
                    + system("Exo sandbox previews...")  if previews registered
                              |
                              v
 each model round, sent to the provider:
   [ instructions + whatever the harness hook adds ]   recomputed, not logged
   [ replayed event log ]                              stored: messages, tool I/O
   [ tool definitions ]                                rebuilt every round

Surprise: the TS example harness features do not reach Codex, Claude Code or Pi

So a runtime system message such as the preview-URL block reaches them, but a per-round injection like the live todo list does not.

Identity and system prompts

Managed-agent definition body

An agent file is YAML frontmatter plus a markdown body. The body is the entire prompt: validate() rejects an empty one, and agent_config() turns it into a single system message. There is no built-in Exo preamble, no tool-use boilerplate. A per-turn system_prompt in the HTTP request body replaces the whole instruction list.

The shipped example agents show the style: short, task-shaped, evidence-demanding.

Other bodies: exoharness/examples/managed-agents/assistant.md:8 ("Help the user with their task."), exoharness/examples/managed-agents/github-analyst.md:12-14, exoharness/examples/managed-agents/notion-analyst.md:12-14. The longest is exoharness/examples/managed-agents/fastapi-developer.md:15-39, which is really a runbook: it tells the model to run a setup script with "the exact browser preview URLs for guest ports 5173 and 8000 provided in the thread context" and what to report back. That "thread context" is the preview notice below.

Idea worth stealing: pair behavioral text with the permission policy it assumes

pi-assistant.md ends with "Respect denied tool calls and explain what remains undone." and sets permission_policy: always_ask in the same file. The denial is delivered to the model as plain text (see approval denials), so the one sentence of prompt closes the loop: the model has been told what to do when the runtime says no.

System messages appended by the runtime

Two system messages are pushed onto agent_config.instructions when a thread is configured. The filesystem one is skipped when the thread is being recovered; the preview one exists only when previews are registered.

In the figure above, the last paragraph is the literal string; the first lines are the format! templates with placeholders named. The filesystem notice has no prose, only a header and a list:

Technique: end operational notices with the failure modes

The preview notice does not just list URLs; its last sentences pre-answer the three things a model gets wrong: which hostnames to use for links and CORS ("preserve paths, queries and fragments"), where guest ports apply ("Inside the sandbox use guest ports"), and what a 502 means ("Start services first"). It is a tiny runbook attached to a data block.

Slack input preamble

Managed adapters do not give the model any adapter instruction (docs for the old tool-based adapters are stale; see drift). The only injected text is a one-line label in front of the user's message. Replies are delivered by the adapter observing the turn's stream, not by a tool.

So the model sees [slack user <sender id>] on one line followed by the message text (the turn is started at crates/executor/src/managed_agents/adapters/mod.rs:780), as a plain user message (kind() is the only adapter kind, "slack").

Scheduler wakeup prompts

When a scheduled sandbox task finishes, the host sends a synthetic user message into the conversation. The agent-authored reportPrompt is embedded under "Report instructions", so the agent writes instructions for its future self. The prompt is saved as a pending fire before delivery (crates/executor/src/native/scheduler_runtime.rs:326-355) and sent as a plain user message (crates/executor/src/native/conversation_wakeup.rs:12-47).

Each stdout/stderr preview is capped at 4,000 bytes (crates/executor/src/native/scheduler_runtime.rs:592-597); the full result lives in the named artifact, so the model gets a pointer plus a sample.

RLM: the REPL-as-context prompts

The rlm harness (a recursive language model setup) does not put the conversation in the prompt. It flattens history into a JavaScript string called context, gives the model a REPL to explore it, and a subquery tool that calls the same model recursively. The prompt is what makes that workable. Rust is the canonical implementation; the TypeScript port is an example.

Between those, {mounts} is either "No external filesystem mounts are configured for the conversation." or one line per mount, - host -> mount (ro|rw) (crates/executor/src/native/rlm.rs:650-669). {preview} is the first 400 characters of the transcript printed with Rust {:?} formatting (crates/executor/src/native/rlm.rs:32).

Analysis.

  • The prompt is a spec of the implementation. "Only JSON-compatible values persist across calls" is literally how it works: every repl_execute builds a fresh Boa JS context, injects context and getMessages, restores the previous globals from JSON, runs the code, then serializes whatever on globalThis survives JSON.stringify (crates/executor/src/native/harness_js_repl.rs:27-117). A function stored on globalThis does not come back, because JSON.stringify drops function values.
  • Termination is a three-way protocol. Preferred: set globalThis.Final; the loop checks js_state.final_value() after every tool call and ends the turn immediately (crates/executor/src/native/rlm.rs:275-278). Fallbacks: reply FINAL(...) or FINAL_VAR(name), parsed by prefix/suffix (crates/executor/src/native/rlm.rs:581-611), and finally any plain text reply with no tool calls is accepted as the answer (crates/executor/src/native/rlm.rs:132-136).
  • Output budget is explained to the model. "Only truncated REPL output is surfaced back to you each iteration" is why it should keep state in variables; the cap is 12,000 characters (crates/executor/src/native/rlm.rs:30). The sentence turns a hidden limit into a strategy.
  • Anti-narration. "Think step by step carefully, plan, and execute immediately. Do not just say what you will do. Prefer code, variables, and recursive subqueries over long prose." Pushes the model to act through tools, which matters because plain text ends the loop.
  • Sub-model hygiene. The sub-LLM gets tools: Vec::new() and "Do not mention this instruction.", so a subquery answer can be pasted into a variable and passed along without meta-chatter. subquery_variable builds {question}\n\nContext:\n{variable} (question first, big context last).

Surprise: the Rust system prompt contains literal double braces

The Rust root prompt uses format!, so {{ index, role, content }} collapses to single braces. The Rust system prompt is a plain String::from, so the model is actually shown {{ index, role, content }} with doubled braces (crates/executor/src/native/rlm.rs:623) while the TypeScript port shows { index, role, content } (exoharness/examples/typescript/rlm-harness.ts:521). Harmless, but a real divergence between the two implementations. Another difference: Rust says "The REPL is secure and intentionally limited", TS drops "secure".

Idea worth stealing: put the context in a variable, not in the prompt

The root prompt carries only the latest request, the transcript's length and a 400-character preview. The full history is a string the model must go and read with code, with getMessages(role) as a structured accessor over a turn-start snapshot. The prompt says so explicitly ("The prompt string in context is the external environment"), so the model treats history as data to query rather than text to continue.

Coding agent harness (tutorial)

A deliberately small prompt for a terminal coding agent. It is assembled from three developer-visible pieces each round: the system prompt, an <env> block, and the current todo list (re-read from an artifact every round).

Analysis. The todo policy is stated twice, in the system prompt and again in the tool description, so the rule is in front of the model both in the prompt and next to the tool schema. "Mark an item completed only after you have verified it works — a command that ran, a test that passed — never on intent alone" defines "done" in observable terms. "Prioritize technical accuracy over agreement" is the anti-sycophancy line. "Reference code locations as file_path:line_number" makes answers clickable. The mutable state (the todo list) is rendered as a developer message each round instead of being left in tool history where it would scroll away.

"The intro is a trap for RAM readers... That flip does NOT mean the intro is over. Idea worth stealing: use the final summary as the memory channel

The harness has no memory tool. Instead the prompt says "reply with a short summary: what you did, what you learned, what to do next time. Your summaries persist in the conversation, so put anything worth remembering there." The only state that crosses turns is assistant prose, so the prompt tells the model to write for its future self.

Cursor SDK preamble

The Cursor SDK takes a single prompt string, so Exo renders instructions and history as a transcript and wraps it in framing text.

"Exoharness is the source of truth for durable conversation history. Treat the transcript below as the canonical prior state." tells a stateless SDK session not to trust anything it remembers. The transcript uses ROLE:\ncontent blocks from messagesToTranscript (exoharness/typescript/harness/index.ts:774-778), which is the same flattening RLM uses for context.

Tool descriptions as prompts

Tool names, descriptions and parameter descriptions are model-visible on every round, and the repo treats them as prompt text: the self-improving agent's own prompt guide says "If a model calls a tool incorrectly, the right fix may be a tool description rather than an identity prompt" (examples/self-improving-agent/docs/prompts.md:120-125). Descriptions here are long, procedural, and often contain the "when" and "when not" as well as the "what".

Built-in tools (TypeScript)

The shell tool's description is intentionally nothing but the interpreter name; the real guidance is put in the harness prompts (for example the coding agent's "Inspect the codebase with commands (ls, cat, grep) instead of guessing"). crates/executor/src/shell_tool.rs contains no prompt text, only the execution path ($program -lc $command).

exoharness/typescript/harness/built-in-tools.ts:194 is a single-quoted JS string, shown above with its escapes resolved (the "${ENV_VAR}" reference is literal). Note how many of these sentences are about one failure: the model writes a tool into a sandbox path but the host resolves the install path, so "never pass /tmp or an absolute sandbox path" appears in the description, the parameter description, and the self-improving agent's developer message.

Analysis. This is a prompt that was clearly written against observed failures. It names the exact wrong shapes a model reaches for ("Do not use zod, inputSchema... handlers must implement execute(args, execution), not invoke or call"), requires the success signal before claiming ("Do not claim the tool was created unless install_agent_tool returns ok: true"), and prevents a fallback detour ("use it directly rather than falling back to shell"). The "available in the next model round of the same turn" sentence matters because the tool registry is rebuilt per round (exoharness/typescript/model-runtime/turn-loop.ts:122-124).

Idea worth stealing: negative-example lists written from real failures

A "do not use zod, inputSchema, ... runtime imports from @exo/harness/tool" list appears in three places, each slightly different (exoharness/typescript/model-runtime/turn-loop.ts:98, exoharness/typescript/harness/built-in-tools.ts:412, examples/self-improving-agent/harness.ts:91). The longest version is "Do not use inputSchema, run, call, invoke, zod, external npm packages, or runtime imports from @exo/harness/tool" (harness.ts). It reads like a changelog of what models tried when asked to write a tool for this harness, and it is repeated wherever the model is looking when it makes the mistake (instruction, tool description, parameter description).

Skill tools

Skills follow the agentskills.io layout (SKILL.md with name and description frontmatter). The design is progressive disclosure: only names and descriptions go in the prompt each round, bodies load on demand.

Error strings returned to the model by these tools are also written as instructions: skill not installed: {name}. Use list_skills to see installed skills. and skill content unreadable for {name}; the stored artifact appears corrupt. Reinstall with install_skill. (exoharness/typescript/harness/skill-tools.ts:379-389). The frontmatter validation error says what the description should contain: "should say what the skill does and when to use it" (exoharness/typescript/harness/skill-tools.ts:287).

Self-improving agent tools

Other descriptions in the same directory: web_search and web_fetch (examples/self-improving-agent/tools/web-tools.ts:601-602, examples/self-improving-agent/tools/web-tools.ts:677-678) state their backend, caching, redirect and private-address behavior in the description. delete_scheduled_task says "Use cancel_scheduled_task instead when history should be preserved" (examples/self-improving-agent/tools/scheduler-tools.ts:168-170).

Idea worth stealing: make the tool description answer "how do I know my own spend?"

list_conversation_events documents that every messages event carries a usage annotation with cost_usd, and that "this tool is also how to answer questions about spend: query kinds ["messages"] and sum usage.cost_usd". The self-improving tool set has no separate cost tool; the description teaches the model to derive it from the log. It also warns which event kinds "can be very large" so the default is a small lifecycle set.

Idea worth stealing: free-text reason fields that become the audit trail

rebuild_and_restart_exo asks for a reason and says "Prefer a concrete description over null"; the description explains that the outcome is "durably" recorded and "self-describing" later. The same sentence is repeated in examples/self-improving-agent/prompts/me.md:22, examples/self-improving-agent/harness.ts:87, and examples/self-improving-agent/harness.ts:112. The model is being asked to write for an auditor, and told why.

Context management, memory, and the missing compactor

Surprise: there is no compaction or summarization prompt anywhere

A search of crates/, exoharness/, examples/, eval/ and the docs finds no history-summarizing prompt, no "compact" instruction, and no LLM call that titles threads (thread_name_from_messages just takes the first 80 characters of the first user message: crates/exoharness/src/basic.rs:3042-3070). The Rust basic harness replays the full event log every round (crates/executor/src/basic.rs:130-132). Context control is done by other means: re-injecting small mutable state each round (below), keeping heavy state in artifacts, and, in RLM, never putting history in the prompt at all.

Per-round state injections

The self-improving harness builds its instruction list each round from a static stack (base instructions, identity, name, harness manual, repo pointer, optional local profile) followed by three dynamic blocks (memory, todos, skills). Each dynamic block returns null when it has nothing to say, so empty state costs zero tokens.

Idea worth stealing: degrade the prompt, never brick it, and never lie

Instruction assembly runs every round, so a corrupt memory artifact would take down every conversation. The code catches the read error, logs loudly, and injects "Your durable memory could not be read this turn... Do not assume it is empty; if the user asks about saved facts, tell them memory is temporarily unavailable." The write tools still throw, so nothing overwrites the corrupt store. The model is told the true state of the world (unknown) rather than being shown an empty list (examples/self-improving-agent/tools/memory-tools.ts:196-209, exoharness/typescript/harness/skill-tools.ts:507-525).

Idea worth stealing: tell the model the freshness contract

"This is measured fresh for every model round, so treat it as current." (sysmon), "refreshed for this model round" (Game Boy), and "The current list is shown back to you each turn" (self-improving todo section, examples/self-improving-agent/harness.ts:102) all state when the data was produced. That lets the model trust the block over its own stale earlier tool output.

Analysis of me.md.

  • Act, then escalate with a counter. "bias toward acting: proceed on reasonable assumptions and notify progress rather than asking. Ask only when genuinely blocked on something only the user can provide, and after about three failed attempts on the same blocker, stop and escalate it plainly instead of looping." Gives both a default (act) and a stop condition (about three), which prevents the usual two failure modes of agents: asking too much and looping forever.
  • Two operating modes in one rule. The next sentence handles headless runs: "When running autonomously with no user attached (scheduled or adapter-triggered work), there is no one to ask... record the blocker clearly (an event, report, or external message) and fail loudly rather than waiting." The model is told which mode it is in by the trigger, not by a flag.
  • Ground claims in files. "Do not speculate about code you have not opened. Before explaining or changing a file, read it. When you reference code, cite it as file_path:line_number."
  • Mutable tool surface. "The set of tools available changes turn to turn... never assume a tool exists because it did earlier, and check the current set before calling one." This is true by construction: the registry is rebuilt every round and agents can install tools mid-turn.
  • Operational guard rails as imperative one-liners. "Never run git add . — stage only the files you intend to commit — and never force-push"; "do not manually kill host processes" (use the guardian).
  • Scope inheritance. When working in a user's repo, "read and follow any AGENTS.md or CLAUDE.md in scope, the same way you consult SELF.md for Exo itself. More deeply nested files take precedence, and explicit user instructions win over both." A one-sentence precedence rule.

The only adapter type in the code is Slack (crates/managed-agents/src/adapters.rs:7-11), and Slack replies need no tool. The rule "include the adapter id and target in the task reportPrompt" (line 13) is likewise a leftover. Line 21 tells the model to read /workspace/examples/self-improving-agent/examples/self-improving-agent/SELF.md, while harness.ts tells it /workspace/exo/examples/self-improving-agent/SELF.md (examples/self-improving-agent/harness.ts:28). examples/self-improving-agent/docs/prompts.md:219-226 also lists a "Fal image-generation developer message" that is not in harness.ts. Prompts drift from code the same way docs do, and nothing tests them.

Idea worth stealing: the layered override ladder

Committed generic identity (me.md) → code-embedded manual (harness.ts) → git-ignored per-machine .exo/exo-profile.md, created by exo.sh setup-profile from two read -p questions (examples/self-improving-agent/exo.sh:665-684). The profile is just a markdown file appended as a developer message, with chmod 600, and the docs state the rule: "Do not put secrets in instructions, setup prompts, tool descriptions, or scheduler reportPrompt values" (examples/self-improving-agent/docs/prompts.md:350-352).

Injected runtime notices and error text

Text the runtime itself writes into the model's context. Most of it is JSON error envelopes, not prose, but the strings are chosen to be actionable.

Tool failure envelope

The TS runner does the same: a thrown error becomes { ok: false, error: errorMessage(error) } (exoharness/typescript/harness/tools.ts:90-105). Malformed tool-call arguments become synthetic results with strings such as "function call arguments must be a JSON object" (exoharness/typescript/model-runtime/responses.ts:1189-1192). Rust errors use {error:#}, so the model receives the whole anyhow context chain, not just the outermost message.

Interrupted tool calls

If the process died after a model requested a tool but before the result was stored, replay inserts a synthetic failed result so every tool call in the history has a paired result.

Egress rejections (visible to code in the sandbox)

The credential-substituting proxy never talks to the model; it talks to whatever program the model ran (curl, git, a package manager). Its response body is what ends up in tool output. Until the latest commit every failure was a 502 with one generic line; now a resolver can return a typed EgressError::Rejected(message) that becomes a 403 with the message verbatim.

Surprise: the useful rejection path has no producer yet

Outside tests nothing in the repo constructs EgressError::Rejected (only the match arms at crates/exoharness/src/egress/mod.rs:599 and crates/worker-runtime/src/operations.rs:152 exist). The built-in vault resolver returns denied(...) for a missing credential (crates/exoharness/src/egress_credentials/session.rs:137), which the native proxy deliberately flattens to "egress request denied or upstream unavailable" so no diagnostic leaks. The hosted worker path, by contrast, returns format!("{error:#}") including the denied text. So today an agent sees a diagnosis only from a hosted resolver that opts in with Rejected. The docs for this are Egress and vaults.

Eval prompts

The Harbor datasets hold the only prompts written purely as tests. They are short, exact about artifacts, and written to be unambiguous to a grader.

The lifecycle smoke test is a single line, eval/harbor/datasets/smoke-test/lifecycle-smoke/instruction.md:1: "Create `/app/done.txt` containing exactly `ready` followed by a newline."

Analysis. The 01/02 pair tests persistence across trials: 02 says "Do not reinstall, replace, or recreate it" and "The point of this trial is to demonstrate that the tool installed by the earlier trial is available in this fresh conversation and container." Both forbid the shell shortcut ("Do not implement the transformation with shell") so the tool's presence is observable in the trajectory. Task 03 gives a numbered protocol for an asynchronous event ("do not end your turn here", "re-check periodically instead of giving up") and insists values "come from the tool result and the event log, so do not invent or guess either one". Task 04 intentionally cannot succeed ("Harbor will stop waiting after 30 seconds") and says so, so the model does not try to be clever.

Idea worth stealing: tell the agent the test is a test when the point is the trajectory

Tasks 02 and 04 state their own purpose. The grader checks files, but the thing being evaluated is behavior (reuse, not reinstall; keep waiting, do not shorten the sleep), so the instruction removes ambiguity about intent rather than hiding it. The set's README states it "does not enforce the mechanism by which the agent accomplishes the smoke test" (eval/harbor/datasets/self-evolution-smoke-test/README.md:3).
